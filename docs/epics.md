# Epics and milestones

Plan of record for building W1. Status: draft for owner review, 13 Nov 2026. Requirements are in `docs/prd.md` (FR and NFR ids), structure in `docs/architecture.md`, decisions in `docs/decisions.md` and `docs/adr/`. Code is authoritative over this document once building starts; status syncs are dated.

## How the plan works

- **Milestones end on exit criteria, not dates.** A milestone is done when every exit criterion is demonstrated, not when its epics are merged.
- **Epics are vertical where possible.** Each epic lists acceptance criteria that a test or a demonstration can check. Epics become tracker issues when the owner approves this plan; the issue links back here instead of copying the criteria.
- **No separate spikes** (decision 24). An unknown is resolved by the first slice of the epic that meets it, with its exit criteria written before the work starts.
- **Every feature module ships its agent tools** with risk tiers (ADR-0007, ADR-0010). A feature is not done until an agent can use it through MCP.
- **Sizes** are rough: S (a few days of agent work, one or two pull requests), M (about a week, several pull requests), L (more than a week, split before starting).

## Definition of done (every epic)

1. Behaviour is covered by tests at the agreed seam: the core's submit-a-command interface, the MCP surface with a real client and Postgres, the app layer driven by a test harness, or a browser end-to-end test. A failing test comes first for behaviour changes.
2. CI is green: format, lint, tests, layering checks, size ceilings, UI literal lint, licence check, a local Cora agent review of the whole diff, recorded in the pull request, with no major or critical finding left.
3. Docs touched by the change are updated in the same pull request (architecture, ADR, glossary, MCP tool catalogue).
4. Agent-facing text and errors are English with stable codes.
5. Commits are signed off and carry no AI attribution; pull requests stay small (15 files or fewer and under 1,000 changed lines, ceilings 20 and 1,500, one kind of content) and the heavier gates are run locally before the pull request.

## M0 Foundation

Goal: the skeleton every feature plugs into, with the standard enforced from the first commit.

### E0.1 Workspace layout by kind (S)
Crates under `crates/{core,engines,integrations,features,app,ui}`, apps under `apps/{server,web}`, each crate declaring its kind (ADR-0007).
- [x] Every crate declares `kind` (and `group` for features) in its manifest; a crate without one fails the check.
- [x] `cargo xtask deps-check` enforces the matrix in `docs/architecture.md` section 3b; its rules are a pure function with unit tests, including one failing case per rule.
- [x] `cargo xtask build-matrix` builds the product with no features and with each feature alone.
- [x] `cargo xtask portable-check` compiles core, engine, integration, feature and app crates for `wasm32-unknown-unknown`.
- [x] `unsafe` is denied workspace-wide.

### E0.2 CI and review gates (S)
- [x] CI runs format, lint (warnings as errors), tests, `deps-check`, `build-matrix`, `portable-check`, `size-check`, `ui-literals`, `licences --check`. (The fast set runs on every pull request; `build-matrix`, `portable-check`, `size-check`, `ui-literals` and `licences --check` run nightly and on demand; `just check` runs all of them except `licences --check`, which is run as `cargo xtask licences --check`.)
- [x] `size-check` enforces 500 lines per file and a ceiling per crate (2,000 when this was ticked, 4,000 from decision 35, 50,000 from decision 42) with an allow-list that only shrinks.
- [x] A local Cora agent review is run and recorded for every pull request (CI Cora is disabled); branch-name and message-standard checks reject AI attribution and wrong prefixes.
- [x] `develop` requires CI to pass before merge; `main` exists and receives release tags only.

### E0.3 Protocol and schema pipeline (S)
- [x] Wire and model types live in `meldframe-protocol`; TypeScript types are generated and a CI check fails on drift.
- [x] Every stored document and snapshot carries a schema version from the first migration.
- [x] Postgres migrations run from a clean database in CI.

### E0.4 Local development environment (S)
- [x] One command starts Postgres and the server for development; one command starts the web client against it. (`just dev` is smoke-tested (`tools/dev-smoke.sh`, in the migrations CI job); `just web` builds the WASM bridge when it is missing and starts the editor on `file_dev` with `/v1` proxied to that server through the guarded dev proxy. Proven on 17 Nov 2026 with `packages/web-e2e/scripts/editor-e2e.mjs`: against the real server and the real WASM the page connects and draws the saved file, shows a change of an agent without a reload, and reconnects after the server was stopped and started again.)
- [x] A seeded development workspace, file and token exist for agents and tests (development only, never in a release build).
- [x] `AGENTS.md` lists the commands; a new session can run the full test suite from a fresh clone.

**M0 exit criteria:** a pull request that breaks a layering rule, a size ceiling or a UI literal is rejected by CI; a fresh clone builds and tests green with one command.

## M1 Connected skeleton (owner's first goal)

Goal: backend, a basic web editor and MCP connected end to end on the carried spike core. Authentication uses development tokens behind the gate's principal interface; Gatehouse arrives in M2 without changing callers.

### E1.1 Core seed (M)
Carry the document core from the spike (decision 14, survey section 6.1): `Command`, validation, history with per-actor undo, replica with rebase and op dependencies, fractional order, layout with the text measurer seam.
- [x] The spike's property tests (convergence, undo, rebase, dependencies) run in this repository and pass with at least 600 seeds per run in CI and more nightly. (600 seeds per run in `cargo test --workspace`; 6,000 in the nightly `property-tests` job.)
- [x] Mutation check: disabling the dependency rule or the per-actor undo rule makes a test fail. (`tools/mutation-check-sync.sh`: eighteen mutations, all killed.)
- [x] Names follow `GLOSSARY.md`; no spike ids remain in file or type names; comments are English.
- [x] The core compiles natively and to WASM with the same tests. (`just wasm-test` passes locally: 233 tests, the six core crates plus the two property-test crates, from the same sources. The `wasm-test` job of the nightly workflow passed on a runner: run 4129, job 13095.)

### E1.2 Room, persistence and snapshots (M)
- [x] One room per file accepts ops in one total order, persists them append-only with actor, idempotency key and sequence number, and snapshots periodically. (`Server` opens one room per file through `meldframe-rooms::Rooms` with a store per backing, `PgStore` or memory; `apps/server/tests/rooms.rs` proves two files stay apart, a retried key writes nothing and a closed file returns with its content; the store contract, snapshots and Postgres cases are in `pg_contract.rs`. Caveat: files are namespaced by workspace in the store key, not in a schema column, until E2.3; the binary picks `PgStore` when `DATABASE_URL` is set (`just dev`, `tools/dev-smoke.sh`).)
- [x] Restarting the server restores every file from snapshot plus log with no change in content (test). (`apps/server/tests/pg_server.rs` builds a `Server` on Postgres, writes 520 ops to one file (past the 500-op snapshot interval) and one to another, drops the server, builds a new one on a fresh connection and compares both trees and sequence numbers, then checks that old keys are still remembered and the next number continues. It skips without `DATABASE_URL`; with `MELDFRAME_REQUIRE_PG` a missing URL fails. The restart test restarts a `Server` on real Postgres, not only a `Room`. A second test restarts and checks that another workspace opening the same file name gets an empty file. Caveats: workspace namespacing is by key, not a schema column (E2.3); the binary now picks `PgStore` from `DATABASE_URL` (`tools/dev-smoke.sh`).)
- [x] A retried op with the same key returns the same sequence number and writes nothing (test). (At the `Store` and `Room` seams. The store refuses the same key with another command (`KeyReused`) and the room reports it as `invalid`. `PgStore` passes the same cases through the shared `meldframe-store-contract` suite, which the in-memory adapter also runs.)
- [x] A dependent op is accepted only if every dependency was applied (carried F3 behaviour, test). (In `Room::accept`, with a property test of replicas fed by the real gate and room; applied keys are kept in the log. The rule is written down in `docs/architecture.md` 7a, one test per clause in `meldframe-rooms/tests/dependencies.rs`.)

### E1.3 Admission gate (M)
ADR-0010; the survey's candidate 2.
- [x] WebSocket, MCP and REST submit through one gate; the room accepts a write only with a permit the gate creates, so a path that skips the gate does not compile. (Proven: the permit and the compile-fail proof in `meldframe-rooms`, and `Server::submit_tool` takes a file and goes Gate, Admission, `Rooms::accept` with no `&mut Room` exposed. The WebSocket and REST transports now call `Server::submit_tool` through one handler in `meldframe-http` and have no other write route (tests). MCP calls the same `Shared::submit_ops` on the same router state; `meldframe-mcp-tests/tests/gate.rs` proves one submitter for an MCP and a REST write and one rate budget per principal across both.)
- [x] Refusals have stable codes and English messages (`forbidden`, `quota_exceeded`, `conflict`, `invalid`, `dependency_rejected`, ...), listed in one table that a test checks against the code. (`docs/error-codes.md` has the gate table; `tests/refusal_codes.rs` in `meldframe-host` checks it.)
- [x] Rate limiting happens before parsing; per-call timeouts apply (carried H1 behaviour, tests). (`meldframe-http`: per-address and per-principal token buckets with an injected clock, spent before the body is read, proven with a body that is never polled; body size limit; per-call timeout. Limits: the budgets are in memory per process, and a timed-out call may still write.)
- [x] The principal comes from development tokens through an interface that Gatehouse implements in M2. (`Authenticator` trait; `DevTokens` reads `MELDFRAME_DEV_TOKENS` from the environment, never argv.)

### E1.4 Live events (S)
ADR-0009. Status: the stream logic is the `meldframe-stream` crate (pure, no transport; `crates/core/meldframe-stream/tests/stream.rs`). `Server::submit_tool` publishes each op the room wrote (not a retried key) to the hub of its file, and `Server::subscribe` reads the range older than the window from the store (`apps/server/tests/live.rs`). The transport is `GET /v1/live/{file}?after={seq}` in `meldframe-http-live` (built on `meldframe-http`; `live_router` or `routes`; one socket per file, so the handshake answers 401, 429 or 503 as a status and one connection owns one stream), with the `resync` and `heartbeat` frames in the protocol crate, and a timer loop (`Timer::run`, spawned by the binary) that calls `Server::tick(now)` on a schedule while client traffic calls `Server::seen`; it is tested over a real socket in `apps/server/tests/ws.rs` (the basic paths), `wsflow.rs` (wake-up, replay and drain, slow reader, cut replay, several readers, a flooding client) and `wsrobust.rs` (a poll that times out, a stuck lock, `subscribe` rules, a stream dropped before its socket registered, a failing resubscribe). Left: the producers of ephemeral frames (capture requests in E1.7, touch hints), which today only a test publishes through `SharedServer::publish_ephemeral`.
- [x] Accepted ops reach every open client as durable frames with sequence numbers (proven with two clients of one file, a drain of 150 frames, and an op published during the replay); a client that reconnects with its last sequence number receives exactly the missed frames (also after a poll that timed out and closed the socket; within the retention: a gap longer than the replay limit of 1024 ends with a `resync` marker, and the client continues from it).
- [x] Ephemeral frames (capture requests, touch hints) carry no sequence number and are never replayed.
- [x] A slow client whose queue is full gets a resync marker and recovers; the room never waits for it (test with a stalled client, and with a replay cut at its limit). A client that stops reading is dropped by the send timeout and the writers go on (test); it reconnects with its last number.
- [x] Concurrent streams are capped; heartbeats are tested against a real clock.

### E1.5 MCP surface v1 (M)
- [x] Tools: read the file tree and nodes, apply commands (atomic by default for multi-command calls), report limits (`whoami`), batch status. Descriptions are English and name the batch limit. (`get_tree`, `get_nodes`, `apply_commands`, `whoami`, `batch_status`; `surface.rs` drives each with an rmcp client; atomic is a dry run under the server lock, see `docs/architecture.md`.)
- [x] Idempotency keys work in both spellings; `ifSeq` rejects a stale edit with `conflict` and says what changed. (`idempotencyKey` and `idempotency_key`, `ifSeq` and `if_seq`; the conflict lists the changes, the node's current data and the file's seq. Limits: an atomic call guards every node a command touches for the first time; `ifSeq` must be within 2,000 changes of the file; see `docs/architecture.md`.)
- [x] A real MCP client (the rmcp client in tests, and Claude Code) completes the M1 demonstration below. (Proven with the rmcp client in `demo.rs`: steps 1, 2 and 6 in part, with the person editing over REST. Steps 3, 4 and 5 are proven headless by `meldframe-capture-tests/tests/m1_headless.rs` against the composed server. In the real browser editor, `packages/web-e2e/scripts/m1-demo.mjs` runs steps 1 to 5 with an agent over MCP, including the dropped connection and the reconnect, and `packages/web-e2e/scripts/m1-claude-demo.mjs` runs steps 1, 2, 3 and 5 with Claude Code itself (the `claude` CLI, `-p`) as the MCP client: it builds the hero in one `apply_commands` call, its next read shows the heading the person moved, its edit with the old `ifSeq` is rejected with `conflict`, the person's undo takes back only the move, and its `capture` returns the PNG from the open editor. Step 6: the activity log holds the actor and the risk tier of every accepted write; the call log of E2.4 holds the decision and the outcome of every write call, refused ones included.)
- [x] Tool text and schemas are listed in a catalogue that a test compares with the server. (`docs/mcp-tools.json`; `catalogue.rs` compares it with the tools an rmcp client lists and with the registry; regenerate with the ignored `regenerate` test of `meldframe-review-tests`.)

### E1.6 App layer and basic web editor (L, split into slices)
ADR-0008. First vertical slice of the app layer: the editor shell.
- [x] `meldframe-app` holds selection, current tool, panel state, connection state and the history buttons as plain data with actions, effects and events; a test harness drives it without the web client. (Tests: `crates/core/meldframe-app-unit-tests/tests`, and `crates/core/meldframe-app-tests` against the real in-memory server: two editors and an agent, ops in flight at a drop and sent again, a real refusal, concurrent edits, a restart with a reused prefix, undo of a selected node, heartbeats past the silence limit. - [x] The web client (Svelte 5 + PixiJS) shows layers on the left, the canvas in the centre and properties on the right, and only renders app state and dispatches actions. - [x] Browser end-to-end tests cover create, edit, undo, a dropped connection and the reconnect. (`packages/web-e2e/scripts/editor-e2e.mjs`, 18 checks in a real browser against the development server, with a second token for the checks of another actor; run by hand before a pull request that changes the editor, not in CI because it needs a browser, a server and Postgres.)

### E1.7 Capture relay (S)
Carried from the spike (S13); headless capture waits for a real need (decision 18).
- [x] An agent can capture a node or a frame as PNG while an editor has the file open; without one it gets `no_capable_client`. (Proven end to end with a fake editor client on the real live WebSocket in `meldframe-capture-tests`; the web editor answers the same requests: it draws the node offscreen and uploads the PNG, proven with an agent over MCP in `packages/web-e2e/scripts/editor-e2e.mjs` and `m1-demo.mjs`.)
- [x] Capture uses the file bound to the session; a different file is refused with `room_mismatch`. (The session is the principal: the first call that names a file binds it; see `meldframe-http-capture`.)
- [x] Capture is a feature module that registers its tool with a Read risk tier.

**M1 exit criteria (demonstration, recorded in the pull request that closes the milestone):**
1. Claude Code, connected through MCP, builds a landing hero (a frame with heading, text and a button) in one atomic batch; the open editor shows it without reload.
2. The person moves the heading; the agent's next read shows the new position; the agent's stale edit of the heading is rejected with `conflict`.
3. The person presses undo: only their move is undone; the agent's work stays.
4. The browser drops its connection and reconnects: it receives exactly the missed changes.
5. The agent captures the frame and receives a PNG.
6. Every write in the run passed the one gate (log shows actor and decision for each).

## M2 Platform and agent identity

Goal: real users, tenants and agents (decisions 10 to 12; ADR-0006, ADR-0010).

### E2.1 Gatehouse login (M)
- [ ] People sign in with Gatehouse (OIDC); the principal carries user and workspace.
- [ ] Sessions are revocable; logout ends the WebSocket.
- [ ] Development tokens are disabled in release builds. (Partly: a release build refuses to start with dev tokens unless `MELDFRAME_ALLOW_DEV_TOKENS=1`, `check_dev_tokens_allowed`; open until Gatehouse replaces them and the override goes.)

### E2.2 MCP OAuth through Gatehouse (M)
First platform slice (risk R9).
Until it lands, `docs/quickstart-agent.md` connects an agent to a local server with a development token.
- [ ] Claude Code connects to the MCP endpoint through an OAuth flow with Gatehouse and acts as an authorised agent of the signed-in user.
- [ ] The client type and scopes chosen in the questionnaire are documented in an ADR.

### E2.3 Workspaces and quotas (M)
- [x] Every file, variable collection, asset and counter belongs to one workspace; a query without the workspace in the principal returns nothing (tests per table). (In: migration 0003 adds `workspace_id` and `name` to `files`, backfilled from the key, with a unique index; `ops` and `snapshots` follow their file, and `pg_workspace.rs` counts rows per workspace for each of the three tables, including a workspace name that is not ASCII, and checks the backfill of rows written before the migration. Since then: an asset follows its workspace (`DiskBlobs` per workspace; `another_workspace_does_not_see_an_asset_even_with_its_id`), the variables of a file are inside its snapshot and follow the file (`a_file_without_variables_and_another_workspace_read_as_empty`), and the quota counters are derived per workspace from rows (`pg_workspace.rs::the_storage_and_total_counters_survive_a_restart`), so each of them has its test; there is no stored counter table.)
- [x] Quotas per workspace (ops per minute, batch size, storage) with stable refusal codes; counters survive a restart. (In: the gate decides `quota_ops_per_minute` (fixed one-minute window, retryable, HTTP 429 with `Retry-After`), `batch_too_large` (HTTP 413; it was `invalid`) and `quota_storage` (bytes of ops, HTTP 413) per workspace, a refused batch charges nothing, and the server sets defaults (`Server::with_quotas`); ADR-0014. The total and storage counters are read from the workspace's own rows when the gate first sees it, so they survive a restart (`PgStore::workspace_usage`, test `the_storage_and_total_counters_survive_a_restart`); the minute window starts from the ops the workspace wrote in the current minute (`Gate::recent`, `PgStore::ops_since` on `ops.created_at`, test `the_ops_of_this_minute_survive_a_restart`), so no counters table is needed. The memory backing starts at zero, as it keeps no files across a restart either.)

### E2.4 Agent grants, risk tiers and activity log (M)
- [ ] An agent connects through an OAuth grant (decision 31): no API key or token is copied by hand, access tokens are short-lived, and revoking the grant ends the session at once so the next call is refused. The consent screen lists the risk tiers.
- [ ] The release build refuses development tokens (decision 25, ADR-0012).
- [ ] Calls carry risk tiers (Read, Change, Delete) with the default policy from the questionnaire; an agent deleting a whole frame or a large subtree is asked first. (In, not ticked: a delete sent alone through REST, WebSocket or MCP is answered `approval_required`; the typed approval state (`meldframe-approvals`: pending, approved, denied, expired, with an id and an expiry), the retry that is admitted once, the stable codes `approval_required`, `approval_denied` and `approval_expired`, and the call-log entries of the ask and of the owner's answer are proven at the gate seam and through the server. Open: no owner can answer yet (`Server::decide_approval` has no route, tool or screen, and needs sign-in to tell an owner from an agent), a delete inside a batch is still `forbidden`, an actor holds at most 20 open asks and a workspace 100 (`approval_limit`), and a tool whose own policy is Ask is still `forbidden`.)
- [ ] Every call is logged with actor, tool, risk, decision and outcome; logs carry no content. (In: the call log, `meldframe_calls::CallLog`, kept by the server: one entry for every write call, over REST, WebSocket and MCP, written or refused, and for the MCP reads `get_tree`, `get_nodes` and `batch_status`, `whoami` and `capture`; the entry holds the workspace, actor, tool, file, risk tier, the policy's decision (allow, ask or deny; none for a malformed call) and the outcome code, and tests show it holds no node names or text. The newest 10,000 entries are kept in memory, and on Postgres every entry is also a row of `calls` (migration 0005, `PgCallLog`, written off the server lock; `of_workspace` reads one workspace's), so the log survives a restart. `whoami` and `capture` and `upload_asset` are logged too, through `Reader::record`, with the stable code of a failed call; a capture or an upload is one entry. Open: the log is not readable by a person yet (the activity panel of E5.1 shows batches, not refused calls; ADR-0021 slice 17, optional, would add a read route over the log).)

### E2.5 Assets on local disk (S)
- [x] Upload png, jpeg, webp or gif (SVG refused); content-addressed; stored on local disk behind a blob interface. (`POST /v1/assets` takes the image as the raw body and `GET /v1/assets/{id}` gives it back with `nosniff` and a no-script CSP, both in the workspace of the token (`meldframe-http-assets`, tested with the real router); the store is `DiskBlobs` under `MELDFRAME_ASSETS_DIR` (required in a release build); `routes.rs` in `apps/server/tests` runs the disk store through the routes (and shows a changed file is `asset_corrupt`), an upload that never ends (`request_timeout`) and the full set of upload places, and the server was tried with a png, an SVG and no token. The assets count against the storage limit of the workspace with its ops: a new image that does not fit is `quota_storage`, and the gate counts the asset bytes when it admits an op. The MCP tool `upload_asset` takes the image as base64 (bounded by the MCP request size), stores it through the same checks and quota, and returns its id; the canvas that draws image fills is the last slice of E2.5.)
- [x] Image fills (cover, contain, fill) render on the canvas; a missing asset is reported as `asset_not_found`. (The canvas asks for each asset from `GET /v1/assets/{id}` through the dev proxy (once, and again every ten seconds or so while it has failed or is missing), decodes it and draws it over the fill and the gradient in the rounded box by `fitRect`; until it arrives, or when it is missing, the node shows its fill. A missing or unreadable asset is said once as a notice with its code, `asset_not_found` for an id the workspace does not hold; a capture and a PNG export wait for the pictures. `editor-e2e.mjs` uploads a three-stripe image and checks in a real browser where cover, contain and fill put it, and that a missing asset shows the fill and the notice `asset_not_found`. A person can pick the image of a fill in the Fill section: the Image type opens a picker of the workspace's images (`GET /v1/assets`, a page of 24 at a time, by id; no names yet, decision 36), a choice is one undo step, and `packages/web-panels/scripts/image-fill-e2e.mjs` checks it in a browser. There is no upload from the browser before sign-in (M2): agents upload through `upload_asset`.)

**M2 exit criteria:** a signed-in person and an authorised Claude Code session work in one workspace; another workspace cannot see that file; revoking the agent stops it on its next call.

## M3 Model round 2 and variables

Goal: the layout and paint model of W1 and the design system on the canvas (FR-4, FR-5, FR-9 to FR-11; ADR-0003, ADR-0004).

### E3.1 Render model (M)

### E5.2 Review and revert (M)
- [ ] Reverting a batch restores only the fields whose last writer is still that agent, as one atomic change authored by the person, which the person can undo.
- [ ] A test fails if the "still last writer" check is removed.

Status note (not ticked: the owner decides after a review and the real Claude Code run): `meldframe-revert` (`revert_batch`) works out the commands from a tree and the log after it: a field goes back only when the newest op that wrote it is an op of the batch (a later write by the person, another agent or a later batch of the same agent stays), the place of a node is one unit, a node the batch added goes only when nothing else touched its subtree, a node the batch removed comes back with its subtree, and the list applies whole. A batch is the ops of one actor whose keys are `{prefix}:{n}` (the keys of one `apply_commands` call). `Action::RevertBatch { actor, keyPrefix }` in the app layer applies the list as one history group of the person, so one undo takes it back; the app keeps the confirmed ops since it loaded the file (the newest 2,000 to 2,255). Tests: `meldframe-revert/tests/revert.rs`, `meldframe-app-review-tests/tests/review.rs`; removing the check makes `a_field_the_person_wrote_afterwards_stays` and `a_field_another_agent_wrote_afterwards_stays` fail. The Activity panel (E5.1) lists the batches and puts a Revert behind a confirmation on each row the app holds in full (`revertable`); for the selected row the app layer works out whether a revert would still change anything (`inEffect`), and the confirmation says when nothing is left; a batch that ran before the page loaded is listed with its note and review state and cannot be reverted from the page (live-only revert is the owner's MVP decision, ADR-0021). A revert changes neither the review state nor the count of batches to review. Open: a server query of changes for batches older than the session (reopen-and-revert, after the MVP), whether an undone revert should make its batch revertable again (by the last-writer rule the person's undo is itself a later write, so the batch has nothing to revert; the owner has not decided), and an atomic send: the ops of a revert go to the room one by one, so a refusal in the middle (a frame removal is Delete tier, ADR-0010) leaves the rest: it is refused and dropped, not held for approval, so a revert or restore across an added frame leaves the frame empty until an approval path exists (E2.4); `OpRejected` names the node.

### E5.3 Checkpoints (S)

## Rune front end (E8, owner decision 45 of 27 Nov 2026)

Ordered by the owner and recorded in ADR-0027 and decision 45. The desktop client is native Rune, which replaces the GPUIX + React plan of decision 42 and E7.4. The web client moves to Rune from the same view crates, with mobile off for now. The React web client is frozen: slices S1 to S11 of E7.3 stay merged, S12 and S13 are on hold, and Svelte and React stay in the repository until the owner retires them. The server stays central and the protocol is the only contract between a client and the product. E7.1 and E7.2 stand, and so do the moves of decision 43 that are done (T9, T11, T12, T14, T16, T17): the thin UI is why this work can start before any Rune code. The boxes below are copied from the issues and none is ticked: a box is ticked only when its whole text is proven. A size is S (a few days, one or two pull requests), M (about a week) or L (split before starting).

**Exit criteria of E8:** the direction is on record and the old front ends cannot grow; every rule a second front end would copy lives in the app layer; a written desktop spike result says go, go with conditions or stop against written criteria; the native desktop alpha and the Rune web build pass their parity gates; and, only after both gates and the owner's OK, one front end codebase is left.

**Principles.** (1) The brain is portable Rust: `meldframe-app` and the core hold every rule, and a Rune front end links them as libraries (the wasm bridge stays for the legacy web client). (2) One view codebase for Rune: desktop and web sit on the same `ui` and `feature-ui` crates, and only what a platform forces lives in a front end of its own. (3) Swapping the toolkit stays cheap: the diff that replaces the Rune views touches no core, engine, integration, os, feature, app or ffi crate and no protocol type (E8.1.9 proves it). (4) No rule is written twice: a new rule goes to the app layer with a test at the app seam first, and the frozen web clients are not rewired for it; each TypeScript copy it leaves is listed for retirement in E8.6.1. (5) Each milestone names its fallback: the frozen React client and the Svelte page for the web, and any other desktop front end on the same protocol. The proposed U10 to U12 of standard v1.4 (toolkit swap, one view codebase, client kind from the credential) are mirrored by E8.0.2.

**Layout.** A second Cargo workspace, `frontends/rune/`, with its own `rust-toolchain.toml`, `Cargo.lock` and `deny.toml`: `crates/ui/meldframe-ui-rune` (kind `ui`: the tokens bound to Rune styles, primitives on `rune-kit`, focus rules), `crates/features/<group>-ui-rune` (kind `feature-ui`: canvas, layers, properties, variables, activity, export, shell parts), `apps/desktop` (kind `bin`: window, socket, keychain, file dialogs, clipboard) and `apps/web-rune` (kind `bin`: the wasm entry with the browser socket, download, paste and fonts). It takes path dependencies into the main workspace for the core, app, protocol and render crates only, and no main workspace crate depends on it. Toolkit imports live only in `ui`, `feature-ui` and `bin` crates (L3). The alternative, raising the toolchain of the main workspace and taking the 8 git pins into its lock, touches every crate and every CI job and is not recommended.

**Tripwires.** These stop the Rune track at the spike or the alpha, with the fallback named and not a silent slip: input method composition fails on macOS with real input methods (C7 of E8.2.1); the frame cost of the reference scenes is not met on a real GPU (C4); the fidelity contract (`docs/fidelity-contract.md`: 0.05 px boxes, 1 px text ink) cannot be met by painting from the core's own measure (C1 to C3); a fork of Rune is needed beyond the 8 pins (C10); Rune API churn costs more than one working day a bump over three bumps in a row (E8.0.4 records each bump).

**Open for the owner, with the proposed default.** Desktop sign-in: an authorisation code flow with PKCE and a loopback redirect through Gatehouse, the token in the system keychain, in a server ADR that extends ADR-0022 and needs Gatehouse support (E8.1.8, E8.3.9). Distribution identities (signing, update host, accounts): the owner creates them and E8.5.3 lists them. The time to interactive bar of the web build: no worse than 1.5 times that of the React client (E8.4.4). Whether the frozen web clients are rewired for new Rust rules: no (E8.6.1).

**Risks.** Rune is pre-1.0 with one dominant maintainer, used by git revision with 8 patches: bounded by the pin, the scoped exception, the tripwires and the fallback front end. The fidelity contract may not hold on Rune's raster if it rounds text to whole pixels: C2 decides, and painting from the core's own measure is the fallback. Two workspaces double part of the CI cost: caches, and the Rune job stays not required until E8.2 passes. The legacy clients drift from the Rust rules: accepted, bounded by E8.0.3 and E8.6. Distributed clients bring abuse and support work: E8.1.8 and E8.5.5 come before any public build. Mobile cannot be blocked by credential, and this is stated and not hidden (E8.1.8).
