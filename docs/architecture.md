# Architecture: Meldframe

This document says how the system is shaped and why. Requirements are in `docs/prd.md`; each hard-to-reverse decision has an ADR in `docs/adr/`. Nothing here is product code. Facts about the spikes come from the survey in `docs/architecture/spike-survey.md` and were not re-measured.

## 1. Context and drivers

Meldframe lets a human and an AI agent edit the same design file, and exports it as HTML/Tailwind. The forces that shape the design:

1. **Agents are first-class clients.** They retry, run in parallel and read tool text as instructions. Every write must be idempotent and attributable.
2. **One truth for geometry.** The canvas, the export and the agent's capture must agree.
3. **Variables must reach code.** They are rendered on the canvas and exported, not flattened to literals.
4. **Human control.** A person can take over at any time and can undo agent work without rewriting history.
5. **A solo owner builds and runs it.** Few moving parts; Postgres, one server binary, one web client.
6. **Open source until the MVP, closed source afterwards; personal use first.** The repository is public until the MVP, then closes because CI needs infrastructure of its own. It has no licence yet (`NOTICE`: all rights reserved). Hosting, pricing and scale are not drivers yet.

## 2. Decision summary

| # | Decision | Status |
|---|---|---|
| ADR-0001 | One `Command` interface for every change (UI, WebSocket, MCP, undo) | accepted |
| ADR-0002 | Rust core shared by native server and WASM client; thin server | accepted |
| ADR-0003 | Core geometry is the source of truth; export is a translation; a browser oracle gates CI | proposed |
| ADR-0004 | Flat variable model (collections, modes, aliases), resolved in the core | proposed |
| ADR-0005 | Agent changes apply live and are reviewed afterwards; the batch is the unit; revert is a new change | proposed |
| ADR-0006 | Workspace is the tenant; authentication through Gatehouse | accepted |
| ADR-0007 | Layered crates with enforced dependency rules; detachable feature modules | accepted |
| ADR-0008 | UI-neutral app layer in Rust (WASM); front ends only render | accepted |
| ADR-0009 | Live events are durable (replayable) or ephemeral (best-effort) | accepted |
| ADR-0010 | One admission gate in front of every change | accepted |
| ADR-0016 | Revert and restore are worked out from the log in the app layer; a field reverts only while the batch wrote it last | proposed |
| ADR-0017 | Variables are a second table of the file; bindings are `{var:..}` objects; resolution happens in the core | proposed |
| ADR-0019 | Export is a pure function of the render model; variables become CSS custom properties named by collection and name | proposed |
| ADR-0023 | Checkpoints are rows kept by the server beside a file's log, taken at an agent's run start by the server, and restored by the person's app from the file at the checkpoint | accepted |

## 3. System shape

```mermaid
flowchart LR
  subgraph Clients
    W[Web editor\nSvelte 5 + PixiJS + WASM core]
    A[Agent\nClaude Code / Cursor / Codex]
  end
  W -- WebSocket ops/events --> S
  A -- MCP tools --> S
  W -- REST snapshot, export --> S
  subgraph S[Server (axum)]
    ADM[Admission\nauth, mode, quota, timeout]
    ROOM[Room actor\none total order per file]
    CAP[Capture hub]
    EXP[Export]
  end
  ADM --> ROOM
  ROOM --> PG[(Postgres\nops, snapshots, assets index)]
  CAP -. request/response .-> W
  G[Gatehouse\nOIDC/OAuth] --> ADM
```

Each file has one room. Every client and every agent talks to that room through the same admission step, so a change made by a person and a change made by an agent take the same path and appear on every open client in the same order.

## 3b. Layers and dependency rules

The structure follows the CodeCora standard `modular-thin-ui` (`docs/standards/modular-thin-ui.md`; ADR-0007 to ADR-0010). Every crate declares a kind and CI enforces the matrix.

One recorded carve-out from L5 (E8.2.2): `meldframe-net` (kind `os`, in the Rune workspace under `frontends/rune/crates/os/`) is the socket of the native desktop shell. It uses threads, `TcpStream`, `tungstenite` and `ureq`, none of which exist on `wasm32-unknown-unknown` (`cargo check --target wasm32-unknown-unknown -p meldframe-net` fails in `getrandom`), so it is native only; the web build of the Rune front end (E8.4) gets its own `os` crate over the browser's `fetch` and `WebSocket`. `cargo xtask portable-check` reads the main workspace only (`xtask/src/packages.rs`, `scope`), so it does not build this crate and needs no exclusion today; if it ever reads the Rune workspace it needs one for this crate. No new kind is made: `deps-check` still holds the crate to the `os` matrix (it depends on core crates only, and no toolkit), which is the part of L5 that protects the layering.

UI toolkits are allowed only in ui, feature-ui and bin crates. Core, engine, integration, feature and app crates must compile for `wasm32`. A product build with each feature alone, and with none, must pass its tests.

**The adapters are `bin` (decision 47, issue 317).** The 7 crates under `crates/integrations/` (the HTTP transport `meldframe-http` and its tool crates, and `meldframe-store-pg`) link axum, rmcp or sqlx, which do not build for `wasm32`, and most of them depend on feature crates, which the `integration` kind may not. The `integration` kind stays what the standard says it is, a portable adapter (L5: `portable-check` builds it for `wasm32`), and no crate has it today. An adapter is declared `bin`: outside the matrix (a `bin` may depend on every kind) and outside `portable-check`. Only another `bin` (the server, the other adapters) and a `tool` crate (its tests, mostly as a dev-dependency) depend on an adapter, and the matrix already forbids every other kind from doing so. So that the label cannot become a way out of the matrix, `deps-check` fails a `bin` crate outside `apps/`, `crates/integrations/`, `frontends/rune/apps/` and `frontends/rune/tools/` (`xtask/src/bin_homes.rs`). Not decided here, and left to the monolith merge (issue 315): the three app-layer crates declared `core` (`meldframe-app-model`, `-parts`, `-rules`) go away when they merge into `meldframe-app` (kind `app`).

**M3 and the app layer.** A cargo feature detaches what a feature adds to a build: its tools, its routes and its registry entries, on the server (`cargo xtask build-matrix` shows it). The state a feature keeps in the app layer is not detachable at build time: `meldframe-app` and `meldframe-app-model` depend on `meldframe-activity` (kind `core`) unconditionally, so a build with the `activity` feature of the server left out still carries the Activity panel's state and its code in the web build (the panel shows nothing without a server that sends batches). There is no cargo feature of `meldframe-app` for it; if a build without the Activity panel is ever wanted, it is its own issue.

`PgStore` is the crate `meldframe-store-pg` (kind `bin`, like the other adapters: sqlx is not portable, L5). Its methods block on a private runtime, so a transport calls it from a plain thread or `spawn_blocking` (dropping the last clone from an async task panics); each `connect` costs one runtime and one pool, so connect once and clone. The sqlx migrator owns the database: `connect` applies `migrations/` and refuses, with a clear error, a database or schema that holds the tables but no `_sqlx_migrations` (what `psql -f migrations/*.sql` and the dev seed leave behind), rather than failing half way. We chose the refusal over a baseline of such a database: which migrations psql applied is not recorded. So until `just dev-db` loads migrations through the same migrator, point `PgStore` at an empty database or schema (`connect_in_schema`), not at the psql-loaded `meldframe_dev`; `tools/check-migrations.sh` is unaffected. A data error that can never succeed (a NUL character that `jsonb` cannot hold) is reported as `StoreError::Unavailable` with the text "retrying cannot succeed", because the seam has no permanent-failure variant. One `files` row per room carries the counter that an append locks, which makes sequence numbers gap-free per file across connections; the op key is unique per `(file, actor, key)` (migration 0002). `meldframe-store-contract` is a `tool` crate for the same reason as the next one: the cases would not fit `meldframe-host` under its 2,000-line ceiling.

The server serves one room per file. `Server` owns a `meldframe-rooms::Rooms` registry (at most `MAX_OPEN_ROOMS`, 256) and opens a file on its first write or `open`, restoring it from its latest snapshot plus the log. A `Backing` picks the store: `Backing::Memory` (one shared `MemoryStore`, so a closed file comes back, a restart loses it) or `Backing::Postgres(PgStore)` (each room gets a clone of the one connected store); `Backing::from_env` chooses Postgres when `DATABASE_URL` is set. `AnyStore` is the `Store` that dispatches to either. A write is `Server::submit_tool(tool, file, principal, ops)`: tool tier and policy, then the one `Gate` (tiers read from the file's own tree), then `Rooms::accept` of that file; the server exposes read access to a room (`with_room`) and never `&mut Room`, and an `Admission` cannot be built by hand, so a path that skips the gate does not compile. A batch whose later op fails after earlier ops were written keeps the earlier ones (each is its own durable write); retrying with the same keys is safe. Files are namespaced by workspace inside the server: the registry and the store key is the workspace's length, the workspace and the file name (injective, so workspace `a/b` with file `c` is not workspace `a` with file `b/c`). Another workspace that opens the same file name gets a different, empty file, whether the first is open, closed or restored after a restart, and a probe cannot tell whether the name exists elsewhere. Honest caveat: this is namespacing by key only. The Postgres schema has no workspace column (`files.id` is the encoded key), so nothing in the database enforces tenancy; a real tenancy column comes with E2.3. A refused call keeps no room open: a refusal after the tool check may open the room for the check and closes it again (with the replay cost); a room that was already open stays open. Rooms idle for five minutes (`IDLE_AFTER_MS`) are closed by the next write. Each workspace may hold at most `MAX_ROOMS_PER_WORKSPACE` (32, `Server::with_workspace_rooms`) open rooms, so one workspace cannot fill the 256-room cap for the others; both caps are `RegistryError`s (`WorkspaceFull`, `Full`), not refusals, and a transport answers them as `unavailable` (see `docs/error-codes.md`, Server limits). The server is the one place that validates names (workspace and file: not empty, at most 128 bytes, no control or hidden character; `RegistryError::InvalidName`, `invalid`), so Postgres never sees a bad one, and it refuses before opening a room (`Server::precheck`, run by `submit_tool` and by `submit_atomic`) a batch over `MAX_BATCH_OPS` (100) ops and a Read-tier tool submitting any op but a delete (so a Read tool re-sending already-applied non-delete ops is `forbidden`, not `written: false`). A bad name is `invalid` 400 on every transport (`failure_of`); a room cap is `unavailable` 503 without `Retry-After`. When an open hits a cap, idle rooms are closed and the open retried, and `Server::tick` closes idle rooms too, so reads and live streams alone do not lock a workspace out. The encoded key can show in the activity log and in `RegistryError` messages. An op whose key was already applied with the same command is answered as a duplicate (`written: false`) before the tier decision, so retrying a small delete after it succeeded works (duplicates skip the tool and gate checks and cost two store reads each, which is why the batch cap comes first); a batch that failed part way keeps the earlier ops written, and sending it again is safe. `SubmitError::refusal()` gives one shape for tool, gate and room refusals (one stable `Refusal::code`); a failure that is not a refusal (store down, registry full) gives `None`. Known limit: the gate counts quota when it admits a batch, before the room accepts, so ops after a failing op are charged and not written, and a retry is charged again; the server sets no quota today and fixing it needs a host change (`meldframe-host` is at its ceiling). The binary does not read `DATABASE_URL` yet (the dev seed makes `meldframe_dev` unusable for `PgStore`), and the only callers of `submit_tool` are the REST, WebSocket and MCP transports of `meldframe-http` (below).

`meldframe-http` (kind `bin`, because axum is not portable) is the thin transport adapter. `POST /v1/files/{file}/tools/{tool}` takes `{"ops": [{"key", "command", "ifSeq"?, "deps"?}]}`; `GET /v1/ws` upgrades (token checked at the handshake) and takes text frames `{"id", "tool", "file", "ops"}`, one reply frame each. Both end in one handler, `Shared::submit`, which calls only `Submitter::submit`; `SharedServer` (in the server crate) implements it over `Server::submit_tool`, so there is no other write route (a test sends to other paths and methods and nothing reaches the submitter). Order of work per call: per-address bucket, token (`Authenticator`), per-principal bucket, and only then the body is read (size limit), parsed (unknown fields refused) and submitted on `spawn_blocking` under a timeout. Buckets take a caller-supplied clock. A refusal keeps its stable code and gets a status; transport codes (`unauthenticated`, `rate_limited`, `too_large`, `bad_request`, `timeout`, `unavailable`, `internal`) are in `docs/error-codes.md`. In-flight blocking calls are bounded (global and per principal, `try_acquire` before `spawn_blocking`): over the cap is `unavailable` 503 at once, and a timed-out call keeps its slot until its job ends, so abandoned jobs cannot pile up behind the server lock. Per-address keys are the IPv4 address or the IPv6 /64; a full bucket table forgets the least recently used key. Dev tokens must have 16 characters or more; a file name is 1 to 128 bytes without slash, control or invisible formatting characters. `CappedListener` caps open connections, in all and per client key (the same IPv4 / IPv6 /64 key as the rate limiter), closing one over its share at once; a WebSocket reply or close that cannot be sent within `ws_send_timeout` drops the connection; pings spend the principal budget, never move the idle deadline, and the limited-frame count is leaky (up per limited frame or ping, down per allowed frame); file and tool names are validated (no `.`, `..`, backslash, bidi or zero-width characters; tools are 1 to 64 of letters, digits, `_`, `-`, `.`); a store error that can never succeed is the typed `Failure::Permanent`, decided by `failure_of` from the fixed prefix `PERMANENT_STORE_ERROR` that `PgStore` writes (it is checked at the start of the message only, so text from a caller inside a message cannot set it); the body read has a timeout; a WebSocket is closed when idle or after repeated limited frames. When a lock is recovered after a panic, `Server::close_all` closes every room so each restores from the store. Honest limits: a timeout stops the wait, not the write (the blocking call finishes; retry with the same keys); the binary serves through `meldframe_http::serve`, a hyper accept loop over `CappedListener` that closes a connection whose request headers are not complete within 10 s, also one that sends nothing or idles between requests (issue 170; an upgraded WebSocket is past it); there is no TLS; the in-memory table and in-flight counters are per process; eviction by 10,000 distinct client keys can reset an idle exhausted client's bucket; a WebSocket is authenticated once, at the handshake, so revocation mid-connection waits for E2.1; buckets live in one process and, past 10,000 keys, the least recently used key is forgotten; a panic in a call is a 500 and the server mutex is recovered, not poisoned; the binary serves only when `MELDFRAME_LISTEN` is set (dev tokens listen on loopback only unless `MELDFRAME_ALLOW_DEV_PUBLIC=1`; a release build needs `MELDFRAME_ALLOW_DEV_TOKENS=1` and prints a warning; the two overrides are separate), with in-memory files, because it does not read `DATABASE_URL` yet; the client address is the TCP peer, except behind a reverse proxy listed in `MELDFRAME_TRUSTED_PROXIES` (comma-separated addresses), where it is the rightmost `X-Forwarded-For` entry the trusted proxies did not add (`meldframe_http::real_client`; IPv4-mapped addresses compare as IPv4, ports are allowed, `Forwarded` is not read, and each trusted proxy must append the address it saw rather than pass the client's header on); the connection caps still count the proxy's connections, and there is no TLS of its own: terminate TLS at that proxy.
The MCP surface is a module of `meldframe-http` behind its `mcp` cargo feature (the server turns it on by default; `rmcp` 3.10, Apache-2.0, stateless streamable HTTP on `/mcp`). `router_with_mcp_config` builds one `Shared` (authenticator, buckets, in-flight slots, submitter) and mounts REST, WebSocket and MCP on it: a middleware spends the per-address and per-principal budgets and checks the same Bearer token before MCP reads the body, and a tool call takes its principal from that request, never from its arguments. `apply_commands` ends in `Shared::submit_ops`, the handler REST and WebSocket end in (they pass `atomic: false`); reads go through the `Reader` seam (`view`, `variables`, `tree`, `conflict`, `applied`: each is one call under one lock on one opening of the file, implemented by `SharedServer` and allowed only when the registry holds the read tool with an Auto policy) on `Shared::blocking`, the same slot and time limit as a write. Six tools of its own, listed with their text, tier and schema in `crates/core/meldframe-mcp-defs/src/lib.rs` and in `docs/mcp-tools.json` (a test compares the file with what an rmcp client lists and with the registry): `whoami` (workspace, actor, batch limit of 100 commands, file limits, call rate), `get_tree` (nested nodes with id, name, kind, geometry, `lastActor` and `lastSeq` from the last 2,000 log entries, and the file's `seq`), `get_nodes` (full data of up to 100 ids, `missing` ids), `get_variables` (the collections with their modes and a page of the variables with their value in every mode: at most 200 a call, `collection` and `prefix` filters, `total` and `next` to page; E3.4), `apply_commands` (1 to 100 commands, the node commands and the ten variable commands (the seven of ADR-0017 and the three renames), a binding as `{var: id}`; command `i` has the op key `{idempotencyKey}:{i}`; `idempotencyKey` or `idempotency_key`, `ifSeq` or `if_seq`, naming both is `invalid`; atomic by default) `batch_status` (how many commands of a key were written, with their sequence numbers); `make_variant` is served beside them by the module `variant` of `meldframe-http` as an `Extra` tool of the `variant` cargo feature (a copy of a frame and its subtree beside it: `meldframe-variant` builds the `addNode`s from the file as read, ids derived from the `idempotencyKey` so a retry finds what it wrote (`replayed`), one atomic `submit_ops` as the tool `make_variant`; a copy of over 100 commands is `invalid`, `E_NOT_A_FRAME` and `E_NODE_NOT_FOUND` are the errors of the frame; there is no `ifSeq`, the copy is of the file as the call reads it). Atomic means: `SharedServer::submit_atomic` holds the server lock, runs `meldframe-batch::check` (a dry run of the batch on a copy of the room's tree and against the room's log, in the order `Room::accept` checks: duplicate key, dependencies, `ifSeq`, the command) and only then submits, so a batch that would fail writes nothing and the error carries the `index` of the failing command. `atomic: false` and REST/WebSocket keep one durable write per op. A conflict names the `nodeId` and, from MCP, the `changes` (seq, actor, command type) since `ifSeq` that touched that node (filtered before the limit of 100, out of the last 2,000 log entries), the node's `current` data and `currentSeq`, read in one `Reader::conflict` call. `ifSeq`: a command whose nodes no earlier command of the call touched carries it as the op's own `ifSeq` (the room checks it on every path); a command that touches a node an earlier command touched and also a new one cannot (the room would count the earlier command as a change after `ifSeq`), so each new node gets a `Guard` that the dry run checks under the server lock; a command that touches only nodes an earlier command touched carries no check; with `atomic: false` a guard cannot be enforced, so the call is refused as `invalid` (with the command's `index`). The dry run reads the log only when an `ifSeq` is within `MAX_SCAN` (2,000) entries of the file's head; further behind is `invalid` (read the file again), so a stale `ifSeq` of 0 cannot make the server read a long log while it holds the lock; the dry run still copies the file's nodes (at most 20,000) once per call. A remove cannot write half of an atomic batch: only a frame can have children, a frame delete is never small, and a batch that adds or reparents gets no small-delete relief from the gate (`Op::batch_tiers`), so `[addNode C under L, removeNode L]`, `[addNode frame F, removeNode F]` and `[reparent X under L, removeNode L]` are refused whole by the gate as `forbidden` before command 0 (`hardening.rs` drives all three), and the room's own remove check cannot fail after the gate relaxed a delete; the dry run therefore does not repeat it. Honest limits: the dry run cannot see the room's snapshot floor (an `ifSeq` below the snapshot the room opened from can still fail mid-batch) or a store that fails part way; `lastActor` is blank for nodes untouched in the last 2,000 entries; the MCP route has no body-read timeout of its own beyond rmcp's; a read tool opens the file for the call and closes it again, and reading a file that does not exist writes nothing (`PgStore` inserts a `files` row only in `append` and a snapshot save, both after an accepted op; a read is `select` only); removing a frame as the only command of a call is `approval_required` (the approval seam is wired into the server, see the approval paragraph of section 7), and inside a larger batch it is `forbidden`; MCP always answers the loopback `Host` names (`localhost`, `127.0.0.1`, `::1`) and also those `MELDFRAME_MCP_HOSTS` lists (comma separated); `Origin` is not validated, because the route has no cookies and no CORS and every call needs the Bearer token; the capture tool is the next paragraph; no push of live events over MCP.

The capture relay (E1.7) is the feature module `crates/features/capture/capture` (a pure relay with an injected clock, the `Binding` of a session to one file, the error codes and the tool text; it registers `capture` with a Read tier) and the integration crate `crates/integrations/meldframe-http-capture`, which holds the relay behind a mutex and offers three parts over one `Capture`: the MCP tool (a seam in `meldframe-http`, `mcp::Extra`, so the tool lives in its own crate), a `ClientHook` on the live sockets of `meldframe_http::live` and the upload route. The flow is documented at the top of `meldframe-http-capture/src/lib.rs`: an editor announces `capabilities: ["capture"]` for its file on its live socket; the agent's `capture {file?, nodeId?, scale?}` binds (first call) or checks (later calls: `room_mismatch`) the file of its principal, fails at once with `no_capable_client` when no editor of the workspace has the file open, otherwise sends that one socket the ephemeral `captureRequest` (random upload token of 16 bytes, `minSeq` = the file's sequence number at the call) through `LiveSource::publish_ephemeral` and waits; the editor `POST /captures/{requestId}` with its Bearer token, `X-Capture-Token` and `X-Capture-Seq`, or answers `captureFailed` on the socket; the body is read as a stream and never beyond `Relay::max_bytes` (the `Content-Length` is checked first, an overflow fails the request with `too_large` and the answer is 413); the PNG header is parsed against `max_pixels`; the agent gets MCP image content or a tool error with one of the codes in `docs/error-codes.md`. An answer with no matching request (unknown id, wrong token, another workspace or client) is ignored (404 on the upload). The live timer expires requests (`timeout`) and a closed or dropped stream fails its requests (`client_disconnected`). The server turns it on with the cargo feature `capture` (default, needs `mcp`). The file is bound only once an editor was found for it, so a typo binds nothing. The upload route checks the request id and token against the pending request before it reads any body (404 otherwise), takes an upload place (per principal and in all, 503 when none), reserves memory from the `Content-Length` (bounded) and reads under the adapter's body timeout (408; a body error is 400); a call that is dropped aborts its own request, and a request that cannot be sent fails only itself, never the editor's capability. Limits: pending requests in all, per workspace, per principal and per editor, capable editors in all and per workspace (an editor refused as one too many gets an `error` frame with code `busy`, and an agent whose file has no editor only because of that cap gets `busy`); images are at most 4 MiB (about 5.5 MiB as base64). Trust: any principal of a workspace may announce `capture` for any file of its workspace; it then receives the upload token of requests for that file and returns the image, so capture trusts every principal of the workspace equally, as the other tools do; the PNG is checked only to its header (signature, IHDR, dimensions against the pixel limit), not decoded. Honest limits: the binding is per principal (workspace and actor) and lives until the server restarts, because MCP here is stateless and has no session; a bound principal cannot rebind to another file; cancelling an MCP call on the client does not stop the server's call (rmcp keeps running it), so a cancelled capture holds its editor's place until its timeout; the file's sequence number is read with a whole-file `Reader::view` because the Reader has no cheaper call; the web editor does not announce `capture` or answer yet (E1.6), so the tests use a fake editor over the real live socket; the relay is in memory, so a restart loses pending captures (the agent gets its transport error); capture does not wait for `minSeq` on the server side: the editor must be at or beyond it, else `stale_client`.


Live events (ADR-0009, E1.4) are a fourth route of the same adapter, in a module of `meldframe-http`, `live` (always on, no cargo feature; it builds on the same `Shared`, so it passes the same checks and a write over REST, `/v1/ws` or MCP wakes its sockets through `Shared::on_write`). `meldframe_http::live::routes` adds `GET /v1/live/{file}?after={seq}` to the router of a `Shared` and returns the `Timer`; `live_router` builds REST, `/v1/ws` and the live route in one call, and the server's `main` merges it with the MCP routes over one `Shared`. The route is `GET /v1/live/{file}?after={seq}` upgrades to a WebSocket that is one stream of one file of the caller's workspace. It is its own socket, not a message on `/v1/ws`, so a refusal is a handshake status (401, 429, `unavailable` 503 at the stream cap), one connection has one stream and one lifetime, and the submit socket stays request and reply. The handshake is an ordinary call: the same `Authenticator`, the per-address and per-principal buckets, the size limit and the REST in-flight slots (`max_in_flight`, `max_per_principal`). After it, the connection's calls on the server (poll, resubscribe, unsubscribe) use their own slots (`LiveConfig::max_live_in_flight`, `max_live_per_principal`), so sockets cannot take REST's places and a stuck server lock cannot grow the blocked jobs beyond them; the `seen` call of each client frame has slots of its own (`max_seen_in_flight`, `max_seen_per_principal`), so a client that pings stays alive while the live slots are taken. A poll with no free slot is skipped and tried again at the next look; a poll that times out or fails may have taken frames and thrown them away, so the socket closes and the client reconnects with its last number; a `seen` with none is owed and done at the next look (with the time the client was heard). `live_poll` is at least 10 ms and at most the server's heartbeat interval (`heartbeat_ms`; a longer value is cut to it), so a heartbeat is sent at most one look after it is due. Each client frame is charged to the principal's budget (a `subscribe` as 4 frames, charged only once it has a live slot, so a busy server costs the client one frame), and `Server::seen` is called before the charge, so a frame the budget refuses still shows the client is alive. The count of refused frames is leaky: up one per refused frame, down one per allowed frame, and the socket closes when it reaches `ws_max_limited`, so a client that keeps asking inside its budget is not closed. A `rate_limited` or busy `unavailable` error frame carries `retryAfterMs`. `ws_idle` does not apply to this socket. The server sends `subscribed`, then the ops after `after` as `event` frames (`room`, `seq`, `actor`, `command`; the store range first, then the hub's window), then whatever the stream queues: further events, ephemeral frames (no `seq`, never replayed: `captureRequest`, `touch` and `batch`, below), `heartbeat`, and `resync {afterSeq, latestSeq}` when the queue overflowed or a replay was cut. After a `resync` the stream sends nothing until the client sends `{"type":"subscribe","id","room","sinceSeq": afterSeq}` on the same socket (answered with `subscribed` and the replay). `subscribe` is accepted only after a marker: otherwise it is `bad_request`, and it never starts before the marker (a missing or smaller `sinceSeq` is the marker's `afterSeq`). A client must send a JSON `{"type":"ping"}` (answered with `pong`) at least once within the server's `dead_after_ms`, or the timer drops it and the socket closes; a browser cannot send a WebSocket-level ping, so it sends this one. `SharedServer` implements `LiveSource`, so every live call runs under the shared mutex on `spawn_blocking`; a connection drains its stream when an accepted op of its file wakes it, and at least every `live_poll`. The tick wakes only the sockets of the streams it dropped; heartbeats and ephemeral frames reach a socket at its next look, within `live_poll`. If a poll times out or fails it may have taken frames and thrown them away, so the socket closes and the client reconnects with its last number (within the retention, the store and the hub's window give exactly the missed frames; a gap longer than the replay limit of 1024 comes with a `resync` marker for the rest); a connection releases its place and its stream when it ends for any reason, the unsubscribe on drop is best-effort (it needs a live slot, and with none free, or the server too stuck to take it, the timer drops the silent stream after `dead_after_ms`). The `Timer` (`Timer::run`, spawned by the binary every `live_tick`) calls `Server::tick(now)` with the adapter's clock: it queues heartbeats and drops silent or stalled streams, and the adapter closes the sockets of the dropped ids. Stream ids never leave the adapter (they are sequential), so a connection owns its stream; the server also checks it: `poll`, `seen`, `resubscribe` and `unsubscribe` do nothing for another actor of the workspace than the one that subscribed (`publish_ephemeral` is the server's own push, scoped by workspace); the `(file key, id)` pairs of `tick` are never forwarded. Every principal of a workspace can still read every file's op log of that workspace through this route (per-file read rights are not built). Honest limits: a stream subscribed at the handshake whose upgrade then fails stays until `dead_after_ms`; a stream the timer dropped before its socket registered is remembered (the last 256) so the socket closes with an error; a room opened for a stream is closed only by idle eviction; the socket is authenticated once, at the handshake (revocation waits for E2.1); a stalled stream gets its marker only after its queue drains, so a very slow client can be reaped by `stall_ms` first.

The snapshot route, `GET /v1/files/{file}`, is the read path an editor starts from; it lives in the module `snapshot` of `meldframe-http` (always on, on `Shared` like the live route), and the server mounts it beside REST and the live route. It answers `{"seq", "nodes": [...]}` (`FileSnapshot` in `meldframe-protocol`, TypeScript generated) and then the client follows `GET /v1/live/{file}?after={seq}`. It takes the same path as the other routes: per-address bucket, token, per-principal bucket, the in-flight slot and time limit of `Shared::blocking`, a file name checked with `valid_file` (`invalid` 400), and the workspace from the principal, so another workspace's file is never read. A file with no ops is `not_found` 404 (`docs/error-codes.md`), also when the name exists in another workspace; the read writes nothing. The batch list is a sibling route on the same path of checks, `GET /v1/files/{file}/batches?before&after&limit` in `meldframe-http-activity` (an empty list, not `not_found`, for a file with no batches or in another workspace; a malformed query is the JSON `invalid`). Each node carries `lastActor` and `lastSeq`: the actor and sequence number of the last op that touched it, with the same notion of "touched" as `get_tree` and `ifSeq` (`meldframe_batch::touches`: an add, update, remove, reorder or reparent names the node, a reparent also its new parent). An undo or a rebalance is an ordinary op of the actor who sent it, so an undo by A makes A the last actor. The answer is worked out from the log, not from a map kept beside the room: it reads the newest `SCAN_WINDOW` (5,000) ops from the store in pages of `REPLAY_PAGE`, so a live room, a room restored from the store across its periodic snapshot and a Postgres replay give the same answer (the first two are tested; the Postgres tests were not run for this change). The cost is one paged read of up to 5,000 ops (pages of `REPLAY_PAGE`, 256, so about 20 `ops_after` calls) while the server lock is held; a node not touched in that window has neither field. To keep one rate-limit token from buying that read again and again, the route keeps a small cache (`AttributionCache`, at most 64 files, the oldest forgotten first) keyed by workspace, file and head sequence number: the log is append-only, so a read at the same head pages nothing, and a write makes the entry stale. A call that had to scan is charged `SCAN_COST` (8) calls of the principal's budget (`Shared::principal_wait`; the charge comes after the scan, so it limits the next call, not the one that scanned). Reading a file that is not open opens its room for the call (snapshot load and up to 500 replayed ops), then closes it; while it is open it counts against the per-workspace room cap, so at the cap a read can get `unavailable` 503 until idle eviction frees a place. A store error goes through `failure_of` like the other routes (a permanent one is `invalid` 400) and an unavailable one is logged; that mapping was tested only with a fake source, since no failing store exists outside Postgres. The log keeps no time, so there is no `lastAt`: adding one needs a time column in the store seam and a migration. Per-field last writer is not built.

Four small tools are modules of `meldframe-http` too (merge C2 of `docs/crate-merge-plan.md`, #315), each behind a cargo feature of its own that lists `mcp` and the feature crate it serves, and the server's feature of the matching name forwards to it (`meldframe-http/export`, `/review`, `/variables-import` and `/variant`), so a build without the feature has neither the module nor the tool: `export` is the MCP tool `export_frame` over the export feature (a seam, `FrameSource`, to read the nodes and the variables of a file, the arguments, and the answer: HTML, CSS and report); `review` is the MCP tool `design_review` (E5.4, ADR-0018), a numbered critique list per file, kept in the workspace of the token; `variables_import` is the MCP tool `import_tokens` over the `variables-import` feature (ADR-0020): the arguments, the plan cut into parts of 100 commands, one atomic `Shared::submit_ops` per part and the answer with the report; `variant` is the MCP tool `make_variant` (E5.4) over `meldframe-variant`, which came out of `meldframe-http` to make room under its ceiling (ADR-0021): the arguments, the copy built from the file as read, one atomic `Shared::submit_ops`, and `VariantModule`, which registers the tool. A module named like a dependency crate (`export`, `variables_import`) makes a bare `use export::X` at the root of `meldframe-http` ambiguous; the modules write the path of the crate without a conflict because they are not the root.

**Touch hints.** When ops of a file are written (over REST, `/v1/ws` or MCP, by a person or an agent), `Server::submit_tool` queues one ephemeral frame on the live streams of that file: `{"type":"touch","actor","nodeIds":[...],"seq"}` (`ServerMsg::Touch`, generated into TypeScript), so the editor can draw the actor's touch ring (2 px in the actor colour with a name label, fading over 1.5 s: `docs/ui-design.md`). It uses the same seam as the capture request, `Streams::publish_ephemeral`, keyed by the workspace-and-file key: only streams that exist get it (no stream, no hub; a room is never opened or woken for it), never another file or workspace, with the streams' own queue cap, and a touch may use only the queue minus a headroom (an eighth of it, 1 to 16 slots) that stays free for durable frames and capture requests, so a hint never causes a resync and never crowds out a capture request (it is dropped silently instead; a full queue drops the frame, it never stalls a stream on its own, and a client that never reads holds at most one queue of frames before its usual `resync` marker). It is never stored (no sequence number is spent, the log is unchanged) and never replayed, and it holds ids only: no node data, no text. `nodeIds` are the nodes the batch touched (`meldframe_batch::touches`, so a reparent also names the new parent), each once, at most 64 (`MAX_TOUCH_NODES`); `seq` is the newest op of the batch, and the frame itself has no number. Rate: `meldframe_stream::Touches` allows at most one frame per actor and file per 100 ms (`TOUCH_WINDOW_MS`). The first goes at once; later ones inside the window replace each other, so the latest `nodeIds` win, and the waiting one is sent by the next `poll` or `tick` after the window ends (a socket looks every `live_poll`, 250 ms by default, so the last frame of a burst can be up to about that late). At most 1,024 actor and file pairs are tracked (`MAX_TOUCH_ENTRIES`); idle pairs (nothing waiting, window over) are dropped only when the table is full and a new pair arrives, and if all 1,024 are still inside their window that new pair gets no hint (best effort). The window uses the wall clock, like the writes; a clock that steps back counts the window as over. `Server` sends none until `with_touch_hints(window_ms)` is called (the binary does it; tests of the exact frame sequence stay unchanged), (`with_live` resets it, so call it first), and a batch that fails part way sends no hint for the ops it did write (the events still arrive). `Streams::touch` records only for a file that has a stream, so unwatched files cost no entry. A touch is a hint, not a record: who changed what is in the log and in `lastActor` of the snapshot.

**Batch frames (ADR-0021).** When `apply_commands` makes or changes the header of a numbered batch, the activity sink queues one ephemeral frame on the live streams of the file after the call's op events: `ServerMsg::Batch` (`room`, `n`, `rev`, `actor`, `keyPrefix`, `tool`, `commands`, `written`, `atomic`, `firstSeq`, `lastSeq`, `atMs`, `note`, `review`, `reviewedBy`, `reviewedAtMs`, `unreviewedCount`), built from the row the store read back. It is sent with `Streams::publish_ephemeral_with_headroom`, the touch headroom (an eighth of the queue, 1 to 16 slots): a stream whose queue is within the headroom of full does not get it. That keeps the last slots of every queue free of frames, so a frame never causes a resync by itself; it does not cap the frames' share of the rest. With a stalled reader and one frame per op the frames stop at 240 of 256 queued and a durable op overflows into the usual `resync` after about 136 one-op calls instead of 256, so the frames halve the slack of a stalled reader. A dropped frame gives no signal, is never replayed and has no number: the frame is a hint over the log and `GET /v1/files/{file}/batches` is the truth, with `rev` (one counter per file) to order changes and see a gap. A client that does not know the frame ignores it.

**Checkpoint frames and routes (ADR-0023).** A checkpoint that was made, a person's or the server's run start, is queued as one ephemeral frame on the live streams of the file after the call's op events: `ServerMsg::Checkpoint` (`room`, `n`, `seq`, `kind`, `label`, `about`, `by`, `atMs`; absent fields are left out), through `publish_with_headroom` like the batch frame, so it never takes the last slots of a queue, is never replayed and gives no signal when it is dropped. A row never changes, so the frame needs no `rev`; the list is the truth. `GET /v1/files/{file}/checkpoints` answers `{checkpoints, canCreate}` newest `n` first to any principal of the workspace (another workspace's file is an empty list, and the list has no call-log entry); `POST` with `{key, kind, seq?, label?, about?}` makes a row for a person, `by` being the principal's actor and never a field: only an actor the binary lists (the reviewers of ADR-0021 until a principal has a kind) under the registry's `Auto` policy for `checkpoint_create` may, `runStart` is refused, `seq` is at most the head of the file (the head by default) and a file with no ops has nothing to checkpoint. It answers `{checkpoint, created}`: the same key and request again answers the row with `created` false and sends no frame, the same key with another request is 409 `key_reused` (the error carries the first row's number as `n`), a `manual` row over its share or its actor's cap is 409 `checkpoint_full`, a store that fails is 503 `unavailable`. The call log holds the actor, `checkpoint_create`, the file and the outcome code, and no label. `GET /v1/files/{file}/checkpoints/{n}/state` is the file as it was at a checkpoint (`checkpoint_state`, the same gate as the create): 404 `not_found` for a number the file does not have, 422 `too_far` beyond 5,000 ops of replay; the answer, its bounds and its cache are described under `meldframe-http-checkpoints` above. The web client carries the three requests and the frame out in `packages/web-transport` (`checkpoints.ts`) and the browser check is `packages/web-panels/scripts/checkpoints-e2e.mjs`.

The room tests of the server are in `apps/server/tests` (`rooms.rs`: one room per file, workspace namespacing, every write through the gate; `approvals.rs`, `calls.rs`, `quotas.rs` and `rooms_limits.rs`); they were the crate `meldframe-server-tests` (#316) and use only the public `Server` API. `meldframe-sync-props` is a separate crate of kind `tool` for one reason: the random runs of several replicas against an in-memory server (convergence, undo per actor, refused ops, op dependencies) would have taken `meldframe-sync` over the 2,000-line ceiling with its scenario tests. The document model was one crate in the first plan. It is now several small core crates (ADR-0011) so that each stays within the crate size limit (ideal 1,500 to 2,500 lines, hard ceiling 50,000) with its tests. Not detachable (inner): the document model, the `Command` interface and the render model. Split concepts: variable bindings are in core; import, export and the panel are the `variables` feature. Server internals (admission, room, sessions) stay modules inside the server crates until a second binary needs them.

This layout replaces the one suggested in the survey (`docs/architecture/spike-survey.md`, section 6.4), which kept crates few and could not prove that a feature can be left out.

### 3c. Text from outside in the app layer (rule U9, #311 part 3)

Status note, 25 Nov 2026: `AppState` carries text that is safe to draw, so a front end cannot forget to clean. The choice of profile is written here once; the helper is `meldframe-text` (`label` for the display profile, `identifier` for the strict one), called where the text enters the app layer. What the file and the replica hold is never changed: node and mode names and node text round-trip as written (`App::nodes`, `App::vars`), and an op is applied under the actor and the key the server sent. ## 4. Modules and seams

Using deep-module vocabulary. A module is **deep** when much behaviour sits behind a small interface.

| Module | Interface (what callers know) | Depth | Adapters at its seam |
|---|---|---|---|
| Document core | submit a command; read resolved state; undo/redo for an actor; apply a remote op | Deep (proven in spikes) | Server (native) and client (WASM) consume it; not a port |
| Render model | resolve nodes and variables into painted boxes | Deep once built; **missing in the spike** | Two consumers: canvas and export (a real seam because two consumers exist) |
| Text measurer | measure text for a font, size, weight and wrap width | Small | Three adapters in the spike: stub, recorded table, browser |
| Admission gate | submit an op or batch with a principal; get a report or a typed refusal | Deep once consolidated; duplicated in the spike across WebSocket, MCP and REST | One gate with three transports on top; the room accepts a write only with a permit the gate creates (ADR-0010) |
| Module registry | register commands, settings, jobs, agent tools and panels; read them | Small interface, wide leverage | Read by editor, MCP and REST; leaving a feature out removes it everywhere (ADR-0007) |
| App layer | dispatch an action; read state; carry out effects; receive events | Deep once built; **does not exist in the spike** (rules live in the Svelte client) | Front ends: web now; desktop or mobile later; a test harness as the second driver (ADR-0008) |
| Room actor | accept ops in order, apply, persist, broadcast (`Server::subscribe`, `poll`, `seen`, `tick` and `submit_tool` (calls take the principal's workspace and the caller's clock) feed a `meldframe-stream` hub per file; the WebSocket transport is not built yet) | Deep (proven) | The `Store` seam has two adapters, in-memory (`meldframe-host`) and Postgres (`PgStore`, `apps/server`), both held to one contract suite (`meldframe-store-contract`) |
| Agent surface | MCP tools contributed by feature modules, over the gate | Thin by design | Adapter over the gate |
| Capture | request an image of a node or frame | Small | One adapter (browser relay); a second renderer is decision 18, so no port yet |
| Export | resolved model in, HTML/Tailwind/CSS variables and a warnings list out | Deep | Consumer of the render model |
| Blob store | put and get image bytes by content hash | Small | Local disk first; object storage later gives the second adapter |

**App layer (E1.6, first slice).** `meldframe-app` is a synchronous, deterministic state machine: `App::dispatch(Action) -> Vec<Effect>`, `App::state()` for the plain-data `AppState`, `App::nodes()` for the document and `App::take_events()` for `Event`s. It reads no clock and does no I/O: time is a payload (`now_ms`) of the actions that need it, and the transport is an effect the shell carries out. `App::new(actor, key_prefix, session, nodes, seq)` takes a session nonce the shell picks fresh for every App (a page load): the server remembers every idempotency key of an actor, so keys and node ids start with prefix and session and a restarted client never reuses one. State: the selection (known nodes only), the current tool, panel state (layers and properties open, collapsed layers), the properties of a single selection, the connection (`Connecting`, `Live`, `Reconnecting { attempt }`, `Offline`, `Halted`, with `confirmed_seq`), the history buttons (`can_undo`, `can_redo` and step counts from the replica's own history), the keys of unconfirmed ops (`pending`) and `last_actor` per node for the layers panel. Document actions (create a frame, rectangle or text node, move, resize, edit text, set a property, delete, reorder, undo, redo) become commands in the replica; a list action (move a selection, delete several) is checked whole before any command is applied, and a non-finite number is refused with `Event::Refused`. The person sees an edit at once; it goes out as `Effect::SendOps` only while the connection is live, and ops made while offline stay pending and go out again with the same keys when `Connected` arrives. Server frames (`Action::Frame`: event, rejected, resync marker, heartbeat) confirm, rebase or reject the pending ops. A refusal the server calls retryable keeps the op and sends it again with the same key after a backoff (`Effect::WakeAfter`, then `Action::Tick`), up to three times, then rolls it back with `Event::OpRejected`; any other refusal rolls back at once. The shell does not read the refusal: it hands the status and the text of the answer to the REST call of an op that is not a 200 as `Wire::OpRefused`, and the app takes the code and the `retryable` flag from `{"error": {...}}` (a code as the server wrote it, `E_` codes included), with `unavailable` for a code it cannot read and "retryable" for a flag it cannot read, so an answer that is not the server's (a proxy's page) is sent again by this rule (audit finding T14; `meldframe-app-parts`, `answers/ops.rs`). A gap in the numbers gives one `Effect::Subscribe { after_seq }` until a frame applies; a resync marker subscribes from the smaller of the marker and the replica's number. The server may refuse that subscribe on the socket it holds: the shell hands the text of the `error` frame that answers its last subscribe (it matches the id, which the app does not know) as `Wire::SubscribeRefused`, and the app sends the subscribe again after the wait the frame names (one second when it names none, and never more than 30 seconds, `MAX_RETRY_AFTER_MS`), three times at most, then goes offline; `bad_request` (a subscribe before the marker) waits for the marker, and any other code, or a frame the app cannot read, goes offline (audit finding T14; `meldframe-app-rules`, `subscribe`). A dropped connection gives `Offline` and `Effect::Reconnect { after_ms }` (1 s, doubling, at most 30 s; the backoff starts again only after the connection stayed live for 10 s); the shell dispatches `Reconnect` when the wait is over, and `Tick` ends a silent live connection (45 s) or a first connection or reconnect attempt that has not come up in 10 s. When the file and the server's events no longer fit, the app raises `Event::Diverged` once and halts (`Connection::Halted`): it ignores frames and edits (selection, tool and panels still work) and the shell must load a fresh snapshot and dispatch `Action::Reload` (below), or make a new `App`. `crates/core/meldframe-app-tests` plays the shell against the real `Server`, two editors and an agent. Export (D9): `AppState::export` names the one selected frame an export acts on (`target`) and, while the Export dialog is open (`OpenExport`, `SetExportFormat`, `CloseExport`; view state, no op), holds the document the `export` feature builds from the person's own view of the file (pending ops included, the modes on view), in Tailwind or plain CSS, with the report of what it could not carry, the size of each file it would save and the size the limit counts against that limit (the export counts the plain CSS stylesheet twice, because the form carries it inline and hands it back), built again only when the document, the modes, the frame or the format changed (a counter that `App::changed` raises); a halted app exports nothing (`OpenExport` is refused as `out_of_sync` and an open dialog closes), because its view may be out of date; the text is measured by the measurer the host injected (`App::set_measurer`; the browser's Pixi metrics on the font the canvas draws with, so a hug text exports the width the canvas draws), and by the layout core's stub when the host gave none; the MCP tool `export_frame` runs on the server, which has no fonts, and keeps the stub. Not built yet: the snapshot reload itself and the handling of `ReplayOverflow` (the shell's job today).

## 5. Data architecture

**Hierarchy.** Workspace has Files; a File has Pages; a Page has Frames; a Frame is a tree of Nodes. Variables live in Collections at workspace level; files bind to them. Components and instances are planned (decision 19).

**Node.** Stable id; type; parent and fractional order key (position among siblings; ties broken by id); geometry and layout fields; paint fields; text fields; optional image reference by content hash; bindings from property to variable.

**History.** An append-only log of ops per file with the actor, idempotency key, sequence number and the command; periodic snapshots for fast load. Every document and snapshot carries a **schema version** from the first release (the spike has none; adding one is part of the seed work).

**Variables.** Collection, Mode, Variable with stable opaque ids; values per mode are literals or aliases; names are slash paths for CSS and Tailwind mapping. Details and open questions: `docs/tokens-and-variables.md`.

**Assets.** Content-addressed by hash; png, jpeg, webp and gif only; metadata in Postgres; bytes on local disk first. Known limit (decision 36): there is no metadata table yet, so an asset has no name and no upload time, and `BlobStore::list` (behind `GET /v1/assets`) walks the workspace's directory on disk, a page of at most 200 at a time in the order of the ids, with the type told by the first bytes of each file. The Postgres index of names and upload times (newest first, search) is a later change; until then this walk is the deviation from "metadata in Postgres".

**Tenancy.** Every file, variable collection, asset and quota counter belongs to one workspace; no row is readable without the workspace in the principal.

## 6. Interfaces

- **WebSocket:** subscribe to a file; submit ops with idempotency keys and optional dependency keys; receive durable frames (accepted ops, with sequence numbers, replayable from a cursor) and ephemeral frames (agent touch hints, capture requests, progress; best-effort, never replayed). A full per-stream queue drops the frame and sends a resync marker (ADR-0009). The wire types are generated from Rust to TypeScript and a CI check fails on drift.
- **MCP:** tools to read, apply, capture, list limits, check batch status, manage assets and run design review. Tool text is English and part of the contract. Errors have stable codes.
- **REST:** snapshot, export, asset upload and session management.
- **Gatehouse:** OIDC for people; OAuth for MCP clients; the principal carries user and workspace.

## 7. Change semantics (carried from the spikes)

**Snapshot load (decision, issue 125).** A snapshot that reaches a replica is bytes from a network, so the client checks it itself rather than trusting that the server did. `Replica::new` returns `Result<Replica, LoadError>`: it runs `FileState::try_from_nodes` (the old-file migration, then `check_file`) and refuses a bad snapshot (duplicate id, missing parent, text node as parent, cycle, too deep, too many nodes, an invalid node) with the typed error and its stable code (`docs/error-codes.md`); nothing is repaired and no replica exists. A snapshot without `pos`, or with equal `pos` among siblings, is migrated exactly as a stored file is, so `E_MISSING_POS` and `E_DUPLICATE_POS` do not reach a replica through `new`. The server may also validate before it sends; that is a second line of defence, not a replacement. `FileState::from_nodes_unchecked` has no caller in library code; it stays for tests.

**Own ops, resync and the cap on the outbox (issue 90).** A live event carries the idempotency key of its op (`ServerMsg::Event.key`; the store already keeps actor, key and command, `ws.rs` copies the key); the field is optional on the wire (`#[serde(default)]`, absent when `None`), so an older client reads new events and a new client reads an old log. `Replica::on_event_keyed(seq, actor, key, command)` looks for the op of its own actor by key among its pending ops (an event without a key, and `Replica::on_event`, compare actor and command with the oldest pending op). A second session of the same actor, or a repeat of my command, has another key and is a remote event, and another actor never matches (keys are per actor). The oldest pending op is the normal case (`Confirmed`). A later one means the server ordered it ahead of an older op of mine: that one was refused for now (a quota, a dependency still pending: the app keeps it and sends it again) or is late, and the stream and the answer to a send are separate channels, so this is ordinary, not a fault. The op is confirmed all the same, out of order: its command goes into `base` at the event's `seq`, its undo step is confirmed, and the ops before it are built again on the new `base` (`Rebased`); the older op is confirmed by its own event later. `Diverged` stays for a key that is pending but comes back with another command, and for an event that does not apply to `base`; it changes nothing. `Replica::resync(nodes, seq, applied)` is the way back from `Diverged` or a lost connection: the snapshot is checked like the one of `Replica::new` and must not be older than the replica (`ResyncError::Load`, `ResyncError::Behind`, code `E_SNAPSHOT_BEHIND`; a refusal leaves the replica as it was). `base` and `seq` are replaced, the keys in `applied` (ops the server applied before the snapshot) are done, and the other pending ops are applied again on the new `base` in order with the same keys, kinds, dependencies and `seen_seq`; the outbox holds them all again, and one that no longer applies is dropped with the ops built on it (the count is returned, and the app raises `Event::OpsDropped`). The events between the old `seq` and the snapshot were not followed, so the undo history made before cannot be rewritten against them (an undo would overwrite another actor's write): it starts empty, and no replayed op is a step of it (a pending undo or redo op stays an op of its kind, and a correction stays a correction, so a later remote event does not make the replica correct them). **Procedure for the shell after a snapshot:** load the file (`nodes`, `seq`), call `resync` with every key whose answer it holds as applied (`applied`; the contract is below), send `take_outbox()` again with the same keys, and report every answer, including the answer to a repeated key (`{seq, written: false}`), to `Replica::on_ack(key, seq)` (the app's `Frame::Acked`): when the replica follows the file up to `seq`, the base holds the op and its event will never come (the stream starts after the snapshot), so the op is drained; an answer ahead of the stream changes nothing, because the event is still to come. **Contract of `applied`:** the shell must pass every key whose answer it holds. An op that the snapshot already contains but that is missing from `applied` is replayed on the snapshot, may fail there (an `AddNode` of an id that exists is a duplicate) and is then dropped together with the ops built on it (an undo of it), which `Event::OpsDropped` reports; the person's undo is lost. An op that replays without error stays pending until its duplicate ack drains it. **Contract of the acks:** the shell must report every answer, including the duplicate-key one, as `Frame::Acked`; with it a pending op is never stuck and cannot fill the cap, and until the shell does, an op the snapshot already holds stays pending and counts against the 10,000 cap. The shell side is not built yet: nothing in the tree emits `Frame::Acked` except the test harness of `meldframe-app-tests`, and the web shell does not exist. Then follow the stream from `seq`. `meldframe-app` models it: `Connection::Halted` (on `Diverged`) is left by `Action::Reload { now_ms, nodes, seq, applied }`, which resyncs, clears the retries and subscribes again from `seq` (`Connection::Connecting`); a bad or older snapshot is refused with `Event::Refused` and the app stays halted. The outbox is capped: `Replica::set_max_pending` (10,000 by default) makes `apply`, `undo` and `redo` (the last two only when there is a step to take) refuse with `SubmitError::OutboxFull` (code `E_OUTBOX_FULL`, `docs/error-codes.md`) while that many ops wait, and the app layer answers a document action with `Event::Refused { code: "outbox_full" }` (a list action is checked whole first). The check runs before anything changes, so a step may end above the cap by its own size and a correction that follows a remote op is not counted. `unconfirmed()` clones every pending op, so a caller that asks on every action pays O(pending), bounded by the cap. Tests: `crates/core/meldframe-sync/tests/{own_keys,resync,outbox_cap}.rs`, `crates/core/meldframe-app-tests/tests/{app_reload,reload}.rs`, and the property runs of `meldframe-sync-props` (events carry the key, refusals arrive behind later events, two edits reach the server in the other order, a replica loses its connection and resyncs, and on odd seeds of `room.rs` two sessions share an actor; `diverged` must stay 0).

Ops are idempotent per actor. The gate decides a batch as a whole; the room does not apply it atomically (7a). `ifSeq` rejects an edit of a node changed after the caller last looked. An op may name dependencies; it is accepted only if every dependency was applied, so an undo never lands on a premise the server rejected. Undo is per actor and recomputed against the current document: a field another actor wrote after me is not overwritten, and a node my undo would put under a parent the other actor deleted goes under the nearest ancestor that survives (the top level if none does); a step whose node was deleted is dropped. An undo or redo that is already on its way when another actor's op is ordered before my edit (a stale op) cannot be recalled, so the replica works out what the rebuilt steps would write and sends a correction: an `UpdateNode` for every node field, `image` included, where the stale op would leave an older value (a stale `Reparent`, `Reorder`, `AddNode` or `RemoveNode` is not corrected). The redo step keeps the fields that the other actor wrote before my edit, and the undo of an edit made later goes back to the other actor's value. A correction is worked out in the replica's model of the rebuilt steps: a later remote op that wrote a field removes it from the correction there, but a correction already sent or queued is not changed, so the server may briefly hold the older value until a follow-up correction restores the remote value. A correction the server refuses is sent once more, and so is every correction that falls with it because it named the refused one as a dependency. A correction that falls because it no longer applies (its node is gone) is not sent again: what it set is not left in the base. A resend refused a second time falls with whatever named it, and nothing else is sent (`stale_limits.rs`); a resync clears the mark, so after one a refused resend counts as a first refusal again. What is sent is only what the confirmed state still lacks: a field that a remote op wrote after the correction was made is left out, and so is a field that a pending op of mine writes (the edit wins). A second refusal ends it, so a server that refuses every correction is not asked without end. A correction that falls because a stale undo or redo it depended on was refused is not sent: that stale value never landed. Known limits: (1) a correction the server refuses twice leaves the stale value in the confirmed state, and nothing tracks it any more; (2) when an op other than a correction is refused or dropped, the replica forgets the stale values that earlier confirmed ops left in the confirmed state (it no longer tracks the state the rebuilt steps would give), so a later undo may start from them; every correction of mine that is still queued is kept and sets them right, and no case where none is left was constructed, which is not a proof that there is none; (3) when two actors have an undo on its way for the same field, a stale op and its correction of one actor are writes that come after the edit of the other, so the field may keep a value of an undone edit (a targeted test in `meldframe-sync` shows it: the replicas agree on the value and neither can tell it comes from an undone edit; the I9 property test skips such fields); (4) the resend skips a field that a pending update of the same node writes, and it cannot tell a stale undo from an edit of the person, so with a stale undo still pending and a refused correction whose dependent fell, the stale value can stay in the confirmed state with no correction (acks normally arrive in order, which makes this unlikely); "second refusal is final" holds per correction, not per field, so a later rebuild can send a fresh correction for the same field. The undo and correction rules before the refusal rules were verified by property tests; the refusal and resend rules and these limits only by the targeted tests in `meldframe-sync` and the unit tests of `correction.rs`. A revert of agent work is a new batch that restores only fields whose last writer is still that agent (`meldframe-revert`, ADR-0016). See the spike docs for evidence and the list of what was not proven.

**Approval for Ask (E2.4).** `Gate::submit` and `Gate::submit_with` are unchanged: an Ask call is `forbidden`. A caller that wants an approval path submits one op through `Approvals::submit(gate, who, file, op, facts, at)` (`meldframe-approvals`, not the gate: `meldframe-host` and `meldframe-rooms` are at their size ceilings and the gate holds no state). It runs the gate first; only a refusal whose policy is Ask opens a pending approval (id, actor, file, key, command summary, state, `created_at`, `expires_at = created_at + ttl`) and returns `approval_required` with the id. The owner calls `decide(id, Approve | Deny, by, at)`; the same op sent again (same workspace, actor, file and whole op: key, command, `if_seq` and dependencies, compared by the op's debug text) is then admitted by the same gate with its Ask read as Auto for that one op (the gate comes from `Approvals::gate(policy)`, an `ApprovalGate` that derefs to `Gate`, wraps the policy and has a flag of its own that only `submit` sets, behind a drop guard, so no other gate and no caught panic leaves Ask lifted; chain `.quota(n)` as usual), so the facts, the tier of the permit and the workspace quota are the real ones and the op is counted in `Gate::used`. The approval is consumed at that admission, not when the room applies the op, so an op the room then refuses has spent it; a quota refusal does not spend it. An op that the gate admits without the approval (the policy or the tier changed) consumes a matching approved one too, so it cannot admit the op again later. A second use asks again under a new id, as a consumed approval does not block a new one for the same op. A denied approval stays `approval_denied`, an expired one (pending or approved) `approval_expired`. A Deny policy, quota or shape refusal is never lifted: the approved op is admitted only after the real gate said Ask. Time is the caller's `at`; nothing reads a wall clock. Decisions go to the approval log (`Approvals::decisions`: approval id, actor, file, key, kind, node, state, `by`, `at`), not to the activity log, whose entries carry the sequence number of an accepted op. `by` is a label: the seam does no authorisation, who may decide is the owner's call (E2.4, Gatehouse). The match does not include the facts the tier depends on (the subtree size); `get` and `find` can show a Pending or Approved approval after its ttl until the next `submit`, `decide` or `request` marks it Expired. Approvals are in memory; `Approvals::prune` drops the finished ones one ttl after their time and keeps the newest 1,000 decisions.

**The server uses the seam (E2.4).** `Server` holds an `Approvals` and an `ApprovalGate` (the gate of the server, built with `Approvals::gate` and tuned through `approval::tune`, which keeps the flag). In `Server::write`, a call of exactly one op goes through `Approvals::submit`; a call of several ops goes to `Gate::submit_with` as before, so a delete inside a batch is still `forbidden`. `check_tool` lets the one Delete op of a Change tool reach the gate (the gate says Ask) instead of denying it for being above the tool's tier; any other op above the tier is still denied there. An approval covers the exact op (key, command, `ifSeq`, dependencies) and is not tied to the tree: a retry without `ifSeq` can delete a frame that gained content after the ask (tying it to the subtree size at ask time is a follow-up). An idempotency key of over 100 characters opens no approval (`forbidden`). The one-op rule counts the ops of the call as sent, before ops already written are left out; a removeNode of a node that is not in the file does not ask and keeps its refusal. An actor may hold 20 open approvals, a workspace 100, and the set is 2,000 in all (`approval_limit`), so every scan stays short; an id is 128 bits, two keyed hashes of a counter under a key made at start, so it is not a count and a stale id never matches a new one. `SubmitError::Approval` carries the refusal; the transport maps it to `Failure::Approval` (HTTP 403, or 429 for `approval_limit`; error code, `retryable: false` and `approvalId`). The owner answers with `Server::decide_approval(who, id, approved)` (also on `SharedServer`): it refuses the actor that asked and an approval of another workspace, records the answer as one call-log entry (`decide_approval`), and is the one seam a route, tool or screen will call once sign-in tells an owner from an agent. No MCP tool answers an approval, because the agent would answer itself. A tool whose own policy is Ask (a Delete-tier tool) is still `forbidden`: the seam covers the Ask of an op, not of a tool. Ttl: `APPROVAL_TTL_MS`, 15 minutes, a working default.

### 7a. The dependency rule in the room

An op may name **dependencies**: idempotency keys of ops. The gate and the room enforce one rule; the replica builds its dependencies from its own pending keys and never relies on it for safety. Each clause is pinned by a test in `crates/core/meldframe-rooms/tests/dependencies.rs` (and, against random runs of replicas, `crates/core/meldframe-sync-props/tests/room.rs`).

1. **Same actor only.** A dependency counts only if the room's log holds that key for the same actor of the same file (`Store::find`). A key of another actor, an unknown key and a key that was refused all answer `dependency_rejected`, naming the first missing key. Two actors may use the same key text; they are different keys.
2. **Every dependency, not one.** The op is written only if all of its dependencies were applied.
3. **At most 512 dependencies** (`MAX_OP_DEPS`), no empty or repeated key, and no op that names its own key. The gate refuses these as `invalid` before the room sees the op (exactly 512 passes, 513 does not).
4. **Forward and cyclic dependencies are refused, not deferred.** The room decides when the op arrives: a dependency that is not applied yet makes the op `dependency_rejected`, and the refusal reserves nothing (the op's own key stays free). The client sends the dependency first and the dependent again. A cycle can therefore never be applied. The room has no `dependency_pending` outcome; that word in `wire.rs` is reserved for a transport that holds a dependent op on a connection, and the room never produces it.
5. **A refusal cascades.** An op that was refused is not applied, so every op that names it, directly or through a chain, is refused with `dependency_rejected` until the first one is corrected and applied.
6. **Order within a batch.** The gate decides a batch as a whole, then the room takes its ops one by one in the batch's order. An op may depend on an earlier op of the same batch (it is applied by then); a dependency on a later op of the batch is a forward dependency. A refused op does not stop the ops after it; its dependents are refused by clause 5. A batch is not atomic in the room today.
7. **Applied keys are remembered for ever.** The rule reads the log, not a cache or a time window, so a resend after any disconnect still finds keys confirmed long ago, across a restart, a snapshot and a log longer than one replay page.

**Small delete (ADR-0010).** The tier of a `RemoveNode` depends on the room's tree, so the gate takes facts about it: `Gate::submit_with(who, ops, &dyn NodeFacts)`, and `Gate::submit` is the same with no facts, where every delete is a Delete. `meldframe-rooms` implements `NodeFacts` as `TreeFacts::new(room.nodes())`. A delete is a Change (Auto under the default policy) when the node is in the file, is not a frame, and its subtree (the node and its descendants) has at most `SMALL_DELETE_MAX_NODES` nodes (10, defined in `meldframe-rooms`); every other delete is a Delete, Ask by default and refused as `forbidden`. A node the facts do not know is a Delete (fail closed). Callers pass the facts of the room the ops target. The facts are the tree before the batch: a node added in the same batch is unknown, and a batch that adds or reparents any node gets no relief for its deletes, because it could grow the subtree it then removes. The facts are read at submit time. The room re-checks one thing when it applies a delete whose permit tier is below Delete: the node must still be a non-frame node without children, otherwise it refuses with `forbidden` (Delete, Ask); so a leaf removed and a frame added under the same id cannot be deleted as a small delete. It does not re-count the subtree. Today only a frame can have children (the core refuses a child under a non-frame node), so the 10-node limit is a guard that no tree built by the room reaches: in practice every non-frame delete is small and every frame delete is Ask. The permit carries the tier the gate decided.

8. **A retry is checked before dependencies.** A key that is already applied returns its first sequence number and writes nothing when the command is the same (`invalid` when it is another command), whatever dependencies the retry names: the stored op keeps no dependency list, and the key is the identity.

## 8. Fidelity and verification

The core's layout result is the source of truth. The export translates it to CSS. An oracle test renders the export in Chromium and compares boxes, text ink and paint probes with the core. The contract, tolerances and measured results are in `docs/fidelity-contract.md`. Documents that fall outside the contract (fill under hug, overflow, zero-width fill) are normalised or warned on write instead of being matched in CSS.

Capture lets an agent check its own work. The first adapter relays the request to an open editor; headless rendering is decided later with measured cost.

## 9. Security and privacy

- Authentication through Gatehouse; agent sessions are short-lived, bound to one file selected in the UI, and revocable at once.
- Rate limiting happens before parsing; quotas per workspace; per-call timeouts.
- Uploads: image types only; SVG rejected until sanitisation exists.
- No secrets in process arguments, logs or tool output; no code from user input runs on the server (imports accept text; config files written in JavaScript are resolved by the agent locally).
- Agent-written text (batch notes, layer names) is untrusted: rendered as plain text, length-limited.
- Audit: every op has an actor and is kept in the log.

## 10. Non-functional approach

Performance is a property of the core running in WASM on the client; the server stays thin. Reliability comes from idempotent ops and a log that can rebuild state. Observability: structured logs with workspace, file, actor and sequence number; counters for rejects by code. Backups are database backups. Scaling beyond one server process is not a driver now; the room actor assumes one writer per file.
