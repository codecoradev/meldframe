# Audit: TypeScript and Svelte front end against the thin UI rules

Repository `codecoradev/meldframe`, `github/develop` at `05a6da8` (feat(html-import): paint stage, the shadows and the opacity, E4.4 slice 5, #304). Read-only audit on a detached worktree. Every line count, import and quotation below was read or measured in that tree; where a figure is an estimate it says so.

Scope: `packages/protocol`, `packages/web-*` (18 packages: 16 of kind `ui`, 2 of kind `tool`), `apps/web`.
Reference rules: `docs/standards/modular-thin-ui.md` (U1 to U8, L1 to L6, D1 to D9), ADR-0007 to ADR-0010, `docs/architecture.md` section 3b, `GLOSSARY.md`.

Two notes on the reference:

1. At the time of the audit (`github/develop` at `05a6da8`) the repository mirror of the standard was still version 1.2 (`docs/standards/modular-thin-ui.md:3`). Version 1.3 was read from the pull request that adopts it (tracking issues #305 to #309; this audit is #307). The parts that matter here:
   - **D1**: a package MUST stay under 50,000 lines; the product is a modular monolith and that is mandatory: one small module per page or capability with its own tests and directory of small files, shared pieces in a reusable module of their own and never copied.
   - **U9**: "Text that comes from a model, a server or a file MUST be made safe to display (control and bidirectional characters removed, markup not interpreted) and capped in length at the point where it enters the app layer, in one reusable helper that every screen shares. A screen MUST NOT clean text again, and MUST NOT show raw text from those sources. A count that cannot be known (a list that failed to load, a request that did not answer) MUST NOT be shown as "nothing waiting" or as zero; it can say Unknown."
   - ADR-0026: the web client moves from Svelte to React after "direction A": every rule and every piece of state of the editor lives in portable Rust, and a front end reads state, dispatches actions and carries out effects.
2. Size limits were stated three ways at the time of the audit: `AGENTS.md` says "a crate under 2,000", `docs/standards` v1.2 and `xtask/src/size.rs` say ideal 1,500 to 2,500 with a hard ceiling of 4,000, and the owner says 50,000 for v1.3. D9 says code is authoritative; the code said 4,000. No TS package is near any of them (largest product package: `apps/web`, 2,143 lines).

How I counted: "product" is every `ts`, `svelte`, `css`, `js`, `mjs` file under the package, excluding `*.test.*`, `scripts/`, `src/harness`, `TestHost.svelte`, `rust/` stubs and `protocol/src/generated`. `apps/web` product includes `vite.config.ts` (103), `eslint.config.js` (18), `svelte.config.js` (3), so its `src/` is 2,022 lines.

Checks I ran in the worktree (all in `apps/web`, after `npm ci`): `npx vitest run` gives 96 files (93 passed, 3 skipped, the WASM ones), 1,263 tests (1,210 passed, 53 skipped), 15 s. `npm run typecheck` (svelte-check): 1,799 files, 0 errors, 0 warnings. `npm run ui-literals`: ok. `eslint` run by hand on three packages the lint script leaves out: see finding T18.

## 1. Size and shape at a glance

Totals: **12,359 product lines** (7,363 ts, 4,677 svelte, 319 css) in 60 `.svelte` files and 81 non-test `.ts` files outside `protocol/src/generated`; **11,497 lines of unit tests** (90 `*.test.ts` plus 3 `*.wasm.test.ts` files, about 1,230 `it()` calls); **6,981 lines of scripts and their tests** (34 `.mjs` files under `packages/*/scripts`: 30 Playwright e2e, demo, perf and helper scripts, run by hand and not in CI, plus 4 tooling files of `web-tools`; the total also holds 252 lines of tooling tests).

The Rust app layer for comparison: `crates/app/meldframe-app` 2,805 lines with its wasm bridge, plus `meldframe-app-model` 2,524, `-parts` 1,485 and `-rules` 1,546. So roughly 8,400 lines of Rust hold state and rules against 12,359 lines of TS/Svelte, and about 2,660 of those TS lines (my sum of the findings below, section 4) are rules or state.

The bridge is narrow and mostly honoured: `crates/app/meldframe-wasm/src/lib.rs` exposes `dispatch`, `stateJson`, `nodesJson`, `variablesJson`, `sceneJson`, `dropPreviewJson`, `takeEventsJson`, `setLayoutOnCanvas`, `setMeasurer`. `packages/web-link/src/engine.ts` is a faithful, rule-free wrapper of it.

### Framework and library confinement (verified by grep over non-test sources)

- `svelte` is imported only by `.svelte` files plus `apps/web/src/main.ts` and `apps/web/src/harness/main.ts` (`mount`, `unmount`). No `.ts` file under `packages/` imports `svelte`, `bits-ui` or `pixi.js`.
- `bits-ui` is imported by 10 `.svelte` files (section 3).
- `pixi.js` is imported only by `apps/web/src/canvas/{Canvas.svelte,stage.ts,overlayview.ts,shadowparts.ts,pixitext.ts}`.
- No `.svelte.ts` rune modules exist: every rune is inside a `.svelte` file, all logic modules are plain TS.
- No `.ts` file imports a `.svelte` file except the two composition roots.

So a framework-import rule would pass today with zero violations (section 5). The front end is better layered at the import level than at the rule level.

## 5. Design of a boundary checker for TS packages (about 30 lines)

`cargo xtask ts-deps-check`, a pure function over package data in the style of `xtask/src/rules.rs`, unit-tested with negative fixtures, run in `npm run check`, `just check` and `ci.yml`. A Node implementation next to `ui-literals-lib.mjs` is the alternative and reuses its comment stripper.

1. Source of truth: `package.json` of every `packages/*` and `apps/web` gets `"meldframe": { "kind": "...", "group": "...", "composite": [] }`. The Cargo stubs, `tsconfig` paths, `vite` aliases, the lint loop and the Tailwind `@source` list are generated from the same set (finding T18).
2. Kinds:
   - `proto`: generated types (`protocol`). No imports.
   - `model`: pure TS, no DOM, no framework, no I/O (`web-document`, `web-canvas`, `web-paint`, the `.ts` parts of the feature packages).
   - `host`: browser adapters with DOM, `fetch`, `WebSocket`, `localStorage` (`web-link`, `web-transport`, `web-assets`, `web-input`, `web-tokens/theme`).
   - `kit`: framework primitives with no feature knowledge (`web-chrome`).
   - `view`: feature components (`web-panels`, `web-activity`, `web-variables`, `web-variables-io`, `web-export`, `web-feedback`, `web-shell`).
   - `render`: the one canvas drawing module (`pixi.js`).
   - `bin`: composition root (`apps/web`). `tool`: scripts and e2e.
3. Matrix (may import): `model` → proto, model; `host` → proto, model, host; `kit` → none but itself; `view` → proto, model, kit, view of the same group or a `composite` group; `render` → proto, model, host (assets only), render; `bin`, `tool` → anything.
4. Framework rule: an import specifier in `svelte*`, `react*`, `bits-ui`, `@radix-ui/*` is allowed only in `kit`, `view`, `bin`; `pixi.js` only in `render` and `bin`. A `.svelte` or `.tsx` file may sit only in `kit`, `view`, `render`, `bin`. In mixed packages (all feature packages are today) apply the rule per file: a `.ts` file may not import a framework or a `.svelte` file. **Verified: this passes with zero violations today.**
5. DOM rule: for `model`, ESLint `no-restricted-globals` (`document`, `window`, `navigator`, `localStorage`, `fetch`, `WebSocket`, `performance`); `host` is where they live.
6. Group rule (L4): two `view` packages of different groups may not import each other unless `composite` names the group. Today it reports `web-variables-io` → `web-export` (`io.ts:7`, `sizeText`) and `web-variables-io` → `web-variables` (`io.ts:8`), which T1 removes by moving the helpers to a shared module; `web-panels` composing the variables dialogs is a legitimate `composite = ["variables"]`.
7. Cycles: fail on any cycle of the package graph (none today; `web-document` → `web-canvas` and `web-panels` → `web-variables-io` → `web-export` are acyclic).
8. Duplicate-name rule (cheap AST heuristic): fail when a `model` or `view` file declares a string-literal union that equals an exported union of `protocol` (`Tool`, `NodeKind`, `RightTab` in T3).
9. Parsing: use the TypeScript compiler API for `.ts` and the Svelte compiler's `parse` for `<script>` blocks; count `import`, `import type`, `export ... from` and dynamic `import()`. Test files are checked only for kind-crossing into other packages, not for frameworks.
10. Output: `path:line: kind -> kind: specifier` per violation, non-zero exit; an allow-list `xtask/ts-allow.toml` in the style of `size-allow.toml` (entries only go down, `--base <ref>` rejects new ones).
11. Self-test: a fixture package per kind with one forbidden import each, and the real tree must pass; add the check to `build-matrix`'s sibling gates in `nightly.yml` only if it proves slow.
