## What stays separate, and why

- **`meldframe-protocol`, `meldframe-text`, `meldframe-css`, `meldframe-module`, `meldframe-order`.** Leaf crates with no dependency of their own and many importers (`protocol` about 50, `text` 24, `module` 26). The lowest crates must stay light: `protocol` for `ts-rs` and the generated TypeScript, `text` and `css` because the MM4 homes in `xtask/monolith.toml` point at their paths and the wasm bridge calls `displayText`. Merging them upward would make every checker depend on a larger crate. No change.
- **`meldframe-app-model`, `meldframe-app-export-model`, `meldframe-camera`.** The vocabulary of the app seam (Action, Effect, Event, AppState and their TypeScript types, which `tools/check-protocol.sh` builds with `cargo test -p`). `meldframe-net` in the Rune workspace is kind `os` and imports only `meldframe-app-model`; if the model were a module of `meldframe-app` the net crate would depend on an `app` crate, which the matrix forbids for `os` (and `deps-check` reads both workspaces). The model has a real cycle among 14 modules (`mm-check` at a lower threshold) that would block it under MM5, and no app logic. Recommendation in the decisions below: it stays, as `core`, which is its honest label.
- **`meldframe-wasm` (ffi), `meldframe-headless`, `meldframe-app-harness`, `meldframe-oracle-runner`, `meldframe-store-contract`, `xtask`.** Bridges, tools and test support with their own reason to exist (L5 for wasm, U8 for the headless proof).
- **The portable and the host side never share a crate.** `meldframe-http*` and `meldframe-store-pg` use axum, hyper, tokio, rmcp and sqlx and are kind `bin`, so `portable-check` does not build them for `wasm32`. They merge among themselves only: no adapter code goes into a feature crate (`export`, `html-import`, `assets`, `capture`, `design-review`, `variables-import`), which stay portable and keep their own cargo feature on the server (M3).
- **`meldframe-store-pg`.** It implements the `Store` seam of `meldframe-host` over Postgres; it is not an HTTP adapter, so a crate named `meldframe-http` would hold it under the wrong name, and it is the only crate with `sqlx` and `migrations/` (`sqlx::migrate!("../../../migrations")`, which also fixes its depth). It stays, and is looked at again with the activity group below.
- **`apps/server`** (composition root), the feature crates and the Rune workspace (a second workspace that `deps-check` keeps one way: its crates may depend on the main ones, never the other way).

## The rules of a merge

A merge is a stack of pull requests on one target crate. Each step is a pure move plus the edits the move forces.

1. **Direction: the consumer first.** The target is the crate the others feed (`meldframe-app`, `html-import`, `meldframe-http`). The member nearest to the target moves first, so that at every step only the target (and members already moved) depend on it. The member cannot be left behind as a re-export of the target: it would depend on the target while the target still depends on it (a cycle), and a `core` member may not depend on an `app` crate. So the facade that carries the stack is the target's: `html_import::html` is `pub use html_import_tree as html` today, and `meldframe_app` already re-exports the model's types. A move turns `pub use member as name` into `pub mod name`, and no caller outside the group changes. A crate outside the group that names the member by its own path (the test crates, the harness) is edited in the same pull request, `use old::` to `use meldframe_app::module::`; the lists below count them.
2. **A pure move.** `git mv` of the member's `src/` into `<target>/src/<module>/`, its `lib.rs` becoming `<module>/mod.rs`. The diff of a moved file is paths and `mod` lines only. Proof, to paste in the body: `git diff -M --numstat origin/develop...HEAD | awk '$1+$2>0 {print $3}'` lists the files whose text changed (a 100% rename prints `0 0`), and that list must be manifests, the named lists and `use` and `mod` lines. No test is rewritten, split or dropped; no function is edited. The one allowed text change in a moved file is a blank `//!` line that ends the first sentence of a module root's doc (what MM2 reads: `doc_sentence` takes the first paragraph of the `//!` docs and wants one sentence), named in the commit.
3. **Phase 1 keeps the shape of the old crates; phase 2 regroups by capability.** Phase 1 turns each member crate into one directory module of the target (`rules/`, `parts/`), so no two files meet and no name clashes, and the top-level modules of the target stay acyclic because the crates were (MM5). Phase 2 moves files between those directories into one directory per capability (`review/`, `checkpoints/`, ...). Each phase-2 move is a `git mv` and a `mod` line, run through `mm-check` for a cycle before it is pushed.
4. **Prepare before the first move.** `mm-check` applies MM1, MM2 and MM5 to a crate above 4,000 lines (tests counted). `meldframe-app` is at 3,995, so the first move crosses it, and then the target's own source is judged. Run on `develop` with the threshold lowered to 1,000 in a scratch edit (reverted), it finds: `meldframe-app` 23 MM2 and 1 MM5 (modules `app`, `document`, `panel`, `scene` use each other); `meldframe-app-parts` 14 MM2 and 1 MM5; `-rules` 18 MM2; `html-import-tree` 12 MM1 (its `lib.rs` holds structs and impls); `html-import-css` 12 MM2 and 1 MM5 (`css`, `tw`); `html-import-style` 6 and 1; `meldframe-http` 20 MM1 and 19 MM2 (`lib.rs` is 437 lines of fns and impls); `meldframe-store-pg` 13 and 6. Most are a missing or two-sentence module doc. These fixes are changes of code or docs, not moves, so each merge opens with its own short preparation pull requests (below), under the same test-first rule. Members' nested modules are not judged (MM2 reads top-level modules only), so only the roots of the new top-level modules and the target itself need work before a phase-1 move.
5. **Budget of a pull request.** Edited lines under 1,000 and 15 files, pure renames not counted (AGENTS.md: pure moves do not count). A member whose edits would pass that, or which Cora would time out on (about 2,500 diff lines, D8), moves in two or three pull requests, leaf files first: the order comes from a script over `use crate::` edges (for `meldframe-app-rules` it gives three layers, 12, 6 and 3 modules; for `-parts` a cycle of five modules that move together).
6. **Stack mechanics (from #316).** A linear stack, one branch on the tip of the one before. A squash merge of step N swallows the commits that step N+1 carries from step N, so after each merge run `git rebase --onto origin/develop <old tip of N> <branch of N+1>`. One merge of a group is in flight at a time. A name that clashes with an existing module or file is given a prefix (`pointer_machine` against the `pointer.rs` of `meldframe-app`), recorded in the commit body. The test counts are compared per binary before and after with `cargo test --workspace --no-fail-fast` (the totals equal; a binary that disappears is the empty library test of a crate that is gone; the `ts-rs` export tests stay with the model).

## Gates of every pull request

`cargo fmt --all --check`, `cargo clippy --workspace --all-targets -- -D warnings`, `cargo test --workspace --no-fail-fast` (counts before and after), and:

- **`cargo xtask deps-check`.** The target's manifest takes the member's dependencies (minus what it has) and loses the member; a feature crate that `meldframe-app` now names directly (`export`, `variables-import`) is allowed for kind `app` (`xtask/src/rules.rs`: app may depend on core, engine, integration, os and feature). The `group` of the merged crate stays (`html-import`). A crate of the Rune workspace is read by the same command.
- **`cargo xtask build-matrix`.** Merges A and B add no feature. Merge C adds nine; each must build alone, and the tests of every crate must pass with default features off.
- **`cargo xtask portable-check`.** `meldframe-app` and `html-import` stay portable: the union of dependencies adds nothing that is not portable (the members were portable crates). The merged `meldframe-http` is `bin` and is not built for wasm.
- **`cargo xtask mm-check --base origin/develop`.** MM1, MM2 and MM5 apply to the target from the first move (rule 4). MM3 and MM4 allow-lists only go down: an `[[allow_copy]]` group follows a moved file by function name, an `[allow_shared]` entry by file name; a group that gains a member fails.
- **`cargo xtask toolkit-swap --graph-only`.** `INNER` in `xtask/src/toolkit_swap.rs` names the members and reports a missing crate as a violation, so each move changes that list and its fixtures in `toolkit_swap/tests.rs` in the same pull request.
- **`cargo xtask size-check --base origin/develop`.** The largest result is `html-import` at about 19,700 lines with tests; no file is over 500 and `size-allow.toml` gets no entry.
- **`just wasm-test`.** None of the three lists (the `justfile` and the two `nightly.yml`) names a member of these groups: they name `html-import`, `variables-import`, `meldframe-headless` and the app test crates, which keep their names. They change only when a test crate moves into a merged crate (#316), and then all three together. A moved file without the `wasm_bindgen_test` lines still passes under wasm without running (AGENTS.md), so a count that must hold is read from the native run.
- **`tools/check-protocol.sh`** unchanged while the model stays; `cargo test -p meldframe-wasm` and `just wasm-smoke` for B (the bridge builds `meldframe-app`).
- **`frontends/rune`.** Its `Cargo.lock` names the app members (`meldframe-app-parts`, `-rules`, `-pointer`, `-nudge`, `export-dialog`, `variables-import-dialog`), and its job runs `--locked`. Each B pull request refreshes that lock (`cd frontends/rune && cargo update --workspace`; the diff must only delete package blocks and dependency lines), which also makes the `rune` job run in that pull request.
- `scripts/ci/message-patterns.sh` on the commits, and the review by Cora before the pull request.

## Risks

- **A merge crosses the monolith threshold in its first pull request.** The preparation pull requests (rule 4) are a code change the issue did not list; they are small and independent of the move, and they can run in parallel with another merge.
- **39 of 40 top-level modules after B5.** There is no room for a second group in `meldframe-app` until phase 2 lands; do B6 to B12 straight after.
- **The public surface of `meldframe-app` grows.** The test crates, the harness and `meldframe-net` use the members' public items, so phase 1 makes `rules`, `parts` and the others `pub mod`. After #316 moves the test crates in, the modules can narrow to `pub(crate)`; do not narrow them in this stack.
- **One crate rebuilds as a whole.** A change in one adapter or one panel recompiles `meldframe-http` (about 8,000 lines) or `meldframe-app` (about 12,000). Record `cargo build -p meldframe-server` after a one-line change before C1 and after C6; no gate, but the number goes in the last pull request.
