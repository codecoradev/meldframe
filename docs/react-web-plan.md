## 1. What changes and what stays

Changes: the 60 `.svelte` files (4,836 lines; 4,677 product, `TestHost` 10, `Harness` 149), Bits UI, the Svelte checks and lint, the Svelte parts of the literal scan, and the 21 + 4 tests that need a Svelte runtime or read `.svelte` source.

Stays, as ADR-0026 says: the Rust app layer and the WASM bridge, the framework-free TypeScript (about 7,000 lines of rules and view models, canvas, paint, input, transport, tokens), Tailwind CSS v4 and the tokens, the gate and the events, and the 30 browser scripts under `packages/*/scripts` as the check that the new screens match the old ones (their 234 `data-testid` values are kept).

## 2. Tailwind stays

Yes. Tailwind v4 is applied by `@tailwindcss/vite` (`apps/web/vite.config.ts`), which is not tied to a framework. Tailwind reads source files as plain text and scans every file that is not git-ignored, so `.tsx` files need no configuration (source: tailwindcss.com/docs/detecting-classes-in-source-files). What the port does to it:

- `class=` becomes `className=` (476 strings in `.svelte` today); the strings themselves are portable.
- A class name must exist in full in the source. Svelte's `class:` directive and string building are not used for colours today; in React a class is never built from a prop (`bg-${x}`), a prop is mapped to complete strings. The review checklist says so; a lint rule is optional.
- The `@source` list in `packages/web-tokens/src/tailwind.css` (the packages that draw with classes) stays as it is. No new package is added for the port (view files sit beside their model files, as U3 is practised today).
- The 25 `style:` directives become `style={{ ... }}` objects and the one `<style>` block (`Canvas.svelte`) becomes a CSS file. Colours, font sizes and durations still come from the tokens module (U4).
- `@custom-variant hov` and the `data-preview` states used by `/?states` are CSS and do not change.

## 4. Options for the shape of the migration

| Option | What it is | For | Against |
|---|---|---|---|
| A. Rewrite on a branch | One long-lived branch, switched at the end | One toolchain at a time | Breaks the rule of small pull requests, nothing to compare the new screens with until the end, the editor changes under it (it is not frozen), large merge risk |
| B. React islands inside the Svelte shell | Panels and dialogs become React roots mounted from `Editor.svelte` and `Layout.svelte` snippets; the shell goes last | Panel by panel, each slice small and shippable; both versions can be run against the same browser script; no freeze | Two frameworks and two plugins in one bundle for a while; leaf primitives (`Button`, `Field`, ...) must exist twice until the last Svelte consumer is gone; two portal and focus systems at once (Bits and the new library) |
| C. New app directory with a list of screens to match | `apps/web-react` beside `apps/web`, switched when the list is green | Clean toolchain | Two editors to keep in step while features keep landing (every change twice), a match only at the switch |
| D. React shell with Svelte islands | The reverse of B | The composition root moves early | The most coupled file (`Editor.svelte`, 374 lines: camera, preview, text edit, overlay, toast) moves first, and Svelte `mount()` inside React is the less trodden path |

Proposed: **B**, leaf panels first and the shell last. Reasons: the audit found no framework import outside view files and no store or context to replace, so an island needs only the engine, which both frameworks read through the same `subscribe` and `snapshot`; the open state of the Export dialog and of the export-variables dialog is app state (`state.export.dialog`, "open while the app holds the text"), and the two page-level flags that remain (`manageOpen` and `importOpen` of the Variables panel, audit finding T11) stay in their Svelte host until that panel is ported and reach its island as a prop and a callback, so no state is shared between the frameworks; `Layout.svelte` already takes its panels as snippets, so a React root fits a snippet.

Transitional duplication, with an end: the primitives of `web-chrome` (about 380 lines of `Button`, `Checkbox`, `Field`, `Icon`, `IconButton`, `Section`, `Segmented`, `Tabs`) get a React copy first, and the Svelte copy goes with the last Svelte file that uses it. The class strings and the logic files (`focus.ts`, the view models) are shared, so only the markup is twice. The `/?states` page checks both copies in six states and two themes.

Optional switch (question 2 in section 9): while a panel exists twice, a query parameter such as `/?react=export,activity` picks the React version, so the same browser script runs on both before the Svelte one is deleted. It is a temporary switch like `/?canvaslayout=`, removed in the last slice.

## 5. Component library that replaces Bits UI

The product uses four families: Dialog (5 places), Menu, Tooltip, Popover. Tabs, Segmented, Checkbox, Field and Switch are hand-written or native already. UI language is English (decision 4), so translated strings, calendars, tables and trees are not needed.

| Library | Fit | Notes |
|---|---|---|
| Base UI (1.x) | Covers the four families; unstyled, part-based like Bits (Root, Trigger, Portal, Popup, Title, Description, Close); MIT; 37 components, 5 direct dependencies, tree-shakable | 1.0 in December 2025, so younger (10 minor releases by October 2026); no translated strings (not needed); the default of shadcn/ui since July 2026; needs a stacking context on the app root for portals (its quick start) |
| Radix Primitives | Same families, the most downloaded, mature | Not deprecated; shadcn/ui still ships both; the part API Base UI copies |
| React Aria Components | Strongest accessibility record and tests, hooks layer | Larger surface; its extra strength (dates, colours, tables, trees, 32 languages) is unused here |

Proposed: **Base UI**, with Radix as the fallback if the pilot dialog fails the focus checks of section 7. The reasoning is fit and size, not popularity: the mapping from Bits is close to mechanical, and only four families are used. Caveat on the evidence: the comparison I read (untitledui.com, October 2026) is by a vendor that builds on React Aria, and its numbers are as of that month; the plan does not depend on them beyond "Base UI covers Dialog, Menu, Popover, Tooltip" and the pilot checks the rest. Focus return after a close stays our own helper (`rememberFocus`, `takeFocusBack`), rewritten against the new library.

### Focus handoff

Status, 25 Nov 2026. Where the focus goes when an overlay closes was written three times in React, in `Menu.tsx`, `ExportDialog.tsx` and `Palette.tsx`, each on top of the one-element slot of `focus.ts` (`rememberFocus`, `takeFocusBack`), and each with a side effect inside Base UI's `finalFocus`. Base UI 1.9.0 resolves `finalFocus` in the cleanup of the focus manager's return-focus effect (`FloatingFocusManager`), whose dependencies include the popup element and the trigger, so the cleanup runs when one of them changes while the popup is open and not only on a close. A call with a side effect is wrong twice: the Export dialog's `takeFocusBack()` spent the remembered element on the first call and `el.focus()` moved the focus out of an open dialog, and the palette ran the chosen entry there (a throw broke the cleanup; no cleanup, no entry). Observed once by hand on 25 Nov 2026, with no script or test that repeats it: with the popup drawn as another element while open (a section for a div, in the overlay fixture) `finalFocus` is called once in the middle of an open and once on the close; an agent's change, a rename, a tab change and a resize of the window, each while the real Export dialog was open, did not call it before the close, so the product did not meet the second call then. Nothing committed counts the calls or resizes the window. What is committed: `handoff.test.ts` asserts through the interface that `finalFocus` answers the same however often it is asked and moves nothing, `overlays-e2e.mjs` draws the fixture dialog's popup as another element while it is open and asserts that the focus stays in the dialog and still goes to the handed place on the close, and `export-e2e.mjs` changes the frame's name and the tab while the dialog is open and asserts that Escape gives the focus back to the File menu button. With the old pattern in the fixture, the second call sent the focus to the remembered place while the dialog was open and the dialog pulled it back; the end result was right by accident, because the moved focus became Base UI's own default.

What the scripts covered before: `export-e2e.mjs` already followed File menu, Export, Close, File menu button, so the menu's ref (through the trigger, the tooltip and the button) did reach `takeFocusBack` there; the overlay fixture's dialog was only an input that never gave the focus back, so `overlays-e2e.mjs` did not.

Deletion test. Delete the module and each of the three callers grows it again: a flag or a ref (`keepFocus`, `later`, `before`), a read of the slot at close, and the order rules (take the slot once, record the opener before the focus moves, run the entry after the close). The same mistake is open in each of three places, so the module earns its keep; it is not a pass-through.

Design it twice. Constraints: `finalFocus` must be a pure read; what must happen once (spend the slot, run the entry) happens on an event that comes once (the open, the choice of a row, the end of the close); the File menu (in the Layout) and the dialog it opens (in the Editor) share no parent, so the slot stays module-wide and the Svelte copies keep using it; the three callers differ in who opens them (a menu that Base UI opens, two dialogs that a prop opens).

| | A. A hook that gives each overlay a `Handoff` | B. A plain object per overlay, wired by hand | C. A wrapper for the popup |
|---|---|---|---|
| Interface | `useFocusHandoff(open)` returns `{ opener, opened, pass(to, then?), finalFocus, closed }`; the rules are in `createHandoff` (`handoff.ts`, no framework) | The same `createHandoff()` and no hook: each caller makes it and calls `opened` itself | `<HandoffPopup>` around `Dialog.Popup` and `Menu.Popup`, owning `initialFocus` and `finalFocus` |

| Seam and test surface | One seam, the `Handoff` interface; one adapter to React, so no port is declared. Chosen: A. B is A without its one real adapter, so it keeps the duplication that the deletion test found; C is shallow. The interface, with its invariants: `finalFocus()` answers the element to give the focus to, `false` to leave it where it is, or `null` for Base UI's own return, and answers the same however often it is asked (nothing is spent, moved or run in it); `opened(opener)` runs once per open before the overlay moves the focus (the hook does it in a layout effect on `open`, which runs before the popup mounts) and takes what an earlier overlay left in the slot; `pass(to, then?)` is for the row or entry that opens a dialog: this overlay then answers `false`, `to` is left in the slot for that dialog, and `then` runs once on `closed()`, which the caller wires to `onOpenChangeComplete(false)` (it fires once per close, when the popup unmounts, which in Base UI's code is before the focus manager's cleanup resolves `finalFocus`, so `finalFocus` must not depend on what `closed` does); an entry that throws leaves the handoff clean and the error reaches the caller. Two edges of this change, the first a small change of behaviour: when the remembered element is no longer connected to the page, the dialog now answers `null` (Base UI's own return) where the Export dialog used to call `focus()` on it, which did nothing for a detached element, so the visible result can differ in that case only (`handoff.test.ts` pins it). And the slot is module-wide and emptied by the next overlay of any kind that opens, a React Menu included (every `opened` takes it), not only by the dialog it was left for. Limits, unchanged from before: a slot left by a row whose dialog never opens waits for the next overlay to open and be taken (which one is the rule just given); `ShortcutHint.tsx` still takes the slot directly in its mount effect (it is not a Base UI popup and the effect runs once per mount); the Svelte copies keep `rememberFocus` and `takeFocusBack` with Bits UI's close event.

## 6. State, the canvas and tests

**State.** One hook, `useAppState(select)`, wraps `useSyncExternalStore(subscribe, getSnapshot)` over the engine. Rules from the React reference (react.dev/reference/react/useSyncExternalStore): the snapshot must be immutable and the same value while nothing changed (the engine already guarantees it); `subscribe` is declared outside the component, or it resubscribes at each render; no suspending on a store value. React holds no editor state; `useState` is only for view state that the audit leaves in the page (hover, open menu, a field's draft). Findings T10 (#323) and T11 (#324) (view state with rules) move to the app layer first, which shrinks what React has to hold.

**Pixi canvas.** Mount the existing framework-free canvas from a ref in an effect, as `Canvas.svelte` does today, and keep `camera` as a controlled prop plus a callback. Do not use `@pixi/react` (declarative JSX over Pixi): the scene comes from the app layer as data (`App::scene` through `sceneFromBoxes`) and a second reconciler over it would hold drawing rules twice, against U1. For the record, `@pixi/react` is production-ready, supports React 19 and Pixi 8, and its `useApplication` works only in a child of `<Application>` (its README); one project's changelog mentions turning React strict mode off to avoid problems with it (snippet only, not read in full, so not relied on). Effects must be idempotent anyway, since React's strict mode runs them twice in development.

**Tests.** Unit tests keep `environment: 'node'`: the 21 tests that render with `svelte/server` are rewritten against `renderToStaticMarkup` of `react-dom/server`, a like-for-like change. The 4 tests that scan `.svelte` source text (`ownskeys`, `textedit`, `shortcuts`, `feedback`) are rewritten to scan `.tsx`, or better replaced by the boundary check. Interactive behaviour (focus, keyboard, dialogs, drag) is covered only by the Playwright scripts, run by hand: they stay the check that the new screens match the old ones, and every slice records in its pull request which script ran against which version and the result. Not verified: Testing Library with React 19 under Vitest's jsdom or happy-dom (the pages I found were generic); it is not needed for the first slices and is a question for the slice that first wants a non-SSR unit test.

## 9. Questions for the owner

1. Component library: Base UI (proposed), Radix or React Aria Components. Both pilot steps passed on Base UI, the Dialog family included (section 5, S2), so the evidence points to Base UI; the owner decides.
2. Per-panel switch (`/?react=...`) so one script runs on both versions, or a straight replacement per panel (smaller code, a weaker check that the result matches). S2 built the switch for one panel (`/?react=export`: two small Svelte files, one function and two import lines); it let the pixel check find two differences that a straight replacement would have shipped.
3. Browser scripts in CI. They run by hand today, so the check that the result matches is as strong as the discipline of running them. The scripts that need only the Vite dev server (`layout-e2e`, `palette-e2e` and `measurer-e2e` per `AGENTS.md`; `states-e2e` is the same, checked 25 Nov 2026) could run in the nightly first. Not decided here.
4. A stop on new `.svelte` files once S0 is merged (recommended).
5. Whether the audit moves (#319 to #323) strictly come first, as the table assumes, or panel by panel in parallel with the port.
6. Accessibility lint: `eslint-plugin-jsx-a11y` needs `axe-core` (MPL-2.0) and `language-subtag-registry` (CC0-1.0), neither on the allowed set of `npm run licences`, and it declares ESLint up to 9. Allow the two licences for development tools, find another check, or keep the review checklist alone. Likewise `eslint-plugin-react-hooks` 7.x needs `caniuse-lite` (CC-BY-4.0) through Babel; S0 uses 5.2.0 until then.
7. The lower-priority rules of the TypeScript front end (T7 to T9 and T11 to T17 of the audit, issue #324): which move into `meldframe-app` before the slices that port them, and which stay as presentation, among them the camera and the pointer state machine (T15). The note `docs/front-end-rules-decisions.md` has a recommendation, a cost in slices and a question for each.
8. Tab in the bind picker (slice S5). Bits UI traps Tab inside the popover; Base UI's non-modal popover does not, and Tab from the last row closed it. The copy keeps the trap with a small key handler of its own (`BindPicker.tsx`), so the two copies behave alike, and that is how it ships unless the owner decides otherwise. Owner decision needed: keep the handler, or take the library's behaviour (no trap; its own trap needs a `Popover.Close` inside the popup, which is a hidden Tab stop).

## 10. Risks

- Two frameworks in one bundle until S13 (size and two focus and portal systems). Mitigation: islands are leaves, dialogs portal to the page root with one stacking context, and the pilot checks focus return.
- The 19 `untrack` calls and 23 effects were written for Svelte's dependency tracking; each needs a ref or a stable callback in React, and the 25 `tick()` focus handoffs become effects or `flushSync`. Reviewed one slice at a time against the script that covers it.
- Behaviour differences between Bits and Base UI (outside click, Escape, focus return, tooltip delay: today one provider with 400 ms). Covered by `states-e2e`, `export-e2e` and `palette-e2e`.
- The migration costs a rewrite of the chrome with no change a person sees (ADR-0026, Risks). This plan keeps each step shippable and reversible until S12.
