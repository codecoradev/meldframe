# Variables are imported from CSS text by a pure parser, and a long import is written in parts of one atomic batch each

E3.4 asks for an import of CSS custom properties and Tailwind v4 `@theme` text into collections, modes and aliases, an agent tool `import_tokens` and a real design system as the test corpus. This records the choices that are hard to change once files hold what an import made.

## Decision

- **A text parser, no CSS engine.** The feature crate `variables-import` (kind `feature`, portable) reads the text with a scanner of its own: blocks, declarations, strings and comments, in one pass. It never opens or runs anything: `@import` and `url()` are reported as skipped and are not followed; `calc()`, `clamp()`, `min()`, `max()`, `color-mix()`, `light-dark()` and `env()` are not evaluated and the variable is skipped. Bounds: 256 KiB of text (`E_IMPORT_TOO_LARGE`), 16 levels of nesting (a deeper block is skipped with a loop, not a recursion), 20,000 custom properties kept, 1,000 bytes of value, and the file limits of E3.3 (32 collections, 16 modes, 5,000 variables, the name and id lengths, 100,000 as the largest number). A report lists at most 200 lines and 32 KiB of text (a message is cut to 240 characters, a name to 80, and control and bidi characters are dropped from everything the text puts in it), notes about the whole import come first and count in the 200, and the rest is counted as omitted. What a scan keeps of the rule a property came from is one label of at most 80 characters, kept once, never the selector list.
- **Where a custom property counts.** Only inside `@theme` (all its forms) or a rule on the root. A rule is a mode rule when its selector is `:root`, `html`, `:host`, `body`, `.light` or `[data-*=light]` (the default mode) or `.dark`, `[data-*=dark]`, optionally after `:root` or `html` or with a trailing ` *` (the dark mode), or a plain `(prefers-color-scheme: dark)` query (alone, or after `screen and` or `all and`) around a root rule; a query that names the scheme in another form (negated, compound, another value) is skipped with `media_query_skipped`; a list sets every mode its selectors name. Any other rule (`.card`) is skipped with its selector in the report, so a component's local property is never taken for a variable. `@layer` is transparent; every other at-rule is skipped whole.
- **Collections and modes.** `@theme` variables go to the collection `theme` (id `col-theme`, one mode `default`). Root properties go to `root` (id `col-root`) with the mode `light` and, when a dark rule sets any variable, the mode `dark`. The model keeps no selector for a mode (`Mode` is an id and a name), so the report names the selector the dark mode was read from and the export picks its own. A variable with no dark value takes its light value (reported once); one that only a dark rule sets is skipped, because a variable needs a default value. A name declared in both sections is imported once, from the section where it first appeared.
- **Aliases.** A value that is exactly `var(--x)` is an alias of the variable made from `--x`, in the same or the other collection; a fallback (`var(--x, 4px)`) is dropped and reported. The type of an alias is its target's. An alias whose target was not imported, a cycle, a chain of more than 16 steps, or values of two types in one variable skips the variable and everything that points at it. The commands come out in an order in which each can be applied (collections first, an alias after its target), whatever the order of the text.
- **Names and ids.** A variable name is the property without `--`, lowercased, each run of other characters one hyphen; in `@theme` a Tailwind namespace (`color`, `spacing`, `radius`, `shadow`, `text`, `font`, `leading`, `tracking`, `breakpoint`, `container`, `blur`, `ease`, `animate` and so on) is split off by one slash, so `--color-brand-500` is `color/brand-500`. A name that changed is reported, and two that become one are not both imported. Ids are `var-<collection>-<name>` (slashes as hyphens; over 64 characters, cut with a hash), so the same text gives the same commands and ids.
- **Values.** A hex colour is kept as written. `rgb()`, `hsl()`, `oklch()`, `oklab()`, the 19 keywords of the table and shadcn's bare HSL triplet (`0 0% 100%`) become hex, each with a line in the report; an `oklch` colour outside sRGB is clamped channel by channel and reported as `clipped`, not as an exact conversion; alpha below 1 is an eight-digit hex. `px` and bare numbers are numbers; `rem` is 16 times the number and reported. Everything else (strings, fonts, shadows, easing, other units, `color()`, `lab()`, `hwb()`) is skipped by name with a code; the model has no string, shadow or wide-gamut colour type yet (ADR-0017), and nothing is stored as a guess.
- **The tool.** `import_tokens` (Change tier; the name is the epic's, the file calls what it makes variables) takes `file`, `css`, an idempotency key, `part` and `dryRun`, and answers with the report. The commands are written with `Shared::submit_ops`, the handler every transport ends in, so the gate, the quota, the limits and the atomic dry run are those of `apply_commands`; they are ordinary variable commands, so undo and revert treat them as they treat the same commands from anywhere else. The op of command `i` has the key `{idempotencyKey}:{digest}:{i}`, where the digest is 48 bits of a hash of the text: a retry writes nothing twice, and the same key with other text is another call (its first part is refused as `E_DUPLICATE_ID`, never replayed). The tool is served only under the `Auto` policy.
- **Parts.** A call writes at most 100 commands (the batch limit of the gate). An import of more is cut into parts of 100 commands in the order of the plan, and a call names the part it writes (`part`, from 1; the answer says `parts`). The plan depends on the text alone, never on the file, so the same text cuts the same way however many parts were written; each part is atomic, the import as a whole is not, and a part sent before the one it depends on is refused whole (`E_COLLECTION_NOT_FOUND` or `E_VARIABLE_NOT_FOUND`) and writes nothing. The keys count commands over the whole import, so no two parts share a key. A bigger batch limit for this one tool was not taken: the limit belongs to the gate, and a workspace's file would then hold more in one op than any other path writes.
- **Quota.** Every command is an op against the workspace's 6,000 ops a minute, so an import of 5,000 variables is about 83% of a minute, and a part the quota refuses writes nothing: the parts before it stay, and the same call sent again later replays them and writes the rest. The index in an error counts commands over the whole import, not in the part.
- **The report in parts.** The answer to part 1 and to a dry run carries the whole report; later parts carry its counts and point at part 1 for the entries. The 32 KiB cap is on the entries; the JSON around them is more.
- **Add, do not update.** The import only adds. Text whose ids the file already holds is refused whole as `E_DUPLICATE_ID` (with a hint), so a second import of the same text is a refusal and not a duplicate. To finish an import that stopped part way, the same call is sent again with the same key and text; to change what a file holds, `apply_commands` is used. Matching by name to update values, add modes and never delete (design note 8.3) is open.

## Considered options

- A CSS crate (`lightningcss` and the like): rejected. It brings a large dependency tree, its licence (MPL-2.0, as `AGENTS.md` notes for its npm package) is not on the allow list of `deny.toml`, it reads `@import` and `url()` by design, has to build for WASM, and parses far more than a theme needs; the scanner is about 400 lines, bounded by construction and exercised by tests on hostile text (every prefix of a theme, broken input, a million nested blocks).
- The agent resolves the config and sends JSON: kept as the way for `tailwind.config.js` (the agent resolves it and sends the CSS or the variable commands); not built here.
- One batch of any size for an import: rejected (see Parts).
- Colours stored as `oklch` text: not possible with the E3.3 model (hex only); the clamp is reported and a wider colour type is an additive change of ADR-0017.

## Consequences

- A second CSS file imported into the same file fails with `E_DUPLICATE_ID`: the collections are always `col-root` and `col-theme`, so what two files define has to be joined into one text. Merging into an existing collection comes with the update of an import (open).
- `hsl(120, 50, 50)`, the old comma form with bare numbers, is read as percent points although browsers refuse it; a stricter reading is a later choice.
- A media query is read with its white space made single and none inside the parentheses or around the colon, so a comment between words is white space and `screenand(...)` is not `screen and (...)`; other forms are skipped as `media_query_skipped`.
- A rule for the light mode (`.light`, `[data-theme=light]`) inside a dark query is skipped as `light_in_dark_media`; a rule on the root there is the dark mode. A negative chroma in `oklch()` is clamped to 0 as CSS does. Text that is not text (control, format, variation-selector and tag characters) is dropped from everything a report echoes. What a scan leaves out is kept for the first 1,000 rules and counted after that.

- The corpus of the tests is a representative theme written for them (`meldframe-variables-import-tests/tests/fixtures/representative-theme.css`), not the owner's Uteke Cloud theme; the real file can be put beside it and run with the same tests.
- Import then export does not give the text back: the export names a variable `--<collection>-<name>`, the import reads `--<name>`; the round trip of the design note (section 10, item 6) is open.
- A dark mode picked by a `@custom-variant` or a config (`darkMode`) is not read; the selectors above are.
- Bindings of layout fields, gradient stops and text, strings and shadows as variables stay open with ADR-0017.
