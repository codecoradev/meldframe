# People sign in through Gatehouse into server-side sessions, agents connect through OAuth grants checked on every call, and the principal carries a kind

M2 replaces development tokens with real identity: E2.1 (a person signs in), E2.2 (Claude Code connects to MCP through OAuth) and what is left of E2.4 (a grant the person can revoke, a consent that lists the risk tiers, and a person who can answer an approval). ADR-0006 chose Gatehouse and ADR-0012 chose OAuth grants; neither says how a sign-in session lives, how a revoked grant stops a call, how the server tells a person from an agent, or who may call `Server::decide_approval`. This records those choices, which are hard to change once files, actors, grants and sessions exist. It was written from the code, not from the docs: where the two disagree, the code is quoted under Consequences. The design was checked against a sibling product that already signs people in with Gatehouse and serves an OAuth-protected MCP endpoint (patterns only, in the table under Considered options) and against what the Gatehouse documentation and tests state it provides today; what could not be confirmed is listed under "What Gatehouse must provide". ADR-0021 (activity lanes, merged) takes migration 0007 and shares several crate ceilings with this ADR; the joint budget is under Consequences. "Client" in this text always means an OAuth client (the web editor is the "web editor"); the glossary's _Avoid_ for the front end cannot be applied to a protocol term.

## Decision

- **Three parties, kept apart.** Gatehouse is the authorization server and the identity provider: it signs people in, registers OAuth clients, shows consent, issues and revokes tokens. Meldframe is an OIDC relying party for people and an OAuth resource server for agents (RFC 9728 metadata, bearer tokens). Meldframe never mints a credential that a person or an agent could copy: the only secrets it issues are opaque sign-in session ids in a cookie the page cannot read. A token Gatehouse issued to an agent is never forwarded to another service (no passthrough). The server keeps its identity state in one process; the in-memory index and the revocation bus below assume a single server process (several would need the table read on every call or a notification channel, a later change).
- **How a person signs in.** The server runs the authorization code flow with PKCE S256 as a confidential client. `GET /v1/auth/login?return_to=` first ignores and clears any session cookie it received and ends that session (no fixation), then makes a login attempt (state, nonce and PKCE verifier, 256 bits each, kept in the database, living 10 minutes), sets the login cookie and redirects with `scope=openid profile` (no `offline_access`: the web session needs no refresh token) and the exact registered `redirect_uri`. The login cookie is `__Host-mf_login=<attempt id>; Secure; HttpOnly; SameSite=Lax; Path=/; Max-Age=600`: Lax, not Strict, because the callback is a cross-site top-level GET and Strict would drop it; it binds the attempt to the browser that started it and is cleared at the callback. `GET /v1/auth/callback` deletes the attempt in one statement (single use), compares `state` in constant time, requires `iss` to equal the configured issuer when the response carries it (RFC 9207), exchanges the code with the client secret and the verifier, and verifies the ID token itself (the JWT rules below, plus `aud` equal to the client id, `azp` when `aud` has several entries, `nonce`). The Gatehouse access token is dropped at once; the server keeps the subject, the Gatehouse session id (`sid`) and a display name. Every failure redirects to `/?login_error=<code>` with one of eight stable codes (`cancelled`, `expired`, `state`, `issuer`, `exchange`, `token`, `signup_closed`, `unavailable`) and no detail. Responses of the callback, of every `Set-Cookie`, of `GET /v1/session` and of the approvals routes carry `Cache-Control: no-store`, and the callback and login redirects `Referrer-Policy: no-referrer`.
- **Where the session lives, and why a cookie.** A sign-in session is a row (`sign_in_sessions`) and a cookie `__Host-mf_sid` of 32 random bytes in base64url; the row keeps only the SHA-256 of the id, so a leaked table gives no cookie. Attributes: `Secure; HttpOnly; SameSite=Lax; Path=/`, no `Domain`, `Max-Age` equal to the absolute limit. The page cannot read the id, so XSS cannot copy it (it can still act in the page, see the editor paragraph). A browser cannot set `Authorization` on a WebSocket and a token in a query string lands in logs, so the cookie is the one credential the web editor and its sockets share. Limits (working defaults, the owner's to change): **8 hours idle and 24 hours absolute** (not 7 days: Gatehouse delivers a back-channel logout once and never retries, so a missed delivery after a ban must not leave a session open for a week; a person signs in again through Gatehouse, which is silent while its own session lives), at most 10 sessions per person (the oldest ends when an 11th starts). Activity that resets the idle timer: any authenticated HTTP request and every WebSocket frame or poll of a socket bound to the session, written to `last_seen` at most once a minute, so an editor open for 9 hours does not end with 4401 mid-edit while a closed tab ends at 8. Where the public URL is plain HTTP on loopback (development) the cookie is named `mf_sid` without `Secure`, and nowhere else.
- **CSRF and cross-site sockets.** A request that authenticates by cookie and is not `GET` or `HEAD`, and every WebSocket upgrade, must carry an `Origin` equal to the configured public origin; with no `Origin`, `Sec-Fetch-Site: same-origin` is required; anything else is `403 origin_not_allowed` before the body is read. A request with an `Authorization` header is judged by the header alone and the cookie is ignored. The check is a pure function in `meldframe-auth` applied once where credentials are read. It is new: today nothing in the server checks `Origin` (`mcp/mod.rs` says so, because there were no cookies), and a cookie-authenticated `/v1/ws` and `/v1/live/{file}` without it would be open to cross-site WebSocket hijacking. `/mcp` never accepts the cookie.
- **The editor is served from the API origin, with a policy.** The cookie is `__Host-` and the `Origin` check is exact, so the web editor and the API share one origin. Nothing in the server serves static files today. A new crate `meldframe-http-web` (bin) serves `apps/web/dist` from the server with `Content-Security-Policy: default-src 'self'; script-src 'self' 'wasm-unsafe-eval'; connect-src 'self'; object-src 'none'; base-uri 'none'; frame-ancestors 'none'` (the style rule is settled against the real build; any `unsafe-inline` for styles is stated in that slice) and `X-Content-Type-Options: nosniff`; behind a reverse proxy the same headers are the proxy's job and the ADR's requirement. This matters beyond hygiene: agent-written text (names, notes) is shown in the editor, and a same-origin script could call the approvals route as the person and approve its own agent's delete. The mitigations are the CSP, Svelte's escaping, a lint that forbids `{@html` in every front-end package, canvas text drawn by Pixi and not as HTML, and an approvals screen that names the file, the kind and the node. What remains is stated under risks.
- **Logout and revocation end the sockets.** `POST /v1/session/logout` (cookie, CSRF-checked; `{"all": true}` ends every session of the person) marks the row ended, removes it from the in-memory index and publishes its id on a revocation bus; every open `/v1/ws` and `/v1/live` socket of that session closes with WebSocket code 4401 and reason `session_ended` within one live poll (250 ms by default). Sockets also re-check their session on every frame and poll, so a missed bus message cannot keep one open. Gatehouse's back-channel logout (`POST /v1/auth/backchannel-logout`) is accepted only when the `logout_token` passes every rule: RS256 signature against the JWKS (the JWT rules below), `iss` equal to the configured issuer, `aud` equal to the web client id, `iat` within the leeway, `typ` `logout+jwt`, an `events` claim holding the back-channel member, no `nonce`, `exp` in the future and at most 120 seconds after `iat`, `jti` never seen (remembered for `exp` plus the leeway), and at least one of `sub` and `sid`. It then ends the sessions with that `sid`; **fail closed**: if no session matches the `sid` (or the session's `idp_sid` is null) it ends every session of that `sub`. Signing out of Gatehouse does not end an agent grant: an agent keeps working while the person is away, and its grant ends only on the Connected agents screen. After a ban at Gatehouse an agent's access token therefore works until it expires (about one hour) unless the grant is revoked in Meldframe, and a web session works until the back-channel logout arrives or the 24 hour limit.
- **The principal has a kind.** `Principal` becomes `{ workspace, actor, kind, tiers }` and moves to a new core crate `meldframe-principal`, re-exported from `meldframe-host` (which is 15 lines under its ceiling and would not fit the new fields). `workspace` and `actor` stay public fields (a reader, as today); `kind` (`Person` or `Agent`) and `tiers` (the risk tiers the credential may reach: all three for a person, the grant's cap for an agent) are private with getters, so no struct literal outside the crate builds one. **The kind is decided by the kind of credential and nothing else**: a valid sign-in cookie is a `Person`; a valid OAuth access token is an `Agent`, even when the same human is behind both; never an actor string, a claim the caller chose or a request field. `Principal::new(workspace, actor)` keeps its signature and builds an `Agent` with all tiers (79 call sites in 47 files keep compiling, and anything not marked a person fails closed). A `Person` is built only by a sealed constructor that `meldframe-auth` calls when it has verified a cookie (cargo feature `mint` of `meldframe-principal`, enabled by `meldframe-auth` alone); `Principal::person` exists only behind the feature `test-support`, which test crates enable. Rust cannot seal a public constructor against another crate, so this is held by a CI check on the feature graph (`cargo tree -e features -i meldframe-principal` must show `mint` enabled only by `meldframe-auth` and `test-support` only by `[dev-dependencies]`), not by the compiler alone; it makes a skipped identity check visible in review instead of invisible. A route lists the credentials it accepts: `/mcp` only agent bearer tokens; `/v1/approvals`, `/v1/grants` and `/v1/session` only the cookie; REST tools, `/v1/ws`, `/v1/live`, snapshots and assets both. An `on_behalf_of` field is left out until a rule reads it (the grant table already names the person).
- **How the actor is derived.** A person is `person:<person id>` with Meldframe's own id (`per_` and 20 base32 characters), never the email and never the raw Gatehouse subject, so a change of provider rewrites no history and no actor string holds personal data. An agent is `agent:<grant id>` (`gr_` and 20 base32 characters): one grant is one actor and one lane. A revoked grant is never reused (a new grant is a new actor, so old attribution, per-actor undo and idempotency keys cannot be resurrected), the per-principal rate budget and in-flight slots are per grant, and the call log, batches and activity lanes name the grant. Two chats of one Claude Code installation share one grant, so one actor and one lane; this answers question 1 of ADR-0021 as "one grant, one lane" and the Connected agents screen says so. The development token's actor stays whatever its entry says.
- **ADR-0021's reviewer rule changes once the kind exists.** ADR-0021 denies by default and lets only actors named in `MELDFRAME_REVIEWERS` set a review, because `Principal` has no kind and an actor prefix cannot be trusted. With this ADR the rule is: the principal's kind is `Person`. ADR-0021 and the epic word the rule as "owner"; M2 has one person per workspace and no roles, so the two coincide, and the wording is corrected in slice 14 (a role field arrives with multi-member workspaces and joins the rule then). `MELDFRAME_REVIEWERS` is not deleted at once: it moves into the development-token adapter, where an entry of `MELDFRAME_DEV_TOKENS` is an `Agent` unless its actor is listed, and it has no meaning for cookie sessions or OAuth tokens.
- **A person may delete in the editor; an agent is asked.** The default policy ignores the principal today (`default_policy(tier)`), so Delete is Ask for everyone; with one person per workspace and the rule that an actor cannot answer its own request, a lone person deleting a frame in the editor would open an approval only they could answer, and could not answer it: a deadlock until expiry. E2.4 says an agent that deletes a whole frame or a large subtree is asked first, and the editor has undo, so the policy closure returns `Auto` for a `Person` at every tier and keeps `Ask` for Delete for an `Agent` (and the caps below). The own-request rule stays for agents (an agent cannot answer its own ask; it cannot answer at all). A person's Delete is logged like any call and is revertible.
- **Workspaces and people.** New tables `people` (id, issuer and subject, display name, `disabled_at_ms`), `workspaces` (id, name, owner) and `memberships` (workspace, person, role), unique on `(issuer, subject)`, not on email. The first sign-in of an allowed subject creates the person and one personal workspace in one transaction. **Sign-up is an allow-list by default**: `MELDFRAME_SIGNUP=allowlist` (the default) admits only the Gatehouse subjects in `MELDFRAME_ALLOWED_SUBJECTS` (comma separated, at most 50, read at start; the first owner is simply the first entry) or in the table `allowed_subjects`; an empty list admits nobody and the server says so at start. A refused sign-in is `signup_closed` and records the subject (an opaque id) in `auth_events`, so the owner can read it and add it. `MELDFRAME_SIGNUP=open` admits anyone Gatehouse admits, capped by `MELDFRAME_MAX_PEOPLE` (default 50). The email is not stored; the `name` claim is kept, at most 128 characters after control and format characters are stripped, else `Person` and four characters of the id. In M2 a workspace has one person (no invitations, no roles beyond ownership), so "another workspace cannot see that file" is a test between two people. The session row carries the workspace and the principal's workspace comes only from there (ADR-0006: never from the request). Disabling a person (`IdentityStore::disable`, reached through a subcommand of the server binary, `meldframe-server admin disable-person <id>`) ends their sessions, revokes their grants and stops sign-in; an erasure request that Gatehouse passes on removes the display name and the subject from `people` (a tombstone keeps the id, so actor strings in the log stay valid and hold no personal data) and the subject from `auth_events`; ops, batches and calls keep only opaque ids.
- **How Claude Code connects.** `/mcp` is an OAuth protected resource per the MCP authorization specification. An unauthenticated or refused call is `401` with `WWW-Authenticate: Bearer resource_metadata="<public>/.well-known/oauth-protected-resource/mcp"` (plus a `scope` parameter when tier scopes are on; today `Reply` always sends the bare `Bearer`). The server serves RFC 9728 metadata at the path-inserted URL and at the root form: `resource` is `<public>/mcp` (canonical, no trailing slash), `authorization_servers` is the Gatehouse issuer, `bearer_methods_supported` is `["header"]`, `scopes_supported` lists `offline_access` (without it a client gets a one-hour token and no refresh) and, when tier scopes are on, the three tier strings. A client then reads Gatehouse's own metadata (RFC 8414 or OIDC discovery; the document's `issuer` must equal the configured issuer), registers, and runs the code flow with PKCE and an RFC 8707 `resource` parameter, so Gatehouse issues an RS256 JWT access token whose `aud` is the resource. The server mirrors the authorization server metadata at its own origin only if a real client turns out to ask there.
- **Client registration (to be settled with the owner and a real Claude Code).** The MCP client is a public client: authorization code with PKCE S256, `token_endpoint_auth_method` `none`, a loopback redirect, refresh tokens. Meldframe is indifferent to how it gets a client id: it sees a `client_id` in the token, derives a grant key from it, and never registers or trusts a client itself. The routes, from Gatehouse's documentation: (a) a public client the owner pre-registers at Gatehouse, which Claude Code is told to use; its redirect URI is an exact-string match, so a loopback redirect needs a fixed port, and whether Claude Code accepts a fixed callback port and a preset client id must be checked; (b) Gatehouse's dynamic registration (RFC 7591), which needs a logged-in person, and Claude Code registers without one, so this route needs the anonymous registration option, which Gatehouse's own runbook calls a deliberate, risky opt-in, gives such clients only `openid profile email`, and marks them self-registered on the consent screen; (c) Gatehouse's client id metadata document path, built for one allowed origin and possibly the zero-setup route if Claude Code uses it (unconfirmed). Consent is never skipped. The questionnaire's earlier working default ("public client with PKCE and dynamic client registration", read and write scopes) is one the owner may replace; this ADR proposes replacing it by the paragraphs above and below (decision 26 keeps a default until the owner overrides).
- **Risk tiers on the wire, behind a switch.** The tiers can travel as three OAuth scopes, `meldframe:read`, `meldframe:change`, `meldframe:delete` (the glossary's _Avoid_ of "scope" is about the tier concept: the strings are only the wire form of Read, Change and Delete, and the code, the screens and the tool text say tier). They are independent, not nested. Gatehouse serves only `openid profile email offline_access` today, and a request for a scope it does not serve fails at authorize with `invalid_scope`, so advertising them early would break every connection. `MELDFRAME_TIER_SCOPES` has two values. `off` (the default): the metadata and the challenge advertise no tier scopes and tokens carry none; the tiers of a grant come only from the cap the person sets (below). `required`: the metadata advertises them, a token without `meldframe:read` is refused `401 invalid_token`, and effective tiers are the token's scopes intersected with the cap. The scope says how far a grant may reach; the policy per tier (Auto, Ask, Deny, ADR-0010) still decides each call inside that reach. A call above the effective tiers is refused by the gate as `forbidden` (HTTP 403; on `/mcp`, with `required`, `WWW-Authenticate: Bearer error="insufficient_scope", scope="meldframe:delete"`). The ceiling has no home today: the server builds its gate with `approvals.gate(|_, tier| default_policy(tier))` (`apps/server/src/lib.rs`), which ignores the principal, and `check_tool` reads a read tool's policy without one. The policy closure already receives the principal, so it reads `tiers` and `kind` (this paragraph and the person paragraph above are one closure); `check_tool` gets the principal too. The closure lives in a new file of a new crate (below), not in `lib.rs`. E2.4's consent line ("the consent screen lists the risk tiers") stays open until Gatehouse serves the scopes and the owner approves the wording; it needs external work that should start now (owner question 5).
- **Consent and the grant the person confirms.** The OAuth consent screen is Gatehouse's. It never names Meldframe's tiers (until the scopes exist) and a person can approve it for a client id they do not recognise. So **a grant is created `pending`** by the first valid token of a client for a person who has signed in, and every call of a pending grant is refused `403 grant_pending` until the person approves it on the Connected agents screen. That screen shows the client's label, when it first connected, the three tier lines (proposed wording, the owner's to approve: "See your designs (Read)", "Create and change designs; changes can be reverted (Change)", "Delete frames and large parts of a design; you are asked first unless you change that in Meldframe (Delete)") and lets the person pick the cap, **Read only by default**; Approve makes the grant `active`. The server holds no wording (standard U5). This is also where a person allows an agent again after a revoke.
- **Agent tokens: short-lived, checked on every call.** The server accepts only a resource-bound RS256 JWT, with these rules (a hostile corpus tests each): the header `alg` is `RS256` (`none`, HS* and everything else are refused); `kid` is present and found in the cached JWKS, and the key comes only from that JWKS, never from a header: a token with `jku`, `jwk`, `x5u`, `x5c` or `crit` in its header is refused; the key is RSA with a modulus of 2048 to 4096 bits, its `use` (when present) is `sig` and its `alg` (when present) is `RS256`; `typ` is absent or `at+jwt` or `JWT`; `iss` equals the configured issuer; `aud` contains the resource; `exp`, `nbf` and `iat` are checked with a leeway of 60 seconds; `exp - iat` is at most 24 hours (Gatehouse's default is one hour; a longer life is refused because NFR-6 says short-lived; slice 0 confirms the claims this depends on); `sub`, `client_id` (or `azp`) and `scope` (at most 512 bytes) are present. Verification is offline against a cached JWKS (fresh 1 hour, served stale up to 24 hours when Gatehouse cannot be reached, one refetch per minute at most for an unknown `kid`). A legitimate key rotation that lands inside that minute answers `503 identity_unavailable` for its first tokens, which is accepted: the client retries. Introspection (RFC 7662) is kept only as an off-by-default fallback for opaque tokens; a token without `resource` is opaque and is refused `401 invalid_token`. After the token passes, the call looks up the grant by `(person of sub, client)` in an in-memory index written through to the database. A grant that is missing, `pending`, revoked or whose person has not signed in refuses the call (`grant_pending`, `grant_revoked`, `grant_requires_sign_in`). **No JWT can be revoked at Gatehouse before `exp`, so the grant table is the revocation**: it is read on every call and never cached for a period.
- **Grants.** Fields: id, person, workspace (the person's), a hash of the client id as the lookup key, **the full client id** (at most 2,048 bytes; it is public, a registered id or a metadata-document URL, and Gatehouse's revoke needs it in plain text), a label of at most 128 characters (the client's name, else the first 32 characters of the id), `state` (`pending`, `active`, `revoked`), `tier_cap`, `created_at_ms`, `last_used_ms` (once a minute), `revoked_at_ms`, `idp_revoke` (`none`, `confirmed`, `failed`) and the retry state. A token for a subject with no person is refused `403 grant_requires_sign_in`: an agent path never creates a person or a workspace. At most 20 active or pending grants per person and 100 per workspace; one more is `grant_limit`.
- **Revoking a grant ends it on the next call, and stays ended.** `DELETE /v1/grants/{id}` (cookie only, CSRF-checked) sets `revoked_at` in the database first and then in the index in one step, publishes the grant id on the revocation bus (its open sockets close with 4401), expires its pending approvals as denied, writes an `auth_events` row, and asks Gatehouse to revoke the person's grant for that client (a server-to-server call with `{user_sub, client_id}`, retried with backoff for up to 24 hours). From then every call with any token of that grant is `401 grant_revoked`. **`iat` cannot tell a refresh from a consent**: a refresh token mints an access token with a later `iat` without any new consent, so "a token issued after the revoke" proves nothing. The deny therefore stays for the pair (person, client): it is lifted only (a) when Gatehouse has answered `revoked: true` (the refresh tokens are gone), after which a token whose `iat` is later than `revoked_at` comes from a new consent and makes a new `pending` grant, while a token minted before `revoked_at` stays refused; or (b) when the person presses Allow again on the Connected agents screen, which is an explicit act and creates a new active grant with a cap they choose. A Gatehouse answer of `revoked: false`, no answer, 4xx or an outage leaves the deny in place for good (state `failed` is shown on the screen with a retry button). If the database cannot record a revocation the route answers `503` and does not claim success.
- **Approvals reach the person.** Two routes, cookie only, `Person` only: `GET /v1/approvals` (the pending approvals of the principal's workspace, oldest first, at most 100, each `{id, actor, file, kind, nodeId, state, createdAt, expiresAt}`, never a command, name or text) and `POST /v1/approvals/{id}/decision` with `{"decision": "approve" | "deny"}` (at most 64 bytes, unknown fields refused). They live in a new crate `meldframe-http-approvals` over a small `Approver` trait that `SharedServer` implements in `apps/server/src/approval.rs`. The editor lists them in the right panel (E5.1's activity lane is the later home) and polls every 5 seconds while the panel is open and once after any `approval_required` reply; a push as an ephemeral frame (ADR-0009) is a follow-up. A request nobody answers expires to denied after 15 minutes (G5, U7); the panel offers Approve once and Deny only, never "always" (U7). With the paragraph on policy above, an approval exists only for an agent's Delete.
- **How `decide_approval` is protected.** (1) The route accepts only the sign-in cookie: a bearer token, an agent's included, is `403 person_required`, and `/mcp` has no such tool. (2) `Server::decide_approval` takes an `Owner<'_>`, a borrowed view that `Principal::as_owner()` builds only for a `Person` (M2: every person in their own workspace); this turns the check into a type the signature names, and a compile-fail test shows a plain `Principal` cannot be passed. It is bounded by the sealed constructor and the CI feature check above, not absolute. (3) The CSRF and `Origin` check. (4) `Approvals::answer` already treats another workspace's id as unknown and refuses the actor's own request. (5) One answer per approval; a second is `409`. (6) The per-principal bucket and the existing caps (20 open per actor, 100 per workspace). (7) The answer is a `decide_approval` entry in the call log, as today, now with the person's actor.
- **Release builds.** The Cargo feature `dev-tokens` is opt-in: it is not in `default`, and only the development profile of `apps/server` (`just dev`, `just dev-server`, `tools/dev-smoke.sh`) and the test crates enable it. A release build is made without it and contains no development-token path. A build that has the feature and the release profile refuses to start with `DevTokens` configured, with no override: `MELDFRAME_ALLOW_DEV_TOKENS` is removed in the slice that adds this refusal and not before, so the override and its replacement never coexist or both vanish. CI proves the absence instead of a Rust test that cannot build both variants: a release job builds `meldframe-server` without the feature and checks `cargo tree -e features -i meldframe-auth` shows no `dev-tokens` and the binary holds no `MELDFRAME_DEV_TOKENS` string. With the feature off, a set `MELDFRAME_DEV_TOKENS` is a start-up error naming the variable. A server with neither the feature nor an OIDC configuration does not start; it is never open. Development tokens and OIDC coexist only in a development build: both authenticators are tried (a bearer matching a dev token first), `check_dev_listen` still demands a loopback listener unless `MELDFRAME_ALLOW_DEV_PUBLIC=1`, and a dev token's kind is `Agent` unless listed. Today `serve()` insists on `MELDFRAME_DEV_TOKENS` (`apps/server/src/main.rs`), so the server cannot start without them.
- **Real sign-in in `just web`.** `apps/web/dev/proxy-guard.ts` and `vite.config.ts` inject the dev token on every `/v1` call and own the `Authorization` header. A mode `MELDFRAME_WEB_SIGNIN=1` makes the proxy pass cookies and `Set-Cookie` through unchanged, stop injecting the token, and treat the Vite origin as the public origin for the `Origin` check; the registered redirect URI is then the Vite origin's callback. The proxy guard and its test move out of `apps/web` first (a pure move to a package, with the size entry lowered in the same pull request), because `apps/web` is over its ceiling and may only shrink; the edits land there.
- **Storage.** Migration numbers follow ADR-0021's 0007 and are taken from the next free number when each slice lands. `0008_identity.sql`: `people`, `workspaces`, `memberships`, `allowed_subjects`, `sign_in_sessions` (`id_hash` primary key, person, workspace, `idp_sid`, `created_at_ms`, `last_seen_ms`, `ended_at_ms`, `end_reason`), `login_attempts`, `backchannel_jti`, and `agent_grants` (grants are never memory-only, so they exist with the first slice that creates one). `0009_auth_audit.sql`: `auth_events` (kind, person, workspace, grant, outcome code, `at_ms`; no address, token, email or name; the subject only on a refused sign-in) and a nullable `grant_id` on `calls` and in `CallEntry`, so the call log can say whose agent a call was without holding content. `auth_events` is append-only in the same sense as `calls`: a trigger refuses `UPDATE`; it also refuses `DELETE` except inside the retention job, which sets a transaction-local setting the trigger checks, because rows older than 90 days (the owner's to change) are removed. The same job, hourly, deletes expired login attempts, ended sessions and used jtis. The server has no job runner today; `meldframe-http-oidc` exposes a `Janitor` that `wire(...)` returns and `main.rs` spawns beside the live timer (slice 12). The sqlx migrator in `PgStore` owns the schema; `PgStore` gains a small accessor so a new crate can run queries on its pool and runtime.
- **Keys, clock, replay, rate limits.** The cookie id needs no signing key (random, looked up), so no cookie key rotates. The OAuth client secret comes from `MELDFRAME_OIDC_CLIENT_SECRET` or a file named by `..._FILE`, never argv, never logged, never in an error text; rotating it is a restart (Gatehouse invalidates the old one at once, so there is no overlap to design). Issuer keys rotate at Gatehouse; the JWKS cache handles it. Time: JWT and session checks use the wall clock the server already has (`now()` in `apps/server`), injected as a trait so tests move it; the rate limiter's monotonic clock is not used for them. A leeway of 60 seconds each way covers skew; a server clock further off fails every token and logs `token`, not in the reply. Replay: an authorization code is single use at Gatehouse and the login attempt is deleted on first read; a back-channel `jti` is remembered; an agent token is a bearer credential and not one-time by design, which is why the grant table, the short life and the audience binding are the controls. Rate limits per client address (the existing `client_ok` bucket, then these): login 10 a minute, callback 20, logout 30, back-channel 60; grants and approvals use the per-principal bucket; failed token verifications are remembered briefly by the SHA-256 of the token so a loop of bad bearers costs one verification; at most 1,000 live login attempts and 10 per address (kept in memory, so no address is stored).
- **Audit.** `auth_events` records sign-in, refused sign-in (code), sign-out, back-channel end, grant created, approved, revoked and allowed again, grant refused (`grant_revoked`, `grant_pending`, `grant_requires_sign_in`, `grant_limit`) and Gatehouse revoke outcome. Ids and codes only. The decision on an approval stays in the call log.
- **Bounds on every input.** Cookie value 64 bytes; bearer token 4,096 bytes; ID token and logout token 8 KiB; `state` and `code` 512 bytes; `return_to` a relative path of at most 512 bytes starting with a single `/`, no `//`, no `\`, no control character, else `/`; `login_error` one of eight codes; every Gatehouse response 64 KiB read with a limit, and at most 16 keys in a JWKS; outbound calls https only (loopback http for tests), no redirect followed, 5 second timeout, 10 seconds for a whole callback; `sub` 255 bytes, `client_id` 2,048 bytes, display name and label 128 characters; scope string 512 bytes and at most 16 scopes, unknown scopes ignored; decision body 64 bytes; grant and approval ids must match their format before any lookup; at most 20 grants per person, 10 sessions per person, 1,000 login attempts, 50 allowed subjects at start. A value over a bound is refused with a short stable code and costs no outbound call. Meldframe has no outbound URL that an attacker influences: the issuer is configured, and fetches of client metadata documents and dynamic registrations are Gatehouse's, so no SSRF defence beyond https-only, no-redirect and size limits is built here.
- **Failure modes** (fail closed; unavailable is `503` and retryable, never `401`, so a client does not discard good credentials during an outage). Gatehouse unreachable at login: `login_error=unavailable`, existing sessions unaffected. JWKS unreachable: cached keys (up to 24 hours stale), then `503 identity_unavailable` for tokens with an unknown `kid`. Database unreachable: sessions and grants already in the index keep working until revoked, new sign-ins, grants and revocations answer `503`; a logout always ends the session in memory and clears the cookie even if the row write is retried later. Unknown or bad token: `401 unauthenticated` with the challenge. Revoked grant: `401 grant_revoked`. Pending: `403 grant_pending`. Tier above the grant: `403 forbidden`. A row or claim that is not understood (an unknown tier name in `tier_cap`, a malformed session row) grants nothing extra: only the tiers that parse count and an empty set leaves Read only, as G5 says (if a row cannot be read at all, only Read proceeds).
- **Testing without a live Gatehouse.** (1) Pure crates with table-driven tests and a hostile corpus (algorithm `none`, HS256 signed with the public key as the secret, `jku`, `jwk`, `x5u`, `x5c`, `crit` headers, a modulus of 1,024 and of 8,192 bits, `aud` missing or an array, wrong `iss`, expired, `nbf` in the future, no `kid`, unknown `kid`, a token of 5 MB, duplicate claims, non-UTF-8, a `scope` of 10,000 entries, a discovery document with another `issuer`). Test keys are a small fixed set of RSA keys made once by a documented script and committed as fixtures (marked for the secret scanner, never used outside tests), not generated in every test, which is slow in a debug build. (2) A fake OIDC provider crate, `meldframe-fake-idp` (kind tool, axum): discovery, JWKS with rotation, authorize (signs a scripted person in), token, end-session, back-channel delivery, the grant-revoke endpoint, and switches for every failure (outage, slow, empty 500, wrong issuer, wrong audience, skew). (3) A store contract suite run against the memory adapter and Postgres. (4) A conformance list that runs against the fake always and against a real Gatehouse when `MELDFRAME_IDP_CONTRACT_URL` is set (it prints `SKIPPED` otherwise, as the Postgres tests do). (5) `tools/mutation-check-auth.sh` in the style of the sync mutation check: switch one rule off at a time (the audience check, the deny after a failed revoke, the origin check, the kind check on `decide_approval`, the re-check on an open socket, algorithm pinning, single use of an attempt, the pending state) and fail if the tests still pass. (6) Named tests that must exist: revoke, Gatehouse answers 4xx, the agent refreshes, the call is still `grant_revoked`; a lone person deletes a frame and it is applied; an agent's Delete is `approval_required` and the person's answer admits it once; a pending grant is `grant_pending`; a back-channel token for an unknown `sid` ends all sessions of the `sub`. (7) Browser checks by hand against the real server and the fake provider: sign in, edit, a socket from a wrong origin refused, logout closes the socket, a second person in another workspace cannot read the first person's file. What needs the real Gatehouse and a real Claude Code is listed under "What Gatehouse must provide" and in the last slice.

## Considered options

- **Gatehouse as the authorization server for agents (chosen), Meldframe as an authorization server of its own that delegates login to Gatehouse (rejected).** The second would let Meldframe show its own consent with the tiers and mint its own tokens, but it puts client registration, redirect validation, code and refresh handling and a token endpoint into the product, the largest attack surface of the design and a second implementation of what Gatehouse exists to be (ADR-0006). The cost of the first is that the consent text is Gatehouse's and the tier scopes need a Gatehouse change; the pending-grant step covers the gap meanwhile.
- **Tiers as scopes in Gatehouse (chosen, behind a switch), tiers only in the grant the person confirms (the fallback until Gatehouse ships the scopes).** The fallback meets everything but "the consent screen lists the risk tiers"; it is not accepted as the end state.
- **Verify agent tokens offline as JWTs plus a local grant table (chosen), introspect on every call (rejected as the default).** Introspection adds a round trip and a dependency on the issuer's availability to every call, and a cache of its answers is a revocation delay; offline checking plus a table read on every call makes revocation exact and keeps Gatehouse off the hot path. The price is that the table, not Gatehouse, decides whether a grant lives, which is why a Gatehouse-side revoke is sent as well and is not relied on.
- **A server-side session row and an opaque cookie (chosen), a stateless signed cookie (rejected), a bearer token held by the page (rejected), a one-time ticket for the socket (rejected).** A stateless cookie cannot be revoked per session, so logout cannot end a socket. A token in page memory or storage is readable by any script on the page and cannot ride a WebSocket handshake except in the URL. A ticket avoids the cookie on the upgrade but puts a credential in a URL and still needs the origin check.
- **`SameSite=Lax` with the `Origin` check (chosen), `SameSite=Strict` (rejected), a CSRF token (rejected).** Strict drops the cookie on the redirect back from Gatehouse; the `Origin` check is needed anyway for the socket; a second token adds a header for no gain.
- **Kind from the credential (chosen), kind from the actor prefix (rejected, ADR-0021), kind from a claim (rejected).** A claim in a token is chosen by whoever configured the client, not by the server.
- **One actor per grant (chosen), one actor per person with a label (rejected), one actor per chat (not possible).** A shared actor would let a revoked agent's history be taken over by its replacement and merge the lanes of an agent and the person who runs it.
- **Delete is Auto for a person and Ask for an agent (chosen), Ask for everyone (rejected).** Ask for everyone deadlocks the editor with one person per workspace.
- **Allow-list sign-up by default (chosen), open sign-up with a cap (available), always open (rejected).** A public pre-alpha must not fill its database or hand out workspaces by accident.
- **Pattern by pattern, against the sibling product** (patterns only; names and addresses left out on purpose):

| Sibling pattern | What Meldframe does | Why |
|---|---|---|
| Gatehouse is the authorization server, the product is the resource server | Same | One identity service |
| The MCP resource verifies a bearer by introspection with a short cache and one shared upstream call per token | Verify a resource-bound JWT offline against a cached JWKS and read the grant table on every call; keep the short negative cache for failures; introspection only as an off-by-default fallback | Revocation must not wait on a cache of the issuer's answer |
| Audience bound by RFC 8707 resource | Same, and the same URL is the RFC 9728 resource | The MCP specification requires it |
| A local table of connections is checked on every request and a revoked client is denied at once; the issuer is asked to revoke too; the deny is lifted only after the issuer confirms | Same, and the deny stays until the issuer answers `revoked: true` or the person allows the agent again | A refresh token can mint later tokens, so only a confirmed revoke or an explicit act lifts it |
| Client scopes are the provider's four OIDC scopes; an optional write scope exists, off by default | Three tier scopes behind a switch, a cap the person sets on each grant, the gate reads it | The tiers are the product contract (ADR-0010) and E2.4 wants them in consent |
| A person is found by lower-cased verified email, the subject pinned on first login; unknown people are refused on the MCP path; sign-up is open or allow-listed | Key on `(issuer, subject)`, no email stored, an agent path never creates a person, allow-list by default | Emails can be recycled; less personal data |

| `/mcp` answers 401 with `resource_metadata`; both metadata documents; the issuer's metadata mirrored at its own origin for clients that look there; a CORS allow-list for browser MCP clients | The 401 challenge and RFC 9728 metadata; the mirror only if a real client needs it; no CORS on `/mcp` by default | Claude Code is not a browser |

| Tests: an in-process stub of the authorization server and a real database schema, one test per failure | A fake provider crate, a store contract, a conformance list that can also run against the real service, a mutation check | The fake must be provably faithful and each rule provably necessary |
| An audit row per login | `auth_events` for sign-in, grant and revoke events, 90 day retention | Ids and codes only |

## Consequences

- **What the code says that the docs do not, and what blocks the design.** Each point was read in the source.
  1. `Authenticator::authenticate(&self, token: &str) -> Option<Principal>` (`crates/integrations/meldframe-http/src/auth.rs`) is synchronous and cannot say "unavailable". JWT verification needs a JWKS fetch and the grant table needs the database, so the seam becomes asynchronous and returns an `Identity` or an error. Seven callers go through `Shared::principal` or `authenticate` with `bearer(req.headers())`: `rest.rs:44`, `ws.rs:36`, `mcp/mod.rs:247`, `meldframe-http-live/src/ws.rs:58`, `meldframe-http-snapshot/src/lib.rs:232`, `meldframe-http-capture/src/upload.rs:54`, `meldframe-http-assets/src/lib.rs:220`. Sixteen files in the workspace name `DevTokens` or `Authenticator`, twelve of them tests that import them from `meldframe_http`, which therefore keeps re-exporting both.
  2. Both sockets authenticate once. `meldframe-http/src/ws.rs` and `meldframe-http-live/src/ws.rs` hold the handshake's principal for the life of the connection and have no session id to revoke by, so nothing can end a socket after a revocation today. `meldframe-http-live/src/ws.rs` is exactly 500 lines, so it is split before it changes.
  3. A browser cannot set `Authorization` on a WebSocket; `browserEnv().openSocket` (`packages/web-link/src/shell.ts`) relies on the dev proxy adding the token, and the editor's actor comes from the build (`__ACTOR__`, `apps/web/src/main.ts`). Real sign-in reads it from `GET /v1/session`.
  4. No route checks `Origin` or sets a cookie; nothing in the server serves static files.
  5. `serve()` in `apps/server/src/main.rs` fails without `MELDFRAME_DEV_TOKENS`. The release rule is `!cfg!(debug_assertions)`, a build setting, overridable by `MELDFRAME_ALLOW_DEV_TOKENS`; E2.1's "disabled in release builds" is only partly true.
  6. Per-agent policy is not represented (`meldframe-module/src/tier.rs`), the gate's closure ignores the principal and `check_tool` reads a read tool's policy without one. The tier ceiling and the person-versus-agent rule are new code, not settings.
  7. `Approvals::answer` refuses only the actor's own request; its comment leaves who may answer to "the caller (sign-in, M2)". `Server::decide_approval` takes any `&Principal`. Wired naively to OAuth identities it would let one agent answer another's approval; with Ask for everyone and one person per workspace it would also deadlock the editor (the policy paragraph). Approvals live in memory only; a restart forgets them and the agent's retry asks again.
  8. `Principal` has two public fields and lives in `meldframe-host` (1,985 lines); `Principal::new` has 79 call sites in 47 files and the struct literal appears only in `gate.rs`.
  9. `just dev` and the web default use the actor `agent:dev`; a person-only answer needs the development editor to be a person (listed through the adapter; ADR-0021's slice 7 touches the same lines in `scripts/dev.sh`).
  10. The workspace has no table: it is a string in `files.workspace_id` (migration 0003) and in the principal.
  11. `calls` and `CallEntry` hold the actor but no grant, so "whose agent" is not answerable from the log.
  12. The server has no TLS client: `Cargo.lock` has no `rustls`, `ring` or `native-tls`, `reqwest` is a test dependency with default features off, and `sqlx` has no TLS feature. The allow list in `deny.toml` is MIT, Apache-2.0, Unicode-3.0, Zlib and BSD-3-Clause. A rustls stack brings ISC, an OpenSSL-style licence on `ring`, and a webpki root set brings CDLA-Permissive-2.0; `ring` also needs a `[[licenses.clarify]]` entry. Slice 10 lists the exact expressions as `cargo deny` reports them. Production Postgres over TLS is the same decision.
  13. `Reply::unauthenticated` sends a bare `WWW-Authenticate: Bearer` on every route.
  14. The questionnaire proposes "read and write scopes" (two) while the glossary and ADR-0010 have three tiers, and Gatehouse serves none of them. `docs/architecture.md` (row "Room actor") still says the WebSocket transport is not built. `MELDFRAME_MCP_HOSTS` must name the public host or `/mcp` answers 403 to real callers.
  15. The rate-limit clock is monotonic since start (`Config::default`); identity code needs the wall clock (`now()` in `apps/server/src/lib.rs`).

The glossary's **Actor** entry says "a human editor or an agent session" and avoids "User"; it changes to "a person or an agent" and gains Person, Principal, Grant and Sign-in session. `session` is also an identifier in `apps/web/src/main.ts` (a random nonce per page load for idempotency keys) and means something else; the glossary entry says so.

## What Gatehouse must provide

The Gatehouse repository became readable during this work. What its documentation and tests state is used above; what follows could not be confirmed from them, or is missing.

- **Missing, needs a change (external work that starts now):** a way to serve resource-specific scopes in discovery, accept them in an authorization request, list them on the consent screen with the owner's wording (consent copy is a fixed function of the four provider scopes and unknown scopes read as "Access to your account data"), and carry them in the access token's `scope`. Also whether a resource-bound token can be issued without `openid profile`, so an agent is not asked for a name and an email it does not need.
- **To confirm against a running instance (slice 0 records them):** the claim names in a resource-bound access token (`scope`, `client_id` or `azp`, `iat`, `jti`, `sid`) and in an ID token; that a client sending `resource` gets a JWT and one that does not gets an opaque token; the `iss` value and whether authorization responses carry `iss`; whether RP-initiated logout needs an `id_token_hint` (the ID token is not stored, so the default is a Meldframe-only logout); refresh behaviour (rotation, lifetime) for a public client; JWKS rotation and cache headers; that the confidential web client and the public MCP client can both be linked to the `<public>/mcp` resource; that the server-to-server grant revoke accepts Meldframe's client; the per-address limits; and **whether Gatehouse asks for consent again for each resource**, since a person who already approved the client for another resource might not see a prompt naming Meldframe.
- **To confirm with a real Claude Code:** that it follows the metadata link, sends `resource`, which registration route it uses (a preset client id and fixed callback port, anonymous dynamic registration, or a metadata document) and that it refreshes without asking again.
- **Cannot be tested without it:** back-channel delivery to a public https URL (Gatehouse refuses non-public targets, so development has none and relies on the session limits), consent wording as rendered, TLS egress.
