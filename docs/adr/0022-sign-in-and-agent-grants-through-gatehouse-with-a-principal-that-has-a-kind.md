# People sign in through Gatehouse into server-side sessions, agents connect through OAuth grants checked on every call, and the principal carries a kind

M2 replaces development tokens with real identity: E2.1 (a person signs in), E2.2 (Claude Code connects to MCP through OAuth) and what is left of E2.4 (a grant the person can revoke, a consent that lists the risk tiers, and a person who can answer an approval). ADR-0006 chose Gatehouse and ADR-0012 chose OAuth grants; neither says how a sign-in session lives, how a revoked grant stops a call, how the server tells a person from an agent, or who may call `Server::decide_approval`. This records those choices, which are hard to change once files, actors, grants and sessions exist. It was written from the code, not from the docs: where the two disagree, the code is quoted under Consequences. The design was checked against a sibling product that already signs people in with Gatehouse and serves an OAuth-protected MCP endpoint (patterns only, in the table under Considered options) and against what the Gatehouse documentation and tests state it provides today; what could not be confirmed is listed under "What Gatehouse must provide". ADR-0021 (activity lanes, merged) takes migration 0007 and shares several crate ceilings with this ADR; the joint budget is under Consequences. "Client" in this text always means an OAuth client (the web editor is the "web editor"); the glossary's _Avoid_ for the front end cannot be applied to a protocol term.

## Summary of the decisions

| Topic | Decision |
|---|---|
| Parties | Gatehouse is the authorization server and identity provider; Meldframe is an OIDC relying party for people and a resource server for agents; no copyable credential is minted |
| Person sign-in | Code flow with PKCE S256 run by the server as a confidential client; a server-side session row and an opaque `__Host-` cookie; 8 h idle, 24 h absolute |
| Browser safety | `Origin` check on cookie mutations and cookie upgrades; the editor is served from the API origin with a CSP |
| Logout | Logout, "sign out everywhere" and back-channel logout end the sockets (close 4401); a bearer socket also ends at its token's expiry |
| Principal | `{workspace, actor, kind, tiers}`; kind comes from the credential type only; `person:<id>` and `agent:<grant id>` actors |
| Policy | A person is Auto at every tier; an agent's Delete is Ask; the same closure and every tool route read the principal |
| Agents | RFC 9728 metadata and challenge; resource-bound RS256 JWTs verified offline; the grant table is read on every call |
| Grants | New grants are `pending` until the person approves them and picks a cap (Read only by default); revoke is local first, then at Gatehouse; the deny lifts only on a confirmed revoke or an explicit Allow again |
| Tier scopes | Three wire strings behind `MELDFRAME_TIER_SCOPES=off` or `required` (default off); needs a Gatehouse change |
| Approvals | Cookie-only routes for a person; `decide_approval` takes a `PersonRef` |
| Release | `dev-tokens` is opt-in; release plus the feature refuses to start; CI proves the path is absent |
| Storage | Migrations 0008 (identity, grants, audit) and 0009 (calls `grant_id`) after ADR-0021's 0007 |
| Plan | M2 S0 to S21 as a stack of small pull requests, with one budget table shared with ADR-0021 |

## Decision

- **Three parties, kept apart.** Gatehouse is the authorization server and the identity provider: it signs people in, registers OAuth clients, shows consent, issues and revokes tokens. Meldframe is an OIDC relying party for people and an OAuth resource server for agents (RFC 9728 metadata, bearer tokens). Meldframe never mints a credential that a person or an agent could copy: the only secrets it issues are opaque sign-in session ids in a cookie the page cannot read. A token Gatehouse issued to an agent is never forwarded to another service (no passthrough). The server keeps its identity state in one process; the in-memory index and the revocation bus below assume a single server process (several would need the table read on every call or a notification channel, a later change).
- **How a person signs in.** The server runs the authorization code flow with PKCE S256 as a confidential client. `GET /v1/auth/login?return_to=` ignores any session cookie it received (a login the person did not ask for must not log them out, since any site can navigate a browser to a GET) and makes a login attempt (state, nonce and PKCE verifier, 256 bits each, kept in the database, living 10 minutes), sets the login cookie and redirects with `scope=openid profile` (no `offline_access`: the web session needs no refresh token) and the exact registered `redirect_uri`. The login cookie is `__Host-mf_login=<attempt id>; Secure; HttpOnly; SameSite=Lax; Path=/; Max-Age=600`: Lax, not Strict, because the callback is a cross-site top-level GET and Strict would drop it; it binds the attempt to the browser that started it and is cleared at the callback. `GET /v1/auth/callback` deletes the attempt in one statement (single use), compares `state` in constant time, requires `iss` to equal the configured issuer when the response carries it (RFC 9207), exchanges the code with the client secret and the verifier, and verifies the ID token itself (the JWT rules below, plus `aud` equal to the client id, `azp` when `aud` has several entries, `nonce`). The Gatehouse access token is dropped at once; the server keeps the subject, the Gatehouse session id (`sid`) and a display name. The session that exists is ended, and a new id made, only at the callback after the code exchange succeeded (no fixation); the editor's sign-in screen also offers a POST that ends the old session before login starts. Every failure redirects to `/?login_error=<code>` with one of eight stable codes (`cancelled`, `expired`, `state`, `issuer`, `exchange`, `token`, `signup_closed`, `unavailable`) and no detail. Responses of the callback, of every `Set-Cookie`, of `GET /v1/session` and of the approvals routes carry `Cache-Control: no-store`, and the callback and login redirects `Referrer-Policy: no-referrer`.
- **Where the session lives, and why a cookie.** A sign-in session is a row (`sign_in_sessions`) and a cookie `__Host-mf_sid` of 32 random bytes in base64url; the row keeps only the SHA-256 of the id, so a leaked table gives no cookie. Attributes: `Secure; HttpOnly; SameSite=Lax; Path=/`, no `Domain`, `Max-Age` equal to the absolute limit. The page cannot read the id, so XSS cannot copy it (it can still act in the page, see the editor paragraph). A browser cannot set `Authorization` on a WebSocket and a token in a query string lands in logs, so the cookie is the one credential the web editor and its sockets share. Limits (working defaults, the owner's to change): **8 hours idle and 24 hours absolute**. Meldframe assumes a back-channel logout is delivered at most once and does not rely on it alone, so the absolute limit is the real bound on a session whose logout was missed; a person signs in again through Gatehouse, which is silent while its own session lives. At most 10 sessions per person (the oldest ends when an 11th starts). What resets the idle timer: any authenticated HTTP request, and a frame that the client sent on a socket bound to the session (an op or a request; not a ping, not the server's own poll or heartbeat), written to `last_seen` at most once a minute. A tab that is open and idle is therefore ended at 8 hours like a closed one; an editor in use is not ended mid-edit; the 24 hour limit ends everything. Where the public URL is plain HTTP on loopback (development) the cookie is named `mf_sid` without `Secure`, and nowhere else.
- **CSRF and cross-site sockets.** A request that authenticates by cookie and is not `GET` or `HEAD`, and every WebSocket upgrade **that authenticates by cookie**, must carry an `Origin` equal to the configured public origin; with no `Origin`, `Sec-Fetch-Site: same-origin` is required; anything else is `403 origin_not_allowed` before the body is read. A request with an `Authorization` header is judged by the header alone and the cookie is ignored, so an agent's upgrade (a bearer, no browser `Origin`) is not subject to the browser check. The check is a pure function in `meldframe-auth` applied once where credentials are read. It is new: today nothing in the server checks `Origin` (`mcp/mod.rs` says so, because there were no cookies), and a cookie-authenticated `/v1/ws` and `/v1/live/{file}` without it would be open to cross-site WebSocket hijacking. `/mcp` never accepts the cookie.
- **The editor is served from the API origin, with a policy.** The cookie is `__Host-` and the `Origin` check is exact, so the web editor and the API share one origin. Nothing in the server serves static files today. A new crate `meldframe-http-web` (bin) serves `apps/web/dist` from the server with a `Content-Security-Policy`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer` and, on https, `Strict-Transport-Security`; behind a reverse proxy the same headers are the proxy's job and the ADR's requirement. The starting policy is `default-src 'self'; script-src 'self' 'wasm-unsafe-eval'; connect-src 'self'; object-src 'none'; base-uri 'none'; frame-ancestors 'none'`, which is **not yet verified against the real build**: with no `style-src`, `img-src` or `font-src` everything falls back to `default-src 'self'`, which would block `blob:` and `data:` images (Pixi textures), inline style attributes and a font loaded from elsewhere. Before slice 13b lands it must be checked with the real build and a browser: Pixi texture loading (`blob:` and `data:` sources), the Inter font, WASM instantiation, any worker (`worker-src`), and Svelte's inline styles; every relaxation (`img-src 'self' blob: data:`, a `style-src` with a nonce or `unsafe-inline`) is written in that pull request with the reason. This matters beyond hygiene: agent-written text (names, notes) is shown in the editor, and a same-origin script could call the approvals route as the person and approve its own agent's delete. The mitigations are the CSP, Svelte's escaping, a lint that forbids `{@html` in every front-end package, canvas text drawn by Pixi and not as HTML, and an approvals screen that names the file, the kind and the node. What remains is stated under risks; asking the person to authenticate again before approving a Delete is a named follow-up.
- **Logout and revocation end the sockets.** `POST /v1/session/logout` (cookie, CSRF-checked; `{"all": true}` ends every session of the person) marks the row ended, removes it from the in-memory index and publishes its id on a revocation bus; every open `/v1/ws` and `/v1/live` socket of that session closes with WebSocket code 4401 and reason `session_ended` within one live poll (250 ms by default). Sockets also re-check their session or grant on every frame and poll, so a missed bus message cannot keep one open. **A socket that authenticated with a bearer token is also bound to that token's `exp`**: it closes with 4401 and reason `token_expired` when the token expires (the client reconnects with a fresh one), so a socket cannot outlive the short-lived credential that opened it. Gatehouse's back-channel logout (`POST /v1/auth/backchannel-logout`) is accepted only when the `logout_token` passes every rule: RS256 signature against the JWKS (the JWT rules below), `iss` equal to the configured issuer, `aud` equal to the web client id, `iat` within the leeway, `typ` `logout+jwt`, an `events` claim holding the back-channel member, no `nonce`, `exp` in the future and at most 120 seconds after `iat`, `jti` never seen (remembered for `exp` plus the leeway), and at least one of `sub` and `sid`. It then ends the sessions with that `sid`; **fail closed**: if no session matches the `sid` (or the session's `idp_sid` is null) it ends every session of that `sub`. Signing out of Gatehouse does not end an agent grant: an agent keeps working while the person is away, and its grant ends only on the Connected agents screen. After a ban at Gatehouse an agent's access token works until it expires (about one hour) unless the grant is revoked in Meldframe, and a web session works until the back-channel logout arrives or the 24 hour limit.
- **The principal has a kind.** `Principal` becomes `{ workspace, actor, kind, tiers }` and moves to a new core crate `meldframe-principal`, re-exported from `meldframe-host` (which is 15 lines under its ceiling and would not fit the new fields). `kind` (`Person` or `Agent`) and `tiers` (the risk tiers the credential may reach: all three for a person, the grant's cap for an agent) are private with getters, so no struct literal outside the crate builds one. **The kind is decided by the kind of credential and nothing else (one development-build exception, below)**: a valid sign-in cookie is a `Person`; a valid OAuth access token is an `Agent`, even when the same human is behind both; never an actor string, a claim the caller chose or a request field. `Principal::new(workspace, actor)` keeps its signature and builds an `Agent` with all tiers (79 call sites in 47 files keep compiling, and anything not marked a person fails closed). A `Person` is built by one function with a distinctive `#[doc(hidden)]` name, `__mint_person`, behind the cargo feature `mint`; `meldframe-auth` calls it when it has verified a cookie, and `Principal::person` exists only behind `test-support`, which test crates enable. This is a convention with two machine checks and **not a seal**: with cargo's feature unification a feature that is on in a build is on for every crate in that build, and the server build always includes `meldframe-auth`, so `cargo tree -e features -i meldframe-principal` bounds who enables `mint` and not who calls it. The second check is a call-site script in CI that fails when `__mint_person` appears anywhere except `crates/core/meldframe-auth/`, the definition and the `test-support` wrapper in `crates/core/meldframe-principal/`, `scripts/ci/` and `docs/`, when a `pub use` or an alias of the name appears outside `meldframe-auth`, and when `test-support` is enabled outside `[dev-dependencies]`. Together they make a skipped identity check visible in review; they do not make it impossible. `workspace` and `actor` stay public fields, so a `&mut Principal` could retarget a person's workspace; this is accepted, because making them private touches every field read in the workspace. A route lists the credentials it accepts: `/mcp` only agent bearer tokens; `/v1/approvals`, `/v1/grants` and `/v1/session` only the cookie; REST tools, `/v1/ws`, `/v1/live`, snapshots and assets both. `Principal::agent(workspace, actor, tiers)` builds an agent with the grant's cap (the resolver uses it); `Principal::new` is the all-tier agent. The exception: in a development build, a `MELDFRAME_DEV_TOKENS` entry whose actor is listed in `MELDFRAME_REVIEWERS` is a `Person`; such an actor is Auto at every tier, so it bypasses Delete approval, and `/mcp` refuses any `Person`-kind principal in every build, so a listed dev actor cannot use it. The grant id for the call log is read with `Principal::grant_id()`, which returns it for an agent whose actor is `agent:gr_...`. An `on_behalf_of` field is left out until a rule reads it (the grant table already names the person).
- **How the actor is derived.** A person is `person:<person id>` with Meldframe's own id (`per_` and 20 base32 characters), never the email and never the raw Gatehouse subject, so a change of provider rewrites no history and no actor string holds personal data. An agent is `agent:<grant id>` (`gr_` and 20 base32 characters): one grant is one actor and one lane. A revoked grant is never reused (a new grant is a new actor, so old attribution, per-actor undo and idempotency keys cannot be resurrected), the per-principal rate budget and in-flight slots are per grant, and the call log, batches and activity lanes name the grant. Two chats of one Claude Code installation share one grant, so one actor and one lane; this answers question 1 of ADR-0021 as "one grant, one lane" and the Connected agents screen says so. The development token's actor stays whatever its entry says.
- **ADR-0021's reviewer check changes once the kind exists.** ADR-0021 denies by default and lets only actors named in `MELDFRAME_REVIEWERS` set a review, because `Principal` has no kind and an actor prefix cannot be trusted. With this ADR the check is: the principal's kind is `Person`. ADR-0021 and the epic word the rule as "owner"; M2 has one person per workspace and no roles, so the two coincide, and the wording is corrected in slice 14 (a role field arrives with multi-member workspaces and joins the rule then). `MELDFRAME_REVIEWERS` is not deleted at once: it moves into the development-token adapter, where an entry of `MELDFRAME_DEV_TOKENS` is an `Agent` unless its actor is listed, and it has no meaning for cookie sessions or OAuth tokens.
- **A person may delete in the editor; an agent is asked.** The default policy ignores the principal today (`default_policy(tier)`), so Delete is Ask for everyone; with one person per workspace and the rule that an actor cannot answer its own request, a lone person deleting a frame in the editor would open an approval only they could answer, and could not answer it: a deadlock until expiry. E2.4 says an agent that deletes a whole frame or a large subtree is asked first, and the editor has undo, so the policy closure reads a `Person`'s Ask as Auto (a Deny, or a policy that cannot be read, still applies: G5), that is Auto at every tier by default, and keeps `Ask` for Delete for an `Agent` (and the caps below). The own-request refusal stays for agents (an agent cannot answer its own ask; it cannot answer at all). A person's Delete is logged like any call and is revertible. This changes a default the owner decided in the questionnaire (Delete is Ask; decisions row 26 keeps defaults until the owner overrides), so it is an owner question (question 16, default yes) and a decisions row when confirmed. An agent that drives the person's own browser (computer use) holds the person's cookie and is therefore a person to the server and Auto at every tier; this is stated under risks.
- **Workspaces and people.** New tables `people` (id, issuer and subject, display name, `disabled_at_ms`), `workspaces` (id, name, owner) and `memberships` (workspace, person, role), unique on `(issuer, subject)`, not on email. The first sign-in of an allowed subject creates the person and one personal workspace in one transaction. **Sign-up is an allow-list by default**: `MELDFRAME_SIGNUP=allowlist` (the default) admits only the Gatehouse subjects in `MELDFRAME_ALLOWED_SUBJECTS` (comma separated, at most 50, read at start; the first owner is simply the first entry) or in the table `allowed_subjects`; an empty list admits nobody and the server says so at start. A refused sign-in is `signup_closed`. It records the subject (an opaque id) in `auth_events`, **at most one row per subject per day and at most 1,000 such rows a day overall**, so a flood of refused attempts cannot fill the table; the first owner, who cannot know their own Gatehouse subject beforehand, signs in once, is refused, and the owner reads it with `meldframe-server admin list-refused` and adds it with `meldframe-server admin allow-subject <sub>` (both in slice 12, writing to `allowed_subjects`). `MELDFRAME_SIGNUP=open` admits anyone Gatehouse admits, capped by `MELDFRAME_MAX_PEOPLE` (default 50). The email is not stored; the `name` claim is kept, at most 128 characters after control and format characters are stripped, else `Person` and four characters of the id. In M2 a workspace has one person (no invitations, no roles beyond ownership), so "another workspace cannot see that file" is a test between two people. The session row carries the workspace and the principal's workspace comes only from there (ADR-0006: never from the request). Disabling a person (`IdentityStore::disable`, reached through a subcommand of the server binary, `meldframe-server admin disable-person <id>`) ends their sessions, revokes their grants, refuses new sign-ins, new pending grants and every token call of their grants; an erasure request that Gatehouse passes on removes the display name and the subject from `people` (a tombstone keeps the id, so actor strings in the log stay valid and hold no personal data) and the subject from `auth_events` (the trigger allows exactly that `UPDATE`: `subject` set to NULL with every other column unchanged); ops, batches and calls keep only opaque ids.
- **How Claude Code connects.** `/mcp` is an OAuth protected resource per the MCP authorization specification. An unauthenticated or refused call is `401` with `WWW-Authenticate: Bearer resource_metadata="<public>/.well-known/oauth-protected-resource/mcp"` (plus a `scope` parameter when tier scopes are on; today `Reply` always sends the bare `Bearer`). The server serves RFC 9728 metadata at the path-inserted URL and at the root form: `resource` is `<public>/mcp` (canonical, no trailing slash), `authorization_servers` is the Gatehouse issuer, `bearer_methods_supported` is `["header"]`, `scopes_supported` lists `offline_access` (without it a client gets a one-hour token and no refresh) and, when tier scopes are on, the three tier strings. A client then reads Gatehouse's own metadata (RFC 8414 or OIDC discovery; the document's `issuer` must equal the configured issuer), registers, and runs the code flow with PKCE and an RFC 8707 `resource` parameter, so Gatehouse issues an RS256 JWT access token whose `aud` is the resource. The server mirrors the authorization server metadata at its own origin only if a real client turns out to ask there.
- **Client registration (to be settled with the owner and a real Claude Code).** The MCP client is a public client: authorization code with PKCE S256, `token_endpoint_auth_method` `none`, a loopback redirect, refresh tokens. Meldframe is indifferent to how it gets a client id: it sees a `client_id` in the token, derives a grant key from it, and never registers or trusts a client itself. The routes, from Gatehouse's documentation: (a) a public client the owner pre-registers at Gatehouse, which Claude Code is told to use; its redirect URI is an exact-string match, so a loopback redirect needs a fixed port, and whether Claude Code accepts a fixed callback port and a preset client id must be checked; (b) Gatehouse's dynamic registration (RFC 7591), which needs a logged-in person, and Claude Code registers without one, so this route needs the anonymous registration option, which is an opt-in the owner must weigh at Gatehouse, gives such clients only `openid profile email`, and marks them self-registered on the consent screen; (c) Gatehouse's client id metadata document path, built for one allowed origin and possibly the zero-setup route if Claude Code uses it (unconfirmed). Consent is never skipped. The questionnaire's earlier working default ("public client with PKCE and dynamic client registration", read and write scopes) is one the owner may replace; this ADR proposes replacing it by the paragraphs above and below (decision 26 keeps a default until the owner overrides).
- **Risk tiers on the wire, behind a switch.** The tiers can travel as three OAuth scopes, `meldframe:read`, `meldframe:change`, `meldframe:delete` (the glossary's _Avoid_ of "scope" is about the tier concept: the strings are only the wire form of Read, Change and Delete, and the code, the screens and the tool text say tier). They are independent, not nested. Gatehouse serves only `openid profile email offline_access` today, and a request for a scope it does not serve fails at authorize with `invalid_scope`, so advertising them early would break every connection. `MELDFRAME_TIER_SCOPES` has two values. `off` (the default): the metadata and the challenge advertise no tier scopes and tokens carry none; the tiers of a grant come only from the cap the person sets (below). `required`: the metadata advertises them, a token without `meldframe:read` is refused `401 invalid_token`, and effective tiers are the token's scopes intersected with the cap. The scope says how far a grant may reach; the policy per tier (Auto, Ask, Deny, ADR-0010) still decides each call inside that reach. A call above the effective tiers is refused by the gate as `forbidden` (HTTP 403; on `/mcp`, with `required`, `WWW-Authenticate: Bearer error="insufficient_scope", scope="meldframe:delete"`). The cap has no home today: the server builds its gate with `approvals.gate(|_, tier| default_policy(tier))` (`apps/server/src/lib.rs`), which ignores the principal, and `check_tool` reads a read tool's policy without one. The policy closure already receives the principal, so it reads `tiers` and `kind` (this paragraph and the person paragraph above are one closure); `check_tool` gets the principal too. The closure lives in a new file of a new crate (below), not in `lib.rs`. E2.4's consent line ("the consent screen lists the risk tiers") stays open until Gatehouse serves the scopes and the owner approves the wording; it needs external work that should start now (owner question 5).
- **Every tool route reads the principal, not a policy fixed at start.** The cap is worthless if a route never asks for it. Today `apps/server/src/main.rs` builds `capture_policy`, `upload_policy`, `review_policy`, `export_policy` and `import_policy` once at start from `registry.policy_for(..)`, with no principal, and passes each as an `Option<Policy>` to its crate; `meldframe-http-assets` (`POST /v1/assets` and the `upload_asset` tool) writes blobs without `gate.submit` at all, and capture and the review route decide on that startup value. A Read-capped agent could therefore call `upload_asset` (a Change) and succeed. So every tool route and every `Extra` takes a principal-aware check, `Fn(&Principal) -> Policy` built from the registry policy and `Principal::may(tier)` (a person: the registry policy; an agent: the registry policy if the tier is in `tiers`, else Deny), instead of an `Option<Policy>`. The crates: `meldframe-http-assets`, `meldframe-http-capture`, `meldframe-http-review`, `meldframe-http-export`, `meldframe-http-variables-import`, and `meldframe-http`'s own tools (`apply_commands`, `make_variant` and the reads, through `check_tool`); ADR-0021 adds `meldframe-http-activity`, which is written to the same rule. Import and export reach the gate through `submit_ops` for their writes, and are checked in their slice. One test per route, in slice 15a: a Read-capped agent is refused on upload (both the route and the tool), capture, review (list is a Read and passes; a write is refused), export and import.
- **Consent and the grant the person confirms.** The OAuth consent screen is Gatehouse's. It never names Meldframe's tiers (until the scopes exist) and a person can approve it for a client id they do not recognise. So **a grant is created `pending`** by the first valid token of a client for a person who has signed in, and every call of a pending grant is refused `403 grant_pending` until the person approves it on the Connected agents screen. That screen shows the client's label, when it first connected, the three tier lines (proposed wording, the owner's to approve: "See your designs (Read)", "Create and change designs; changes can be reverted (Change)", "Delete frames and large parts of a design; you are asked first unless you change that in Meldframe (Delete)") and lets the person pick the cap, **Read only by default**; Approve makes the grant `active`; **Deny** marks a pending grant `revoked` with reason `denied` (the row stays, no Gatehouse call is made, and the slot is freed), which is also how a malicious client that fills the 20 pending slots is cleared. The server holds no wording (standard U5). This is also where a person allows an agent again after a revoke.
- **Agent tokens: short-lived, checked on every call.** The server accepts only a resource-bound RS256 JWT, with these rules (a hostile corpus tests each): the header `alg` is `RS256` (`none`, HS* and everything else are refused); `kid` is present and found in the cached JWKS, and the key comes only from that JWKS, never from a header: a token with `jku`, `jwk`, `x5u`, `x5c` or `crit` in its header is refused; the key is RSA with a modulus of 2048 to 4096 bits, its `use` (when present) is `sig` and its `alg` (when present) is `RS256`; `typ` is absent or `at+jwt` or `JWT`; `iss` equals the configured issuer; `aud` contains the resource; `exp`, `nbf` and `iat` are checked with a leeway of 60 seconds; `exp - iat` is at most 24 hours (Gatehouse's default is one hour; a longer life is refused because NFR-6 says short-lived; M2 S0 confirms the claims this depends on); `sub`, `client_id` (or `azp`) and `scope` (at most 512 bytes) are present; when both `client_id` and `azp` are present and differ, the token is refused. These claim names are working assumptions that M2 S0 confirms or corrects. Verification is offline against a cached JWKS (fresh 1 hour, served stale up to 24 hours when Gatehouse cannot be reached, one refetch per minute at most for an unknown `kid`). A legitimate key rotation that lands inside that minute answers `503 identity_unavailable` for its first tokens, which is accepted: the client retries. Introspection (RFC 7662) is kept only as an off-by-default fallback for opaque tokens; a token without `resource` is opaque and is refused `401 invalid_token`. After the token passes, the call looks up the grant by `(person of sub, client)` in an in-memory index written through to the database. A grant that is missing, `pending`, revoked or whose person has not signed in refuses the call (`grant_pending`, `grant_revoked`, `grant_requires_sign_in`). **No JWT can be revoked at Gatehouse before `exp`, so the grant table is the revocation**: it is read on every call and never cached for a period.
- **Grants.** Fields: id, person, workspace (the person's), a hash of the client id as the lookup key, **the full client id** (at most 2,048 bytes; it is public, a registered id or a metadata-document URL, and Gatehouse's revoke needs it in plain text), a label of at most 128 characters (the client's name, else the first 32 characters of the id), `state` (`pending`, `active`, `revoked`), `tier_cap`, `created_at_ms`, `last_used_ms` (once a minute), `revoked_at_ms`, `confirmed_at_ms` (when Gatehouse answered `revoked: true`), `idp_revoke` (`none`, `queued`, `confirmed`, `failed`, `cancelled`) and the retry state. A partial unique index allows at most one `pending` or `active` row per (person, client hash); the newest non-revoked row wins. A token for a subject with no person is refused `403 grant_requires_sign_in`: an agent path never creates a person or a workspace. At most 20 active or pending grants per person and 100 per workspace; one more is `grant_limit`.
- **Revoking a grant ends it on the next call, and stays ended.** `DELETE /v1/grants/{id}` (cookie only, CSRF-checked) sets `revoked_at` in the database first and then in the index in one step, publishes the grant id on the revocation bus (its open sockets close with 4401), expires its pending approvals as denied, writes an `auth_events` row, queues the Gatehouse revoke for the person's grant for that client (`{user_sub, client_id}`, retried with backoff for up to 24 hours by a worker described in the storage paragraph) and answers `204`. From then every call with any token of that grant is **`403 grant_revoked` with no `WWW-Authenticate` challenge**: a `401` would send an MCP client back through authorization in a loop, while a `403` tells it the grant is refused (the client stops, and the person re-allows on the screen). **`iat` cannot tell a refresh from a consent**: a refresh token mints an access token with a later `iat` without any new consent, so "a token issued after the revoke" proves nothing. The deny therefore stays for the pair (person, client) and is lifted only (a) when Gatehouse has answered `revoked: true`, recorded as `confirmed_at_ms` (the refresh tokens are gone); from then a token whose `iat` is later than **`confirmed_at_ms`** (not `revoked_at_ms`) comes from a new consent and makes a new `pending` grant, and a token with `iat` at or before `confirmed_at_ms` stays refused until it expires: this closes the case where a refresh minted a token at T0+5 seconds while Gatehouse was down, which would otherwise look like a new consent once Gatehouse confirmed at T1; **A new grant inherits `not_before_ms`, the largest `confirmed_at_ms` of the earlier revoked grants of the pair, and every token with `iat` at or before it (plus a leeway of 60 seconds for the clock difference between Meldframe and Gatehouse, which can only ever produce a pending grant) is refused for that pair until it expires, whichever row is newest**; otherwise a stolen token X from before the revoke would be judged against a later approved grant B and act as `agent:B` (test: X, then Y after re-consent, approve B, X refused); or (b) when the person presses **Allow again** on the Connected agents screen, an explicit act that creates a new active grant with a cap they choose, **cancels the queued Gatehouse retry of the old grant** (a late retry would revoke the refresh tokens of the new grant) and sets `not_before_ms = max(its existing `not_before_ms`, the time the person pressed Allow again)`, with the same 60 second leeway rule: every token with `iat` at or before it is refused for the pair until it expires, whichever row is newest, so a token stolen or leaked before the revoke cannot act as the new grant, and a legitimate agent just refreshes (a new `iat`) and continues, at the cost of one refresh. No Gatehouse confirmation exists on this path, which is why the time of the act is the bound. The same applies when a person approves a pending grant B after a revoke: its `not_before_ms` is the inherited value or the time of the approval, whichever is later (a first grant with no earlier revoke has no such bound). Allow again while a pending grant B of the pair exists is defined as approving B with the chosen cap, so the one-live-grant index never breaks; a retry still in flight at Gatehouse when Allow again happens can still revoke the new grant's refresh tokens, which is accepted: the agent's next refresh fails and it connects again as a new pending grant the person approves. The retry the person can force is `POST /v1/grants/{id}/retry-revoke`; a retry that Allow again cancels is `idp_revoke = cancelled`. What `revoked: false` means is not assumed: Gatehouse's revoke is idempotent, so `false` can mean the first attempt already succeeded or that the client never held a refresh token, and Meldframe cannot tell it from a failure. The intended behaviour is fail closed: `false`, 4xx, no answer and an outage all leave the deny in place, the screen shows the state and a retry button, and Allow again is the exit; M2 S0 asks Gatehouse what `false` is meant to say. If the database cannot record a revocation the route answers `503` and does not claim success.
- **Approvals reach the person.** Two routes, cookie only, `Person` only: `GET /v1/approvals` (the pending approvals of the principal's workspace, oldest first, at most 100, each `{id, actor, file, kind, nodeId, state, createdAt, expiresAt}`, never a command, name or text) and `POST /v1/approvals/{id}/decision` with `{"decision": "approve" | "deny"}` (at most 64 bytes, unknown fields refused). They live in a new crate `meldframe-http-approvals` over a small `Approver` trait that `SharedServer` implements in `apps/server/src/approval.rs`. The editor lists them in the right panel (E5.1's activity lane is the later home) and polls every 5 seconds while the panel is open and once after any `approval_required` reply; a push as an ephemeral frame (ADR-0009) is a follow-up. A request nobody answers expires to denied after 15 minutes (G5, U7); the panel offers Approve once and Deny only, never "always" (U7). With the paragraph on policy above, by default an approval exists only for an agent's Delete.
- **How `decide_approval` is protected.** (1) The route accepts only the sign-in cookie: a bearer token, an agent's included, is `403 person_required`, and `/mcp` has no such tool. (2) `Server::decide_approval` takes a `PersonRef<'_>`, a borrowed view that `Principal::as_person()` builds only for a `Person`; this turns the check into a type the signature names, and a compile-fail test shows a plain `Principal` cannot be passed. The compile-fail test covers only that case; who can make a `Person` is bounded by the two CI checks above, not by the compiler. (3) The CSRF and `Origin` check. (4) `Approvals::answer` already treats another workspace's id as unknown and refuses the actor's own request. (5) One answer per approval; a second is `409`. (6) The per-principal bucket and the existing caps (20 open per actor, 100 per workspace). (7) The answer is a `decide_approval` entry in the call log, as today, now with the person's actor.
- **Release builds.** The Cargo feature `dev-tokens` lives in `apps/server` and is opt-in: not in `default`, enabled only by the development recipes (`just dev`, `just dev-server`, `tools/dev-smoke.sh`) and by the test crates that start the server assembly. It gates the only code that reads `MELDFRAME_DEV_TOKENS` and constructs `DevTokens`; the `DevTokens` type itself stays in `meldframe-auth` and is re-exported by `meldframe-http`, so the twelve test files and every test crate keep compiling with no manifest change. A release build is made without the feature and does not reference the type. A build that has the feature and the release profile refuses to start with `DevTokens` configured, with no override: `MELDFRAME_ALLOW_DEV_TOKENS` is removed in the slice that adds this refusal and not before, so the override and its replacement never coexist or both vanish. CI proves the absence instead of a Rust test that cannot build both variants: a release job builds `meldframe-server` without the feature, checks `cargo tree -p meldframe-server -e features` shows no `dev-tokens`, and checks the binary holds neither the `DevTokens` symbol nor the text of its spec-parse error. With the feature off, a set `MELDFRAME_DEV_TOKENS` is a start-up error naming the variable. A server with neither the feature nor an OIDC configuration does not start; it is never open. Development tokens and OIDC coexist only in a development build: both authenticators are tried (a bearer matching a dev token first), `check_dev_listen` still demands a loopback listener unless `MELDFRAME_ALLOW_DEV_PUBLIC=1`, and a dev token's kind is `Agent` unless listed. **A dev-token person cannot answer an approval**: the approvals routes accept the cookie only, so the development editor can create approvals as an agent would not, but answering one needs the sign-in mode of slice 19b; before that, tests answer through the `test-support` constructor. Today `serve()` insists on `MELDFRAME_DEV_TOKENS` (`apps/server/src/main.rs`), so the server cannot start without them.
- **Real sign-in in `just web`.** `apps/web/dev/proxy-guard.ts` and `vite.config.ts` inject the dev token on every `/v1` call and own the `Authorization` header. A mode `MELDFRAME_WEB_SIGNIN=1` makes the proxy pass cookies and `Set-Cookie` through unchanged, stop injecting the token, and treat the Vite origin as the public origin for the `Origin` check; the registered redirect URI is then the Vite origin's callback. The proxy guard and its test move out of `apps/web` first (a pure move to a package, with the size entry lowered in the same pull request), because `apps/web` is over its ceiling and may only shrink; the edits land there.
- **Storage.** Migration numbers follow ADR-0021's 0007 and are taken from the next free number when each slice lands. `0008_identity.sql` (slice 8): `people`, `workspaces`, `memberships`, `allowed_subjects`, `sign_in_sessions` (`id_hash` primary key, person, workspace, `idp_sid`, `created_at_ms`, `last_seen_ms`, `ended_at_ms`, `end_reason`), `login_attempts`, `backchannel_jti`, `agent_grants` (grants are never memory-only, so they exist with the first slice that creates one) and **`auth_events`** (kind, person, workspace, grant, outcome code, `at_ms`; no address, token, email or name; the subject only on a refused sign-in), so every slice that writes an event has its table. `0009_calls_grant.sql` (slice 16a2): a nullable `grant_id` on `calls` and in `CallEntry`, so the call log can say whose agent a call was without holding content. `auth_events` is append-only in the sense `calls` is: a trigger refuses `UPDATE` except one that sets `subject` to NULL with every other column unchanged (the erasure path); it refuses `DELETE` except of a row whose `at_ms` is older than the retention (90 days, the owner's to change), with no setting involved, so the hourly retention job can remove old rows and nothing else can. That protects against bugs, not against a hostile database role: any statement by the application's role could still drop the trigger; a separate owner role for the migrations is the stronger form and is a later hardening. The same job, hourly, deletes expired login attempts, ended sessions and used jtis. The server has no job runner today; `meldframe-http-oidc` exposes a `Janitor` that `wire(...)` returns and `main.rs` spawns beside the live timer (slice 12). The Gatehouse revoke retry is not the hourly job (its backoff of 5 seconds, 30 seconds, 5 minutes, 30 minutes and 2 hours is finer): it is a `RevokeWorker` task in `meldframe-http-grants` that sleeps until the earliest `next_attempt_at`, also returned by `wire` and spawned in `main.rs` (slice 16b). The sqlx migrator in `PgStore` owns the schema; `PgStore` gains a small accessor so a new crate can run queries on its pool and runtime.
- **Keys, clock, replay, rate limits.** The cookie id needs no signing key (random, looked up), so no cookie key rotates. The OAuth client secret comes from `MELDFRAME_OIDC_CLIENT_SECRET` or a file named by `..._FILE`, never argv, never logged, never in an error text; rotating it is a restart (Gatehouse invalidates the old one at once, so there is no overlap to design). Issuer keys rotate at Gatehouse; the JWKS cache handles it. Time: JWT and session checks use the wall clock the server already has (`now()` in `apps/server`), injected as a trait so tests move it; the rate limiter's monotonic clock is not used for them. A leeway of 60 seconds each way covers skew; a server clock further off fails every token and logs `token`, not in the reply. Replay: an authorization code is single use at Gatehouse and the login attempt is deleted on first read; a back-channel `jti` is remembered; an agent token is a bearer credential and not one-time by design, which is why the grant table, the short life and the audience binding are the controls. Rate limits per client address (the existing `client_ok` bucket, then these): login 10 a minute, callback 20, logout 30, back-channel 60; grants and approvals use the per-principal bucket; failed token verifications are remembered briefly by the SHA-256 of the token so a loop of bad bearers costs one verification; at most 1,000 live login attempts and 10 per address (kept in memory, so no address is stored).
- **Auth log.** `auth_events` records sign-in, refused sign-in (code), sign-out, back-channel end, grant created, approved, revoked and allowed again, grant refused (`grant_revoked`, `grant_pending`, `grant_requires_sign_in`, `grant_limit`) and Gatehouse revoke outcome. Ids and codes only. The decision on an approval stays in the call log.
- **Bounds on every input.** Cookie value 64 bytes; bearer token 4,096 bytes; ID token and logout token 8 KiB; `state` and `code` 512 bytes; `return_to` a relative path of at most 512 bytes starting with a single `/`, no `//`, no `\`, no control character, else `/`; `login_error` one of eight codes; every Gatehouse response 64 KiB read with a limit, and at most 16 keys in a JWKS; outbound calls https only (loopback http for tests), no redirect followed, 5 second timeout, 10 seconds for a whole callback; `sub` 255 bytes, `client_id` 2,048 bytes, display name and label 128 characters; scope string 512 bytes and at most 16 scopes, unknown scopes ignored; decision body 64 bytes; grant and approval ids must match their format before any lookup; at most 20 grants per person, 10 sessions per person, 1,000 login attempts, 50 allowed subjects at start. A value over a bound is refused with a short stable code and costs no outbound call. Meldframe has no outbound URL that an attacker influences: the issuer is configured, and fetches of client metadata documents and dynamic registrations are Gatehouse's, so no SSRF defence beyond https-only, no-redirect and size limits is built here.
- **Failure modes** (fail closed; unavailable is `503` and retryable, never `401`, so a client does not discard good credentials during an outage). Gatehouse unreachable at login: `login_error=unavailable`, existing sessions unaffected. JWKS unreachable: cached keys (up to 24 hours stale), then `503 identity_unavailable` for tokens with an unknown `kid`. Database unreachable: sessions and grants already in the index keep working until revoked, new sign-ins, grants and revocations answer `503`; a logout always ends the session in memory and clears the cookie even if the row write is retried later. Unknown or bad token: `401 invalid_token` with the challenge (`unauthenticated` when none was sent). Revoked grant: `403 grant_revoked`, no challenge. Pending: `403 grant_pending`. A 403 body carries an `error_description` that points the person to the Connected agents screen. Tier above the grant: `403 forbidden`. A row or claim that is not understood (an unknown tier name in `tier_cap`, a malformed session row) grants nothing extra: only the tiers that parse count and an empty set leaves Read only, as G5 says (if a row cannot be read at all, only Read proceeds).
- **Testing without a live Gatehouse.** (1) Pure crates with table-driven tests and a hostile corpus (algorithm `none`, HS256 signed with the public key as the secret, `jku`, `jwk`, `x5u`, `x5c`, `crit` headers, a modulus of 1,024 and of 8,192 bits, `aud` missing or an array, wrong `iss`, expired, `nbf` in the future, no `kid`, unknown `kid`, a token of 5 MB, duplicate claims, non-UTF-8, a `scope` of 10,000 entries, a discovery document with another `issuer`). Test keys are a small fixed set of RSA keys made once by a documented script and committed as fixtures (marked for the secret scanner, never used outside tests), not generated in every test, which is slow in a debug build. (2) A fake OIDC provider crate, `meldframe-fake-idp` (kind tool, axum): discovery, JWKS with rotation, authorize (signs a scripted person in), token, end-session, back-channel delivery, the grant-revoke endpoint, and switches for every failure (outage, slow, empty 500, wrong issuer, wrong audience, skew). (3) A store contract suite run against the memory adapter and Postgres. (4) A conformance list that runs against the fake always and against a real Gatehouse when `MELDFRAME_IDP_CONTRACT_URL` is set (it prints `SKIPPED` otherwise, as the Postgres tests do). (5) `tools/mutation-check-auth.sh` in the style of the sync mutation check: switch one rule off at a time (the audience check, the deny after a failed revoke, the origin check, the kind check on `decide_approval`, the re-check on an open socket, algorithm pinning, single use of an attempt, the pending state) and fail if the tests still pass. (6) Tests live in several tool crates with a budget each, as the repo does for its other suites (the plan names the crate for every slice). Named tests that must exist: revoke, Gatehouse answers 4xx, the agent refreshes, the call is still `grant_revoked`; a lone person deletes a frame and it is applied; an agent's Delete is `approval_required` and the person's answer admits it once; a pending grant is `grant_pending`; a Read-capped agent is refused on upload, capture, review, export and import; a token minted while Gatehouse was down and a revoke confirmed later does not make a new grant; after Allow again a token X minted before is refused and a token Y minted after is accepted, and the same after approving a pending grant B following a revoke; a back-channel token for an unknown `sid` ends all sessions of the `sub`. (7) Browser checks by hand against the real server and the fake provider: sign in, edit, a socket from a wrong origin refused, logout closes the socket, a second person in another workspace cannot read the first person's file. What needs the real Gatehouse and a real Claude Code is listed under "What Gatehouse must provide" and in the last slice.

## Considered options

- **Gatehouse as the authorization server for agents (chosen), Meldframe as an authorization server of its own that delegates login to Gatehouse (rejected).** The second would let Meldframe show its own consent with the tiers and mint its own tokens, but it puts client registration, redirect validation, code and refresh handling and a token endpoint into the product, the largest attack surface of the design and a second implementation of what Gatehouse exists to be (ADR-0006). The cost of the first is that the consent text is Gatehouse's and the tier scopes need a Gatehouse change; the pending-grant step covers the gap meanwhile.
- **Tiers as scopes in Gatehouse (chosen, behind a switch), tiers only in the grant the person confirms (the fallback until Gatehouse ships the scopes).** The fallback meets everything but "the consent screen lists the risk tiers"; it is not accepted as the end state.
- **Verify agent tokens offline as JWTs plus a local grant table (chosen), introspect on every call (rejected as the default).** Introspection adds a round trip and a dependency on the issuer's availability to every call, and a cache of its answers is a revocation delay; offline checking plus a table read on every call makes revocation exact and keeps Gatehouse off the hot path. The price is that the table, not Gatehouse, decides whether a grant lives, which is why a Gatehouse-side revoke is sent as well and is not relied on.
- **A server-side session row and an opaque cookie (chosen), a stateless signed cookie (rejected), a bearer token held by the page (rejected), a one-time ticket for the socket (rejected).** A stateless cookie cannot be revoked per session, so logout cannot end a socket. A token in page memory or storage is readable by any script on the page and cannot ride a WebSocket handshake except in the URL. A ticket avoids the cookie on the upgrade but puts a credential in a URL and still needs the origin check.
- **`SameSite=Lax` with the `Origin` check (chosen), `SameSite=Strict` (rejected), a CSRF token (rejected).** Strict drops the cookie on the redirect back from Gatehouse; the `Origin` check is needed anyway for the socket; a second token adds a header for no gain.
- **Kind from the credential (chosen), kind from the actor prefix (rejected, ADR-0021), kind from a claim (rejected).** A claim in a token is chosen by whoever configured the client, not by the server.
- **One actor per grant (chosen), one actor per person with a label (rejected), one actor per chat (not possible).** A shared actor would let a revoked agent's history be taken over by its replacement and merge the lanes of an agent and the person who runs it.
- **Delete is Auto for a person and Ask for an agent (chosen), Ask for everyone (rejected).** Ask for everyone deadlocks the editor with one person per workspace.
- **Allow-list sign-up by default (chosen), open sign-up with a cap (available), always open (rejected).** A public pre-alpha must not fill its database or hand out workspaces by accident.
- **What Meldframe takes from the sibling product, and where it differs** (patterns only; names and addresses left out on purpose):

| Pattern | What Meldframe does | Why |
|---|---|---|
| Gatehouse is the authorization server, the product is the resource server | Same | One identity service |
| Audience binding by RFC 8707 `resource` | The token's `aud` must contain the MCP URL, which is also the RFC 9728 `resource` | The MCP authorization specification requires it |
| A local table of connections is read on every request, and the issuer is asked to revoke the grant as well | Same two steps; the deny lifts only on a confirmed revoke or an explicit Allow again | A refresh token can mint later tokens, so only a confirmed revoke or an explicit act may lift it |
| Web login by a server-side flow with a confidential client; the token is dropped after the identity is read | Same, with the attempt kept in the database and bound to the browser by an opaque cookie | No token in the browser |
| `Origin`, else `Sec-Fetch-Site`, on cookie-authenticated mutations | Same rule, extended to every cookie-authenticated WebSocket upgrade, in one pure function | Meldframe authenticates sockets by cookie |
| A `401` with `resource_metadata`, and RFC 9728 metadata | Same; the issuer's metadata is mirrored only if a real client needs it; no CORS on `/mcp` by default | Claude Code is not a browser |
| An unavailable authorization server is a `503`, not a `401` | Same | A client must not drop good credentials in an outage |
| Outbound auth calls over https (loopback http in tests), no redirects, bounded time and size | Same, with the numbers under Bounds | Basic hygiene |
| Tests with an in-process stand-in for the authorization server and a real database schema | A fake provider crate, a store contract, a conformance list that can also run against the real service, a mutation check | The fake must be provably faithful and each rule provably necessary |
| Tiers and people | Tier scopes behind a switch and a cap on each grant; people keyed on `(issuer, subject)` with no email stored; an agent path never creates a person; server-side session rows | The tiers are the product contract (ADR-0010); less personal data; revocable sessions with live sockets (E2.1) |


## Consequences

- **What the code says that the docs do not, and what blocks the design.** Each point was read in the source.
  1. `Authenticator::authenticate(&self, token: &str) -> Option<Principal>` (`crates/integrations/meldframe-http/src/auth.rs`) is synchronous and cannot say "unavailable". JWT verification needs a JWKS fetch and the grant table needs the database, so the seam becomes asynchronous and returns an `Identity` or an error. Seven callers go through `Shared::principal` or `authenticate` with `bearer(req.headers())`: `rest.rs:44`, `ws.rs:36`, `mcp/mod.rs:247`, `meldframe-http-live/src/ws.rs:58`, `meldframe-http-snapshot/src/lib.rs:232`, `meldframe-http-capture/src/upload.rs:54`, `meldframe-http-assets/src/lib.rs:220`. Sixteen files in the workspace name `DevTokens` or `Authenticator`, twelve of them tests that import them from `meldframe_http`, which therefore keeps re-exporting both.
  2. Both sockets authenticate once. `meldframe-http/src/ws.rs` and `meldframe-http-live/src/ws.rs` hold the handshake's principal for the life of the connection and have no session id to revoke by, so nothing can end a socket after a revocation today. `meldframe-http-live/src/ws.rs` is exactly 500 lines, so it is split before it changes.
  3. A browser cannot set `Authorization` on a WebSocket; `browserEnv().openSocket` (`packages/web-link/src/shell.ts`) relies on the dev proxy adding the token, and the editor's actor comes from the build (`__ACTOR__`, `apps/web/src/main.ts`). Real sign-in reads it from `GET /v1/session`.
  4. No route checks `Origin` or sets a cookie; nothing in the server serves static files.
  5. `serve()` in `apps/server/src/main.rs` fails without `MELDFRAME_DEV_TOKENS`. The release rule is `!cfg!(debug_assertions)`, a build setting, overridable by `MELDFRAME_ALLOW_DEV_TOKENS`; E2.1's "disabled in release builds" is only partly true.
  6. Per-agent policy is not represented (`meldframe-module/src/tier.rs`), the gate's closure ignores the principal and `check_tool` reads a read tool's policy without one. The tier cap and the person-versus-agent rule are new code, not settings.
  7. `Approvals::answer` refuses only the actor's own request; its comment leaves who may answer to "the caller (sign-in, M2)". `Server::decide_approval` takes any `&Principal`. Wired naively to OAuth identities it would let one agent answer another's approval; with Ask for everyone and one person per workspace it would also deadlock the editor (the policy paragraph). Approvals live in memory only; a restart forgets them and the agent's retry asks again.
  8. `Principal` has two public fields and lives in `meldframe-host` (1,985 lines); `Principal::new` has 79 call sites in 47 files and the struct literal appears only in `gate.rs`.
  9. `just dev` and the web default use the actor `agent:dev`; a person-only answer needs the development editor to be a person (listed through the adapter; ADR-0021's slice 7 touches the same lines in `scripts/dev.sh`).
  10. The workspace has no table: it is a string in `files.workspace_id` (migration 0003) and in the principal.
  11. `calls` and `CallEntry` hold the actor but no grant, so "whose agent" is not answerable from the log.
  12. The server has no TLS client: `Cargo.lock` has no `rustls`, `ring` or `native-tls`, `reqwest` is a test dependency with default features off, and `sqlx` has no TLS feature. The allow list in `deny.toml` is MIT, Apache-2.0, Unicode-3.0, Zlib and BSD-3-Clause. A rustls stack brings ISC, an OpenSSL-style licence on `ring`, and a webpki root set brings CDLA-Permissive-2.0; `ring` also needs a `[[licenses.clarify]]` entry. Slice 10 lists the exact expressions as `cargo deny` reports them. Production Postgres over TLS is the same decision.
  13. `Reply::unauthenticated` sends a bare `WWW-Authenticate: Bearer` on every route.
  14. The questionnaire proposes "read and write scopes" (two) while the glossary and ADR-0010 have three tiers, and Gatehouse serves none of them. `docs/architecture.md` (row "Room actor") still says the WebSocket transport is not built. `MELDFRAME_MCP_HOSTS` must name the public host or `/mcp` answers 403 to real callers.
  15. The rate-limit clock is monotonic since start (`Config::default`); identity code needs the wall clock (`now()` in `apps/server/src/lib.rs`).
  16. The glossary's **Actor** entry says "a human editor or an agent session" and avoids "User"; it changes to "a person or an agent" and gains Person, Principal, Grant and Sign-in session. `session` is also an identifier in `apps/web/src/main.ts` (a random nonce per page load for idempotency keys) and means something else; the glossary entry says so.

- **Layering.** New crates and kinds: `meldframe-principal` (core), `meldframe-auth` (core: the seam, `Credential`, `Identity`, the revocation bus, the origin decision, cookie parsing, the async seam as boxed futures (`Pin<Box<dyn Future + Send>>`, no `async-trait` crate and no runtime dependency, so `portable-check` passes; the revocation bus is a shared revoked-set with an epoch that sockets poll on their existing tick and per frame, not a channel), the generic `SessionAuthenticator` over a `SessionLookup` trait, which is the only place that mints a `Person`, and the development-token adapter), `meldframe-oidc` (core: pure OIDC and OAuth rules, portable, with injected randomness and clock; it must pass `cargo xtask portable-check`), `meldframe-identity` (core: people, workspaces, sessions, grants, attempts, the grant index, and a synchronous `IdentityStore` seam like `Store` with a memory adapter; it implements `SessionLookup`), `meldframe-app-access` (**core**, in `crates/core/`, like `meldframe-revert` and ADR-0021's `meldframe-activity`: kind `app` may not be depended on by `meldframe-app`, since L2 lets `app` depend on core, engine, integration, os and feature only, `xtask/src/rules.rs`), `meldframe-http-oidc`, `meldframe-http-agents`, `meldframe-http-grants`, `meldframe-http-approvals`, `meldframe-http-web`, `meldframe-identity-wire` and `meldframe-identity-pg` (bin: they hold a network, server or database stack, so they are not portable, like `meldframe-store-pg`), the tool crates named in the budget table, and `packages/web-access` and `packages/web-dev`, each with a `Cargo.toml` that declares `kind = "ui"` and a `rust/lib.rs` like the other `packages/web-*` units.

- **Risks that stay.** A grant is per OAuth client installation, so two chats share a lane and one revoke stops both. The tier cap changes only by revoking and allowing again in M2. Approvals are in memory. A missed back-channel logout leaves a web session valid for up to 24 hours, and a banned person's agent token works until it expires unless its grant is revoked. The Gatehouse-side revoke is best effort and the local table is authoritative. Any script that runs in the editor's origin (a flaw in the page, a compromised dependency) can approve an agent's delete as the person; the CSP, escaping and lint reduce that and do not remove it. The email is not stored, so a later invitation feature must ask for it. A token stolen before a revoke is refused after Allow again, but one stolen after the person's Allow again is valid until it expires or the grant is revoked again. An agent that drives the person's own browser (computer use) holds the person's cookie and is a person to the server, Auto at every tier. The in-memory index assumes one server process.

## What Gatehouse must provide

What Gatehouse documents today is used above; what follows is required of it and could not be confirmed.

- **Missing, needs a change (external work that starts now):** a way to serve resource-specific scopes in discovery, accept them in an authorization request, list them on the consent screen with the owner's wording (consent copy is a fixed function of the four provider scopes and an unknown scope gets a generic line), and carry them in the access token's `scope`. Also whether a resource-bound token can be issued without `openid profile`, so an agent is not asked for a name and an email it does not need.
- **To confirm against a running instance (M2 S0 records them):** the claim names in a resource-bound access token (`scope`, `client_id` or `azp`, `iat`, `jti`, `sid`) and in an ID token; that a client sending `resource` gets a JWT and one that does not gets an opaque token; the `iss` value and whether authorization responses carry `iss`; whether RP-initiated logout needs an `id_token_hint` (the ID token is not stored, so the default is a Meldframe-only logout); refresh behaviour (rotation, lifetime) for a public client; JWKS rotation and cache headers; that the confidential web client and the public MCP client can both be linked to the `<public>/mcp` resource; that the server-to-server grant revoke accepts Meldframe's client; the per-address limits; **what `revoked: false` means** from the revoke endpoint (it is idempotent: a retry after success, or a client that never held a refresh token, may answer `false`), and **whether Gatehouse asks for consent again for each resource**, since a person who already approved the client for another resource might not see a prompt naming Meldframe.
- **To confirm with a real Claude Code:** that it follows the metadata link, sends `resource`, which registration route it uses (a preset client id and fixed callback port, anonymous dynamic registration, or a metadata document) and that it refreshes without asking again.
- **Cannot be tested without it:** back-channel delivery to a public https URL (development has none and relies on the session limits), consent wording as rendered, TLS egress.
