# People sign in through Gatehouse into server-side sessions, agents connect through OAuth grants checked on every call, and the principal carries a kind

M2 replaces development tokens with real identity: E2.1 (a person signs in), E2.2 (Claude Code connects to MCP through OAuth) and what is left of E2.4 (a grant the owner can revoke, a consent that lists the risk tiers, and an owner who can answer an approval). ADR-0006 chose Gatehouse and ADR-0012 chose OAuth grants; neither says how a session lives, how a revoked grant stops a call that is already on its way, how the server tells a person from an agent, or who may call `Server::decide_approval`. This records those choices, which are hard to change once files, actors, grants and sessions exist. It was written from the code, not from the docs: where the two disagree, the code is quoted under Consequences. The design was checked against the sibling product that already signs people in with Gatehouse and serves an OAuth-protected MCP endpoint (patterns only, in the table under Considered options), and against what the Gatehouse documentation and tests state it provides today; what could not be confirmed is listed under "What Gatehouse must provide".

## Decision

- **Three parties, kept apart.** Gatehouse is the authorization server and the identity provider: it signs people in, registers OAuth clients, shows consent, issues and revokes tokens. Meldframe is a relying party for people (OIDC) and a resource server for agents (OAuth 2.1 style bearer tokens, RFC 9728 metadata). Meldframe never mints a credential that a person or an agent could copy: the only secrets it issues are opaque sign-in session ids that live in a cookie the page cannot read. A token that Gatehouse issued to an agent is never forwarded to another service (no passthrough).
- **How a person signs in.** The server runs the authorization code flow with PKCE S256 itself, as a confidential OAuth client (a back-end-for-front-end): `GET /v1/auth/login?return_to=` makes a login attempt (state, nonce and PKCE verifier, 256 bits each, kept in the database and not in a cookie, living 10 minutes), sets a login cookie that holds only the attempt's opaque id (so a login started in another browser cannot be finished in this one), and redirects to the authorization endpoint with `scope=openid profile` (no `offline_access`: the web session needs no refresh token) and the exact registered `redirect_uri`. `GET /v1/auth/callback` deletes the attempt in one statement (single use), compares `state` in constant time, requires `iss` to equal the configured issuer when the response carries it (RFC 9207), exchanges the code at the token endpoint with the client secret and the verifier, and then verifies the ID token itself: RS256 only against the issuer's JWKS, `iss`, `aud` equal to the client id (and `azp` when `aud` has several entries), `exp`, `iat` and `nbf` with a leeway of 60 seconds, `nonce`. The Gatehouse access token is dropped at once; the server keeps only the subject, the Gatehouse session id (`sid`) for back-channel logout, and a display name. Every failure redirects to `/?login_error=<code>` with a short stable code (`cancelled`, `expired`, `state`, `issuer`, `exchange`, `token`, `signup_closed`, `unavailable`) and no detail.
- **Where the session lives, and why a cookie.** A sign-in session is a row (`sign_in_sessions`) and a cookie `__Host-mf_sid` holding 32 random bytes, base64url; the row keeps only the SHA-256 of the id, so a leaked table gives no cookie. Attributes: `Secure; HttpOnly; SameSite=Lax; Path=/`, no `Domain`, `Max-Age` equal to the absolute limit. The page cannot read the id, so XSS cannot copy it. A browser cannot set `Authorization` on a WebSocket, and a token in the query string lands in logs, so the cookie is the one credential the web editor and its sockets share. Limits (working defaults, the owner's to change): 8 hours idle, 7 days absolute, at most 10 sessions per person (the oldest ends when an 11th starts), `last_seen` written at most once a minute. A new id is made at every login, so there is no fixation. Where the public URL is plain HTTP on loopback (development) the cookie is named `mf_sid` without `Secure`, and nowhere else.
- **CSRF and cross-site sockets.** A request that authenticates by cookie and is not a `GET` or `HEAD`, and every WebSocket upgrade, must carry an `Origin` equal to the configured public origin; with no `Origin`, `Sec-Fetch-Site: same-origin` is required; anything else is refused `403 origin_not_allowed` before the body is read. A request that carries an `Authorization` header is judged by the header alone and the cookie is ignored (the two are never mixed). The check is a pure function in `meldframe-auth`, applied once where credentials are read, so no route can skip it. This is new: today nothing in the server checks `Origin` (`crates/integrations/meldframe-http/src/mcp/mod.rs` says so, because there were no cookies), and a cookie-authenticated `/v1/ws` and `/v1/live/{file}` without the check would be open to cross-site WebSocket hijacking. `/mcp` never accepts the cookie, only a bearer token.
- **Logout and revocation end the sockets.** `POST /v1/session/logout` (cookie, CSRF-checked; `{"all": true}` ends every session of the person) marks the row ended, removes it from the in-memory index and publishes its id on a revocation bus; every open `/v1/ws` and `/v1/live` socket of that session closes with WebSocket code 4401 and reason `session_ended`, within one live poll (250 ms by default). Sockets also re-check their session on every frame and every poll, so a missed bus message cannot keep one alive. Gatehouse's back-channel logout (`POST /v1/auth/backchannel-logout`, a `logout_token` JWT: `typ` `logout+jwt`, `events` holds the back-channel member, no `nonce`, `exp` within 120 seconds, `jti` never seen before) ends every Meldframe session with that `sid` (all of the person's when `sid` is absent). Signing out of Gatehouse does not end an agent's grant: an agent keeps working while the person is away, and its grant is ended only on the Connected agents screen or by "revoke all" (owner question 9).
- **The principal has a kind.** `Principal` becomes `{ workspace, actor, kind, tiers, on_behalf_of }` and moves to a new core crate `meldframe-principal`, re-exported from `meldframe-host`, which is 15 lines under its ceiling and would not fit the new fields. `kind` is `Person` or `Agent`; `tiers` is the set of risk tiers the credential may reach (a person has all three, an agent the tiers of its grant); `on_behalf_of` is the person who gave the grant (agents only). **The kind is decided by the kind of credential and nothing else**: a valid sign-in cookie is a `Person`; a valid OAuth access token is an `Agent`, even when the same human is behind both; it is never read from an actor string, a claim the caller chose or a request field. `Principal::new(workspace, actor)` keeps its signature and makes an `Agent` with all tiers, so the 98 call sites and the tests keep compiling and anything not marked a person fails closed; `Principal::person(workspace, actor)` is explicit. A route lists the credentials it accepts: `/mcp` only agent bearer tokens, `/v1/approvals` and `/v1/grants` only the cookie, REST tools, `/v1/ws`, `/v1/live`, snapshots and assets both.
- **How the actor is derived.** A person is `person:<person id>`, where the id is Meldframe's own (`per_` and 20 base32 characters), never the email and never the raw Gatehouse subject, so a change of provider rewrites no history and no actor string holds personal data; the display name is read from `people` when a screen needs it. An agent is `agent:<grant id>` (`gr_` and 20 base32 characters): one grant is one actor and one lane. That differs from the person's actor in what matters: a revoked grant is never reused (re-consent makes a new grant and so a new actor, so old attribution, per-actor undo and idempotency keys cannot be resurrected), the per-principal rate budget and in-flight slots are per grant, and the call log, batches and activity lanes name the grant, not the human. Two chats of one Claude Code installation share one grant, so one actor and one lane; this answers question 1 of ADR-0021 as "one grant, one lane" and says so on the Connected agents screen. A lane per chat is not possible when the OAuth client gives the server no per-chat label, and inventing one from the token would disagree with the call log. The development token's actor stays whatever its entry says.
- **ADR-0021's reviewer rule changes once the kind exists.** ADR-0021 denies by default and lets only actors named in `MELDFRAME_REVIEWERS` set a review, because `Principal` has no kind and a prefix of the actor string cannot be trusted. With this ADR the rule becomes: the principal is a `Person` and a member of the workspace with the owner role (M2 has no other role). `canReview` and the setter read `principal.kind`. The list `MELDFRAME_REVIEWERS` is not deleted at once: it moves into the development-token adapter, where an entry of `MELDFRAME_DEV_TOKENS` is an `Agent` unless its actor is listed (so a test or a development editor can be a person), and it has no meaning for cookie sessions or OAuth tokens. The rule "an actor cannot answer its own request" in `Approvals::answer` stays. This is slice 14 and lands after ADR-0021's review setter.
- **Workspaces and people.** New tables `people` (id, Gatehouse issuer and subject, display name, disabled), `workspaces` (id, name, owner) and `memberships` (workspace, person, role), with the unique key on `(issuer, subject)`, not on email. The first successful sign-in of an unknown subject creates the person and one personal workspace in one transaction (policy `MELDFRAME_SIGNUP`, default `jit`, with a cap `MELDFRAME_MAX_PEOPLE`, default 50, so open sign-up cannot fill the database; `closed` refuses with `signup_closed`). Access control stays at Gatehouse (who may sign in at all). The email is not stored (data minimisation); a name from the `name` claim is kept, at most 128 characters after control and format characters are stripped, else `Person` and four characters of the id. In M2 a workspace has one person (no invitations, no roles beyond owner), so "another workspace cannot see that file" is a test between two people. The session row carries the workspace; the principal's workspace comes only from there (ADR-0006: never from the request). A person with several workspaces, a switcher and invitations are later work; the tables allow them without a migration of the principal.
- **How Claude Code connects.** `/mcp` is an OAuth protected resource per the MCP authorization specification. An unauthenticated or refused call is `401` with `WWW-Authenticate: Bearer resource_metadata="<public>/.well-known/oauth-protected-resource/mcp", scope="meldframe:read meldframe:change meldframe:delete offline_access"` (today `Reply` always sends the bare `Bearer`). The server serves RFC 9728 metadata at the path-inserted URL and at the root form: `resource` is `<public>/mcp` (the canonical identifier, no trailing slash), `authorization_servers` is the Gatehouse issuer, `bearer_methods_supported` is `["header"]`, `scopes_supported` lists the three tier scopes and `offline_access` (without it a client gets a one-hour token and no refresh). A client then reads Gatehouse's own authorization server metadata (RFC 8414 or OIDC discovery), registers (below), and runs the code flow with PKCE and an RFC 8707 `resource` parameter, so Gatehouse issues an RS256 JWT access token whose `aud` is the resource. Meldframe mirrors the authorization server metadata at its own origin only if a real client turns out to ask there; Claude Code is expected to follow the metadata link and this must be shown against the real thing (owner questions 4 and 5).
- **Client registration.** The MCP client is a public OAuth client: authorization code with PKCE S256, `token_endpoint_auth_method` `none`, a loopback redirect, refresh tokens. How it gets a client id is Gatehouse's setting and is chosen by the owner, in this order of preference: a client id the owner registered once for Meldframe and that Claude Code is told to use; Gatehouse's dynamic registration (RFC 7591) switched on for loopback redirects; a client id metadata document. Consent is never skipped for any of them. Meldframe is deliberately indifferent: it sees a `client_id` in the token, derives a grant key from it, and never registers or trusts a client itself. The questionnaire's earlier working default ("public client with PKCE and dynamic client registration", read and write scopes) is replaced by this paragraph and by the next one.
- **Risk tiers on the wire.** The tiers travel as three OAuth scopes, `meldframe:read`, `meldframe:change` and `meldframe:delete` (the glossary's _Avoid_ of "scope" is about the tier concept; the strings are only its wire form, and the code, the screens and the tool text say tier). They are independent, not nested; Read is always present in a grant (standard G3), so a token without it is refused. A scope says how far a grant may reach; the policy per tier (Auto, Ask, Deny, ADR-0010) still decides each call inside that reach, so Delete in a grant is still Ask by default. Effective tiers of a call are the scopes of the presented token intersected with the cap stored on the grant, and a call above them is refused by the gate as `forbidden` (HTTP 403, and on `/mcp` a `WWW-Authenticate: Bearer error="insufficient_scope", scope="meldframe:delete"` so a client can ask for more). The ceiling has no home today: the server builds its gate with `approvals.gate(|_, tier| default_policy(tier))` (`apps/server/src/lib.rs`), which ignores the principal, and `check_tool` reads the registry's policy for a read tool without a principal. The policy closure of the gate takes the principal and so can read `tiers`; `check_tool` takes the principal too. **This depends on Gatehouse**, which today serves only `openid profile email offline_access` and shows any other scope as "Access to your account data" (owner question 5); until it serves the three scopes, an agent token carries none, the grant cap defaults to Read and Change, and the consent line of E2.4 stays open.
- **Consent.** The consent screen is Gatehouse's. Meldframe supplies, as text for the owner to approve, one plain line per tier: "See your designs (Read)", "Create and change designs; changes can be reverted (Change)", "Delete frames and large parts of a design; you are asked first unless you change that in Meldframe (Delete)". The wording is the owner's (question 5); the server holds no wording (standard U5). The Connected agents screen in the editor shows the same three lines with what the grant holds, which is the part the server can show even before Gatehouse does.
- **Agent tokens: short-lived, checked on every call.** The server accepts only a resource-bound RS256 JWT: header `alg` `RS256` (`none`, HS* and every other algorithm are refused, and the key type must be RSA, which closes the key-confusion attack), `kid` present and known; `iss` equal to the configured issuer; `aud` containing the resource; `exp`, `nbf` and `iat` with a leeway of 60 seconds; `exp - iat` at most 24 hours (Gatehouse's default is one hour; a longer lifetime is refused because NFR-6 says short-lived); `sub`, `client_id` (or `azp`), and a space-separated `scope` of at most 512 bytes. Verification is offline against a cached JWKS (fresh for 1 hour, served stale for 24 hours when Gatehouse cannot be reached, one refetch per minute at most for an unknown `kid`), so a call costs no round trip and the authorization server's per-address introspection budget is not shared by all of Meldframe's callers. Introspection (RFC 7662) is kept only as a documented fallback for opaque tokens, off by default: a token without `resource` is opaque and is refused `401 invalid_token`. After the token passes, the call looks up the grant by `(person of sub, client)` in an in-memory index that is written through to the database; a grant that is missing, revoked or in a person with no sign-in refuses the call. **No JWT can be revoked at Gatehouse before `exp`, so the grant table is the revocation**: it is checked on every call, not cached for a period.
- **Grants.** The first valid token of a client for a person who has signed in creates a grant: id, person, workspace (the person's workspace; there is one in M2), a hash of the full client id and a label of at most 128 characters (the client's name from the token or the registration, else the first 32 characters of the id), the tier cap from the token's scopes, `created_at`, `last_used_at` (written at most once a minute), `revoked_at`. A token for a subject with no person is refused `403 grant_requires_sign_in` with a message that says to sign in to Meldframe once: an agent path never creates a person or a workspace. At most 20 active grants per person and 100 per workspace; one more is refused `grant_limit`.
- **Revoking a grant ends it on the next call.** `DELETE /v1/grants/{id}` (cookie only, CSRF-checked, owner of the workspace) sets `revoked_at` in the database first and then in the index in the same step, publishes the grant id on the revocation bus (its open sockets close with 4401), expires its pending approvals as denied, writes an `auth_events` row, and asks Gatehouse to revoke the grant server to server so its refresh token stops (the Gatehouse call is retried with backoff for up to 24 hours; its failure never un-revokes the local grant). From then every call with any token of that grant is `401 grant_revoked`. A token whose `iat` is later than `revoked_at` (plus the leeway) was minted after a new consent, so it makes a new grant with a new id; a token minted before is refused for good. This closes the question the sibling product had to answer with a timer (it kept its local deny for as long as the longest access token could live, because introspection carried no `iat`); with a JWT the rule is exact and needs no timer. If the database cannot record the revocation the route answers `503` and does not claim success; a revocation is never memory-only.
- **Approvals reach the owner.** Two routes, cookie only, `Person` only: `GET /v1/approvals` (the pending approvals of the principal's workspace, oldest first, at most 100, each `{id, actor, file, kind, nodeId, state, createdAt, expiresAt}` and never a command, a name or a text) and `POST /v1/approvals/{id}/decision` with `{"decision": "approve" | "deny"}` (at most 64 bytes, unknown fields refused). They live in a new crate `meldframe-http-approvals` over a small `Approver` trait that `SharedServer` implements in `apps/server/src/approval.rs`. The editor lists them in a panel in the right panel (E5.1's activity lane is the later home) and polls every 5 seconds while the panel is open and once after any `approval_required` reply; a push as an ephemeral frame (ADR-0009) is a follow-up. A request that nobody answers expires to denied after 15 minutes (G5, U7); the panel offers Approve once and Deny only, never "always" (U7).
- **How `decide_approval` is protected.** (1) The route accepts only the sign-in cookie: a bearer token, an agent's included, is `403 person_required`, and `/mcp` has no such tool. (2) The type system: `Server::decide_approval` takes an `Owner<'_>`, a borrowed view that only `Principal::as_owner()` builds and only for a `Person` whose role is owner (M2: every person in their own workspace), so a path that skips the check does not compile; this is the permit idea of standard G2 applied to the answer. (3) The CSRF and `Origin` check above. (4) `Approvals::answer` already refuses another workspace's id as unknown and the actor's own request; it keeps doing so. (5) One answer per approval; a second is `409`. (6) The per-principal bucket and the existing caps (20 open per actor, 100 per workspace) bound the load. (7) The answer is a `decide_approval` entry in the call log, as today, now with the person's actor.
- **Release builds.** A Cargo feature `dev-tokens` (on by default in `apps/server`, listed in the build matrix) gates the whole `DevTokens` adapter and its start-up checks; a release build is made without it and then contains no development-token path, which is stronger than the runtime refusal that exists now (`check_dev_tokens_allowed`, which `MELDFRAME_ALLOW_DEV_TOKENS=1` overrides). With the feature off, `MELDFRAME_DEV_TOKENS` or `MELDFRAME_ALLOW_DEV_TOKENS` set at all is a start-up error naming the variable, so a leftover is loud. `MELDFRAME_ALLOW_DEV_TOKENS` is removed with the slice that wires Gatehouse (E2.1 asks for exactly that); until then it stays. The seed scripts keep their own release refusals. A server with neither the feature nor an OIDC configuration does not start: it is never open. Today `serve()` insists on `MELDFRAME_DEV_TOKENS` (`apps/server/src/main.rs`), so the server cannot be started without them.
- **Storage.** Migration numbers are after ADR-0021's 0007 and are taken from the next free number when each slice lands (0008 to 0010 here). `0008_identity.sql`: `people`, `workspaces`, `memberships`, `sign_in_sessions` (`id_hash` primary key, person, workspace, `idp_sid`, `created_at_ms`, `last_seen_ms`, `ended_at_ms`, `end_reason`), `login_attempts` (id, state, nonce, verifier, return path, `expires_at_ms`), `backchannel_jti` (jti, `expires_at_ms`). `0009_agent_grants.sql`: `agent_grants` (id, person, workspace, `client_hash`, `client_label`, `tier_cap`, `created_at_ms`, `last_used_ms`, `revoked_at_ms`, `idp_revoked_at_ms`, unique `(person, client_hash, created_at_ms)`), and the Gatehouse-revoke retry state. `0010_auth_audit.sql`: `auth_events` (append-only like `calls`, a trigger refuses an update; kind, person, workspace, grant, outcome code, `at_ms`, address key) and a nullable `grant_id` on `calls` and in `CallEntry`, so the call log can say whose agent a call was without holding content. Expired attempts, ended sessions and used jtis are deleted by a job that runs hourly; `auth_events` are kept 90 days (the owner's to change, question 8). The sqlx migrator in `PgStore` owns the schema, so the new tables go through it; `PgStore` gains a small accessor so a new crate can run queries on its pool and runtime.
- **Keys, clock, replay, rate limits.** The cookie id needs no signing key (it is random and looked up), so there is no cookie key to rotate; the OAuth client secret comes from `MELDFRAME_OIDC_CLIENT_SECRET` or a file named by `..._FILE`, never argv, never logged, never in an error text, and rotating it is a restart (Gatehouse invalidates the old secret at once, so there is no overlap to design). Signing keys of the issuer are rotated by Gatehouse; the JWKS cache above handles that (an unknown `kid` forces one refetch, then a token with it is refused). Time: the JWT and session checks use the wall clock the server already has (`now()` in `apps/server`), injected as a trait so tests move it; the rate limiter's monotonic clock is not used for them. A leeway of 60 seconds each way covers skew; a server whose clock is more than that off fails every token and says `token` in the log, not in the reply. Replay: an authorization code is single use at Gatehouse and the login attempt is deleted on first read; a back-channel `jti` is remembered for its 120 seconds plus the leeway; an agent token is a bearer credential and is not one-time by design, which is why the grant table, the short life and the audience binding are the controls. Rate limits per client address (the existing `client_ok` bucket, then these): login 10 a minute, callback 20, logout 30, back-channel 60, grants and approvals routes the per-principal bucket; failed token verifications are remembered by the SHA-256 of the token for 10 seconds so a loop of bad bearers costs one verification; at most 1,000 live login attempts and 10 per address.
- **Audit.** `auth_events` records sign-in, refused sign-in (with the code), sign-out, back-channel end, grant created, grant revoked, grant refused (`grant_revoked`, `grant_requires_sign_in`, `grant_limit`), and Gatehouse revoke outcome. Names, ids and codes only: no token, no email, no name, no claim, as with the call log. The decision on an approval stays in the call log.
- **Bounds on every input.** Cookie value 64 bytes; bearer token 4,096 bytes; ID token and logout token 8 KiB; `state` and `code` 512 bytes; `return_to` a relative path of at most 512 bytes starting with a single `/`, no `//`, no `\`, no control character, else `/`; `login_error` one of the eight codes; every Gatehouse response 64 KiB read with a limit and never more than 16 keys in a JWKS; outbound calls https only (loopback http for tests), no redirect followed, 5 second timeout, 10 seconds for a whole callback; `sub` 255 bytes, `client_id` 2,048 bytes, display name 128 characters, label 128 characters; scope string 512 bytes and at most 16 scopes, unknown scopes ignored; decision body 64 bytes; grant id and approval id must match their format before any lookup; at most 20 active grants per person, 10 sessions per person, 1,000 login attempts. A value over a bound is refused with a short stable code and costs no outbound call.
- **Failure modes** (fail closed; unavailable is `503` and retryable, never `401`, so a client does not discard good credentials during an outage; the sibling product learned this the hard way). Gatehouse unreachable at login: a `login_error=unavailable` page, existing sessions unaffected. JWKS unreachable: cached keys (up to 24 hours stale), then `503 identity_unavailable` for tokens with an unknown `kid`. Database unreachable: sessions and grants already in the index keep working until revoked (the index is the hot path and revocation writes the database first), new sign-ins, grants and revocations answer `503`; a logout always ends the session in memory and the cookie even if the row write is retried later. Unknown or bad token: `401 unauthenticated` with the challenge. Revoked grant: `401 grant_revoked`. Tier above the grant: `403 forbidden` with `insufficient_scope`. A row or claim that is not understood (an unknown tier name in `tier_cap`, a malformed session row) grants nothing: only the tiers that parse count, and none leaves Read refused too (G5).
- **Testing without a live Gatehouse.** (1) Pure crates with table-driven tests, including a hostile corpus (algorithm `none`, HS256 signed with the public key as the secret, `aud` missing or an array, wrong `iss`, expired, `nbf` in the future, no `kid`, unknown `kid`, a token of 5 MB, duplicate claims, non-UTF-8, a `scope` of 10,000 entries). (2) A fake OIDC provider crate, `meldframe-fake-idp` (kind tool, axum): discovery, JWKS with key rotation, authorize (signs a scripted person in), token, userinfo, end-session, back-channel delivery, dynamic registration, and switches for every failure above (outage, slow, 500 with an empty body, wrong issuer, wrong audience, clock skew). (3) A store contract suite run against the memory adapter and Postgres, as `meldframe-store-contract` does for files. (4) A conformance list that runs against the fake always and against a real Gatehouse when `MELDFRAME_IDP_CONTRACT_URL` is set (it prints `SKIPPED` otherwise, as the Postgres tests do), so the fake cannot drift unnoticed. (5) `tools/mutation-check-auth.sh` in the style of the sync mutation check: switch one rule off at a time (the audience check, `iat` against `revoked_at`, the origin check, the kind check on `decide_approval`, the re-check on an open socket, algorithm pinning, single use of an attempt) and fail if the tests still pass. (6) Browser checks by hand against the real server and the fake provider (`apps/web/scripts`): sign in, edit, a socket from a wrong origin refused, logout closes the socket, a second person in another workspace cannot read the first person's file. What needs the real Gatehouse and a real Claude Code is listed under "What Gatehouse must provide" and in the plan's last slice.

## Considered options

- **Gatehouse as the authorization server for agents (chosen), Meldframe as an authorization server of its own that delegates login to Gatehouse (rejected).** The second would let Meldframe show its own consent with the tiers and mint its own tokens, but it puts client registration, redirect validation, code and refresh handling, and a token endpoint into the product, which is the largest attack surface of the whole design and a second implementation of what Gatehouse exists to be (ADR-0006). The cost of the first is that the consent text is Gatehouse's and the tier scopes need a Gatehouse change.
- **Tiers as scopes in Gatehouse (chosen), tiers only in a Meldframe grant record (kept as the fallback until Gatehouse ships the scopes).** The fallback meets everything but the sentence "the consent screen lists the risk tiers": the person would approve at Gatehouse without seeing them and see them afterwards in Meldframe. It is not accepted as the end state.
- **Verify agent tokens offline as JWTs plus a local grant table (chosen), introspect on every call (rejected as the default).** Introspection was the sibling's choice because it also needed the email; it costs a round trip per cache miss, shares the issuer's per-address budget across every caller, answers a bare 500 for some forged tokens, and a 30 second positive cache is a 30 second revocation window. Offline checking plus a table checked on every call makes revocation exact and keeps Gatehouse off the hot path. The price is that the table, not Gatehouse, is the authority on whether a grant lives, which is why a Gatehouse-side revoke is sent as well and is not relied on.
- **A server-side session row and an opaque cookie (chosen), a stateless signed cookie (the sibling's, rejected), a bearer token held by the page (rejected), a one-time ticket for the socket (rejected).** A stateless cookie cannot be revoked per session, so logout cannot end a socket and a stolen cookie lives to its expiry; the sibling accepts that because it has no live sockets and rotating a server secret is its only kill switch. A token in page memory or storage is readable by any script on the page and cannot ride a WebSocket handshake except in the URL. A ticket avoids the cookie on the upgrade but puts a credential in a URL and still needs the origin check.
- **`SameSite=Lax` with the `Origin` check (chosen), `SameSite=Strict` (rejected), a CSRF token (rejected).** Strict drops the cookie on the redirect back from Gatehouse and on links from other sites; the `Origin` check is needed anyway for the socket; a second token adds a header the web editor would have to carry for no gain.
- **Kind from the credential (chosen), kind from the actor prefix (rejected), kind from a claim (rejected).** ADR-0021 already rejected the prefix; a claim in a token is chosen by whoever configured the client, not by the server.
- **One actor per grant (chosen), one actor per person with a label (rejected), one actor per chat (not possible).** A shared actor would let a revoked agent's history be taken over by its replacement and would merge the lanes of an agent and the person who runs it, which ADR-0021's open question 1 warned about.
- **Pattern by pattern, against the sibling product** (public-safe summary; names and addresses left out on purpose):

| Sibling pattern | What Meldframe does | Why |
|---|---|---|
| Gatehouse is the authorization server, the product is the resource server | Same | One identity service, no second authorization server to secure |
| The MCP resource verifies a bearer by introspection (cache 30 s, rejections 10 s, one upstream call shared by concurrent requests, key is a hash of the token) | Verify a resource-bound JWT offline against a cached JWKS; keep the hash-keyed negative cache and single flight for failures; introspection only as an off-by-default fallback | Revocation must not wait on a cache; no per-call round trip; the issuer limits introspection per address |
| Audience binding by RFC 8707 resource, `aud` must contain the MCP URL | Same, and the same URL is the RFC 9728 `resource` | Required by the MCP authorization specification; stops tokens meant for other services |
| A local table of connections checked on every request (primary key lookup) denies a revoked client at once; the issuer is asked to revoke the grant as well; the local deny outlives the longest access token because introspection has no `iat` | Same two steps; the deny is permanent per grant, and a token with `iat` after `revoked_at` is a new consent and makes a new grant | JWTs carry `iat`, so the timer is not needed and a revoked grant is never revived by waiting |
| Client scopes are only the provider's (`openid profile email offline_access`); an optional required scope and write scope exist but are off by default | Three tier scopes on the resource, a cap on the grant, the gate reads it; needs a Gatehouse change | The tiers are the product's contract (ADR-0010) and E2.4 wants them on the consent screen |
| A person is found by lower-cased verified email; the subject is pinned on first login; unknown people are refused on the MCP path; sign-up policy is open or allow-listed | Key on `(issuer, subject)`; no email stored; an agent path never creates a person; sign-up policy `jit` or `closed` with a cap | Email can be recycled; less personal data; the agent path must not create people |
| Web login is a server-side flow with a confidential client; the code is exchanged server to server; the token is dropped after the identity is read | Same | No token in the browser; no CORS needed at the token endpoint |
| The session is a stateless signed cookie holding the person id and an expiry; logout clears the cookie; rotating the server secret ends all sessions | A server-side row and an opaque cookie, so a session can be ended and its sockets closed | Meldframe has live sockets and requires revocable sessions (E2.1) |
| PKCE verifier and state travel in a short-lived signed cookie | Kept in the database, bound to the browser by an opaque cookie | The verifier never reaches the browser; attempts are single use and countable |
| CSRF: a cookie-authenticated mutation needs the portal's own origin (`Origin`, else `Sec-Fetch-Site`) | Same rule, extended to every WebSocket upgrade, in one pure function applied where credentials are read | Meldframe authenticates sockets by cookie; the sibling has none |
| `/mcp` answers 401 with `resource_metadata`; serves both metadata documents; mirrors the issuer's authorization server metadata at its own origin for clients that look there; CORS allow-list for browser-based MCP clients | The 401 challenge and RFC 9728 metadata; the mirror only if a real client needs it; no CORS on `/mcp` by default, an allow-list setting for inspectors | Claude Code is not a browser; fewer open doors |
| The authorization server being down is `503`, not `401`, and is never cached | Same | A client must not throw away good credentials in an outage |
| Outbound auth calls: https only (loopback http for tests), no redirects, bounded time, response read with a limit, the provider's error text filtered to a short charset | Same, with the numbers under Bounds | Server-side fetches of attacker-influenced URLs are the usual SSRF route |
| Tests: an in-process stub of the authorization server and a real database schema; one test per failure (outage, wrong audience, wrong issuer, unverified email, subject mismatch, caches, concurrency) | A fake provider crate, a store contract on memory and Postgres, a conformance list that can also run against the real service, a mutation check | The fake must be provably faithful, and each rule must be proven necessary |
| An audit row per login per workspace | `auth_events` for every sign-in, grant and revocation event, with a 90 day retention | One table, names and codes only |

## Consequences

- **What the code says that the docs do not, and what blocks the design.** Each point was read in the source.
  1. `Authenticator::authenticate(&self, token: &str) -> Option<Principal>` (`crates/integrations/meldframe-http/src/auth.rs`) is synchronous and cannot say "unavailable". JWT verification needs a JWKS fetch and the grant table needs the database, so the seam becomes asynchronous and returns an `Identity` or an error. All eight callers go through `Shared::principal` or `Shared::authenticate` and `bearer(req.headers())`: `rest.rs`, `ws.rs`, `mcp/mod.rs`, `meldframe-http-live` (`lib.rs`, `ws.rs`), `meldframe-http-snapshot`, `meldframe-http-capture/src/upload.rs`, `meldframe-http-assets`.
  2. Both sockets authenticate once. `meldframe-http/src/ws.rs` (`serve(socket, s, who)`) and `meldframe-http-live/src/ws.rs` hold the handshake's principal for the life of the connection and have no session id to revoke by, so today nothing can end a socket after a revocation.
  3. A browser cannot set `Authorization` on a WebSocket; `browserEnv().openSocket` in `packages/web-link/src/shell.ts` relies on the Vite proxy adding the development token (`apps/web/dev/proxy-guard.ts`). Real sign-in needs the cookie path described above, which also means the web editor's `actor` can no longer come from the build (`__ACTOR__` in `apps/web/src/main.ts`) and is read from `GET /v1/session`.
  4. No route checks `Origin` or sets a cookie (`mcp/mod.rs` line 111 says so for `/mcp`). That comment stays true for `/mcp` only.
  5. `serve()` in `apps/server/src/main.rs` fails without `MELDFRAME_DEV_TOKENS`: the server cannot start with real identity until slice 13. The release rule is `!cfg!(debug_assertions)`, which is a build setting, not a feature; a profile with debug assertions on is "not release".
  6. Per-agent policy is not represented (`crates/core/meldframe-module/src/tier.rs` says so), the server's gate ignores the principal, and a read tool's policy is read without one (`check_tool`). The tier ceiling is new code in the gate's closure and in `check_tool`, not a setting.
  7. `Approvals::answer` (`meldframe-approvals/src/approvals/answer.rs`) refuses only the actor's own request; its comment says who may answer "is the caller's call (sign-in, M2)". `Server::decide_approval` takes any `&Principal`. Wired naively to an OAuth identity it would let one agent of a workspace answer another's approval. Approvals live in memory only; a restart forgets them (the agent's retry asks again, which is acceptable and should be said).
  8. `Principal` has two fields and lives in `meldframe-host` (1,985 lines); `Principal::new` is called 98 times and the struct literal only in `gate.rs`, which is why the new fields can arrive without churn.
  9. `just dev` sets the development token's actor to `agent:dev` and the web default actor is `agent:dev` (`scripts/dev.sh`, `apps/web/vite.config.ts`). Once an approval answer needs a person, the development editor must be a person: the dev entry is listed as one through the adapter's list (ADR-0021's slice 7 touches the same lines).
  10. The workspace has no table: it is a string in `files.workspace_id` (migration 0003) and in the principal. Membership, a person's workspace and a workspace name have nowhere to live until `0008`.
  11. `calls` and `CallEntry` hold the actor but no grant or person, so "whose agent made this call" cannot be answered from the log today.
  12. The server has no TLS client: `Cargo.lock` has no `rustls`, `ring` or `native-tls`, `reqwest` appears only as a test dependency with default features off, and `sqlx` is built without a TLS feature. The licence allow list in `deny.toml` is MIT, Apache-2.0, Unicode-3.0, Zlib and BSD-3-Clause; the usual TLS stack brings ISC and OpenSSL-style licences. Talking to Gatehouse over https is therefore an owner decision under D2 (question 10), and a Postgres over TLS in production is the same decision.
  13. `Reply::unauthenticated` sends a bare `WWW-Authenticate: Bearer` for every route, so `/mcp` needs its own reply with the metadata link.
  14. `docs/owner-questionnaire.md` proposes "Meldframe read and write scopes" (two), the glossary and ADR-0010 have three tiers, and Gatehouse serves none of them. `docs/architecture.md` (row "Room actor") still says the WebSocket transport is not built. The MCP `Host` allow list (`MELDFRAME_MCP_HOSTS`) must name the public host or `/mcp` answers 403 to every real caller.
  15. The server's rate-limit clock is monotonic since start (`Config::default`); the identity code needs the wall clock (`now()` in `apps/server/src/lib.rs`), so the two must not be confused.
- **Crate sizes (counted as `cargo xtask size-check` counts, tests included).** `meldframe-http` is at 1,999 and must shrink first: moving `auth.rs` (115 lines) out in slice 2 leaves it near 1,925 and the new code there stays under 25 lines. `apps/server` is at 1,913, so its wiring is at most 25 lines, bought by moving `open_assets` (about 22 lines) into `meldframe-http-assets`, which already owns `assets_dir`; the identity wiring itself lives in the new crate `meldframe-http-oidc` (`wire(...)` returns the authenticator and the routes). `meldframe-app` is at 1,882, so the access state goes into `meldframe-app-model` (847 lines, plain data) and a new `meldframe-app-access`, with at most 40 lines of composition in `meldframe-app`. `meldframe-mcp-tests` (1,983), `meldframe-http-tests` (1,906), `meldframe-server-tests` (1,950) and `meldframe-live-tests` (1,791) get no new tests; a new tool crate `meldframe-identity-tests` holds them and reaches helpers by path, as `meldframe-export-http-tests` does. `meldframe-host` (1,985) shrinks by the 15 lines of `Principal`. `apps/web` is over its ceiling (allow-list entry 4,864, which may only go down), so its edits must be net negative; the new screens live in a new package `packages/web-access`.
- **Layering.** New crates and kinds: `meldframe-principal` (core), `meldframe-auth` (core: the seam, `Credential`, `Identity`, the revocation bus, the origin decision, cookie parsing), `meldframe-oidc` (core: pure OIDC and OAuth rules, portable, with injected randomness and clock), `meldframe-identity` (core: people, workspaces, sessions, grants, attempts, the store seam with a memory adapter), `meldframe-http-oidc`, `meldframe-http-agents`, `meldframe-http-approvals` and `meldframe-identity-pg` (bin: they hold a network or database stack, so they are not portable, like `meldframe-store-pg`), `meldframe-fake-idp` and `meldframe-identity-tests` (tool), `meldframe-app-access` (app), `packages/web-access` (ui). The development-token adapter moves into `meldframe-auth` behind the `dev-tokens` feature so the release build can leave it out.
- **Docs and tools that change with it.** `GLOSSARY.md` gains Person, Principal, Grant (an agent's OAuth grant, one actor) and Sign-in session, with _Avoid_ lines (Session is already avoided for a Room's live channel; a sign-in session is a different thing and the entry says so); `docs/error-codes.md` gains `unauthenticated` (challenge), `invalid_token`, `grant_revoked`, `grant_requires_sign_in`, `grant_limit`, `person_required`, `origin_not_allowed`, `identity_unavailable`, `signup_closed` and the close reason `session_ended`; `docs/architecture.md`, `docs/epics.md` (E2.1, E2.2, E2.4 boxes), `docs/decisions.md` (the rows the owner confirms), `AGENTS.md` (the new commands, `MELDFRAME_OIDC_*`), `docs/mcp-tools.json` and `skills/meldframe/SKILL.md` (`whoami` gains `kind` and `tiers`; the skill says what a revoked grant looks like), `.env.example` and `scripts/dev.sh`.
- **Risks that stay.** A grant is per OAuth client installation, so two chats share a lane and one revoke stops both. The tier cap can be lowered only by revoking and reconnecting in M2. Approvals are in memory. Sessions are valid in memory while the database is down, so a session ended during an outage is ended in memory at once and in the table when the database returns. The Gatehouse-side revoke is best effort and the local table is authoritative. The email is not stored, so a later invitation feature must ask for it.

## What Gatehouse must provide

The Gatehouse repository became readable during this work. What its documentation and tests state is used above; what follows is what could not be confirmed from them and what is missing.

- **Missing, needs a change:** a way to serve resource-specific scopes (`meldframe:read`, `meldframe:change`, `meldframe:delete`) in discovery, accept them in an authorization request, list them on the consent screen with the owner's wording (consent copy is a fixed function of the four provider scopes today, and unknown scopes read as "Access to your account data"), and carry them in the access token's `scope` claim. Also whether a resource-bound token can be issued without `openid profile`, so an agent is not asked for a name and an email it does not need.
- **To confirm against a running instance:** the claim names in a resource-bound access token (`scope`, `client_id` or `azp`, `iat`, `jti`, `sid`); that a client sending `resource` gets a JWT and one that does not gets an opaque token; the `iss` value and whether authorization responses carry `iss`; whether RP-initiated logout needs an `id_token_hint` (we do not store the ID token, so the default is a Meldframe-only logout); the refresh token behaviour (rotation, lifetime) for a public client; JWKS rotation and cache headers; that the confidential web client and the public MCP client can both be linked to the `<public>/mcp` resource; that the server-to-server grant revoke accepts Meldframe's client; the per-address limits (token, authorize, introspect, userinfo) against the rates above.
- **To confirm with a real Claude Code:** that it follows the protected-resource metadata link and the `scope` in the challenge, sends the `resource` parameter, uses the registration path chosen by the owner (a pre-registered client id, dynamic registration for a loopback redirect, or a metadata document), and refreshes without asking again.
- **Cannot be tested at all without it:** back-channel delivery to a public https URL (a loopback or private address is refused by Gatehouse, so development has none and relies on the session limits), real consent wording as rendered, and TLS egress from the server.

## Open questions for the owner

Only the owner can decide or provide these; the working default is in brackets.

1. **Which Gatehouse tenant and issuer Meldframe uses**, for development, for the test environment and later for production [a labs instance for development].
2. **A confidential OAuth client for the web sign-in:** its registration at Gatehouse, the redirect URI (`<public>/v1/auth/callback`), the post-logout URI, a back-channel logout URL (public https only), and where the client secret is kept.
3. **The public origin of Meldframe** (domain, https, one origin for the web editor and the API, which `__Host-` cookies and the `resource` identifier require). Nothing public is created without an owner order (`AGENTS.md`), and decision 13 postpones hosting [loopback only until the owner names one].
4. **How Claude Code gets an OAuth client id:** a client the owner registers once, dynamic registration switched on at Gatehouse for loopback redirects, or a client id metadata document [a pre-registered public client; no open registration].
5. **Tier scopes and the consent wording:** whether Gatehouse adds three resource scopes, their final names, and the three lines of text the consent screen shows (proposed above). Until then E2.4's consent line stays open.
6. **The resource identifier** `<public>/mcp` registered at Gatehouse, and the client link to it.
7. **Sign-up policy:** anyone Gatehouse admits gets a personal workspace (`jit`), or only people the owner provisions (`closed`); and the cap [`jit`, 50 people].
8. **Lifetimes and retention:** 8 hours idle and 7 days for a sign-in session, the longest access token accepted (24 hours; Gatehouse issues one hour), 90 days for `auth_events`.
9. **Whether signing out of Gatehouse should also end agent grants** [no: grants end only on the Connected agents screen], and whether revoking at Meldframe must also revoke at Gatehouse [yes, best effort].
10. **Licences for outbound TLS and RS256:** allow ISC and the OpenSSL-style terms of a rustls stack in `deny.toml`, or use the system OpenSSL, or terminate egress elsewhere; the same decision covers Postgres over TLS [rustls with the licences added, if the owner agrees; `jsonwebtoken` with its pure Rust backend or `rsa` with `sha2`, to be settled with `cargo deny` in slice 5].
11. **One lane per grant, or per chat** (ADR-0021 open question 1) [per grant; per chat is not possible without a label from the client].
12. **Several workspaces per person, invitations and roles:** out of M2 [one personal workspace, one role].
13. **Whether to keep the person's email** (needed later for invitations) [no].
14. **Per-agent policy overrides** (ADR-0010) in the Connected agents screen [not in M2].
15. **Removing `MELDFRAME_ALLOW_DEV_TOKENS`** with the Gatehouse wiring, as E2.1 asks [yes].
