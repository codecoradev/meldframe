# Variables are a second table of the file, and a field is a literal or a binding

ADR-0004 fixed the model (flat, stable ids, resolution in the core). This one records how E3.3 builds it, where that chose between options that are hard to undo once files hold variables.

## Decision

- **A file is `Doc { nodes, vars }`.** The collections and variables are a second table beside the node tree, not nodes. Seven variable commands (`addCollection`, `removeCollection`, `addMode`, `removeMode`, `addVariable`, `removeVariable`, `setVariableValue`) are members of the one `Command` enum, so they travel the same op log, `ifSeq`, atomic batch, room, replica and per-actor undo as node commands. `ifSeq` names a variable as `$var:<id>` and a collection as `$col:<id>` (a node id cannot hold a `$`), and a conflict says so.
- **Model.** A collection has at least one mode; the first is the default. A variable has a type (`color` or `number`; strings, shadows, gradients and typography come as new values of the enum), a slash-path name unique in its collection (`color/brand-500`: lowercase segments, single hyphens), and exactly one value per mode of its collection. A value is a literal of the type or an alias `{"var": id}` to a variable of the same type. The "one value per mode" rule is an invariant, kept by `addMode`, which copies the values of the mode named in `copyFrom` (the default mode if absent), and by `removeMode`, which drops them. So `setVariableValue` always replaces a value and its inverse is exact, and no resolution needs a fallback to another mode.
- **Binding.** `Bind<T> = T | {"var": id}` is the type of `fill` (a colour, `none`, or a colour variable), `radius` and `opacity` (a number, or a number variable). A file that has only literals is unchanged on the wire, so `SCHEMA_VERSION` stays 1 (ADR-0013). Fields that layout reads (`gap`, `padding`, margins, sizes, `fontSize`) are not bindable yet: layout runs on the stored numbers and the canvas does not apply layout yet (the `FROM_LAYOUT` rows of the coverage table), so a binding there would need a resolve step before layout. The set of bindable fields is one list in `meldframe-variables` (`node_bindings`), and the coverage table of `meldframe-render` has a `bindable` column that a test compares with it.
- **Refused at command time**, each with its own code (`docs/error-codes.md`): a missing variable, collection or mode, a type mismatch, an alias that closes a cycle (in any mode) or makes a chain of more than 16 steps, bad or taken names, values that are not one per mode, the default mode removed or a mode put before it, a collection that still holds variables, and a variable that a node field or an alias still uses. Removal never detaches: the caller unbinds first. That keeps `removeVariable` undoable with an exact inverse and a single command per effect.
- **Resolution** is one function, `meldframe_variables::resolve(vars, id, choice)`. An alias is followed with the mode picked for the collection of the variable it points at, as in the design tools, so one switch of `appearance` reaches what it aliases in other collections. A chain with a cycle or over 16 steps, or a missing variable, resolves to nothing and never panics. The render step (`resolve_with`) paints a bound field with the resolved value, holds a resolved number to the range of its field, and paints the default of the field when the binding cannot be resolved.
- **The mode is view state.** `AppState::modes` maps a collection to the mode picked; `Action::SetMode` writes no op and no undo step and the file does not change. The canvas paints `App::scene`, which is the render step over the document and the modes.
- **Undo and sync.** The unit of last writer wins is `(variable, mode)`: a remote value, removal or re-creation drops the steps of my history that wrote it (`meldframe-undo` `remote_vars`). In the replica a variable and a collection are pseudo nodes in the footprint, so an undo depends on the pending ops it was built on. Variables get no corrections (see the glossary): a stale undo of a value that another actor wrote after it is not set right.
- **Persistence.** The op log keeps its shape, but it is not backward readable: `Command` gains seven variants and a node op can carry `{"var": id}` in `fill`, `radius` or `opacity`. A snapshot of a file without variables stays the JSON array of nodes it always was; one with variables is `{"nodes": [...], "variables": {...}}`, and both read back (`meldframe-store-pg` `state`, which now reports the real parse error instead of "did not match any variant"). No migration. `SCHEMA_VERSION` stays 1: nothing reads the column back yet (only `ops`, `files` and `snapshots` write it), so a second value would refuse nothing. **A rollback to a server of before this change is therefore not clean.** The old server cannot parse an op log that holds a variable command or a binding, nor a snapshot of the object form, and it says "bad snapshot state" or a plain parse error, not a refusal that names the version. The way back is to drop the snapshots and the ops of files that use variables before the old server starts, or to restore them from a backup; files that never used variables read as before. A distinct `schema_version` for the object form, checked on read, is the proper fix and is left for the slice that first reads the column (a migration and a refusal with its own code).
- **Risk tier.** Every variable command is Change, removals included: `removeVariable` is refused while anything uses the variable, and its undo is `addVariable`. The activity log records them as the kind `variable`. A file-wide restyle by one `setVariableValue` (a colour that every bound node shows) is accepted as Change tier on purpose: it is one op, it is undone by one undo, and the person or agent cannot reach more than the file they already edit. A gate that wants approval for a change of reach would need a footprint of the nodes a variable touches; that is a design decision for the gate (ADR-0010), not made here.
- **Cost of an op against the quota.** The workspace quota counts one op for each variable command, as for a node command. The work is not the same: `removeVariable`, `addVariable` and `setVariableValue` read the nodes (who uses the variable) and the alias graph, which is O(nodes) and O(variables times modes), and a check of an alias is linear in the file (`Aliases`, one pass in dependency order, so a layered file with many paths costs as many steps as it has variables and aliases). The counts are bounded (32 collections, 16 modes, 5,000 variables) and the load check is linear too, so the worst op is bounded, but a count that weighs an op by its work is not built. The in-use error names at most five of the users.
- **Undo against a removal by another actor.** When another actor removes a variable (which they may only when nothing uses it in the file they see), my steps that would bind or alias it again are rewritten: a field of an `updateNode` bound to it is let go, a node added again takes the default of that field, and a `setVariableValue` or `addVariable` that aliases it goes. Otherwise the undo is refused for ever with `E_VARIABLE_NOT_FOUND` and blocks the stack. A step whose undo is left empty by this is passed by the next undo, as for a node another actor deleted. A new mode that another actor adds copies the default mode of its collection into a variable I bring back, as `addMode` does.
- **Revert and checkpoints (ADR-0016) cover nodes only.** `meldframe-revert` replays the confirmed log on the nodes of the load. A variable command in a batch is not taken back by a revert: the node commands are, and each variable command is listed in `skipped` (`what` is `variable`, `node` holds the id of the variable or collection, reason `not_applicable`), so `Event::Reverted` does not report a full revert that is not one. A log that touches variables loaded from the snapshot does not replay, so the revert is refused instead of wrong. A restore of a checkpoint compares nodes and plans node commands only; it leaves the variables as they are. Reverting variable changes is open for a later slice.

## Considered options

- Generalise the node store to entities of several kinds (the design note's recommendation): rejected for now. It would have rewritten `Vec<Node>` through the replica, the footprint and the corrections for a second table whose only needs are the same order, `ifSeq` and undo, which the commands above already give.
- Variables as nodes of the tree: rejected. A node would carry a map of values per mode, every consumer of the tree would have to skip them, and "node" would stop meaning an element of a frame.
- A side map `bindings: {field: id}` beside the literal fields (purely additive, no change of any field type): rejected. It is the smaller change, but it lets a literal and a binding disagree in one node and it is not the `T | {var: id}` that ADR-0004 and the epic fix.
- A `detach` flag on `removeVariable` that bakes the resolved values into the bound fields (design note 5.2): deferred; it can be added later as another command without changing these.

## Consequences

- Every function that applied a command to `Vec<Node>` has a twin for `Doc`; the node-only ones stay for callers that hold no variables and refuse a variable command (`E_NO_VARIABLES`) or a binding.
- Open for later slices: bindings for layout fields, gradient stops, shadows and text; the Variables panel and the import (E3.4); the MCP surface (`apply_commands` does not list the variable commands yet, and no tool reads the variables); export as `var(--...)` (E4.1); frame-level mode overrides and the page override of the design note (4.2).
