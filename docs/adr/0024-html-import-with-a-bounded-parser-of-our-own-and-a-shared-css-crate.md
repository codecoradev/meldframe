## Decision

- **A parser of our own, bounded by construction, no crate.** The feature crate reads HTML with a tolerant tree builder over a documented subset: void elements, the usual implied end tags (`p`, `li`, `td` and the like), character references and comments dropped. It is not the full HTML parsing algorithm. It reads CSS with a scanner of rules, simple selectors (type, `.class`, `#id`, `[attr]`, `[attr=value]`, `*`, compounds, descendant and child combinators, selector lists, and the export's `[data-node="id"]` with CSS escapes), the cascade (specificity, then source order, `!important` over normal), inheritance and a small fixed table of browser defaults, and it decodes the Tailwind forms that `crates/features/export/export/src/tw.rs` writes, back to declarations. It opens nothing and runs nothing: `<script>` is not read, and `<link>`, `@import`, `@font-face`, `url()` and `src` are never followed, only listed. The work is counted (as `TEXT_WORK` counts the scan of `variables-import`) so a test can assert that it is bounded.
- **The limits, as the starting numbers.** The note proposes 256 KiB of input, 100 Commands, the report bounds (200 entries, 32 KiB, a message of 240 characters, a value of 80) and the cut of a listed `src` to 200; this ADR takes those as written. It borrows two numbers: the nesting depth of 64 from `MAX_DEPTH` in `crates/features/export/export/src/emit.rs` and the 1,000 bytes of a value or an attribute from `MAX_VALUE` in `variables-import` (`value.rs`). The 5,000 elements and the 5,000 rules are new starting guesses with nothing behind them. Input: 256 KiB for `html` and `css` together, in bytes, refused before anything is read (the size of `import_tokens` and of the export output; under the 1 MiB body limit of `meldframe-http`). Elements: 5,000. Nesting depth: 64 (the export's own `MAX_DEPTH`); the tree builder does not refuse a deeper text, it flattens the element into the deepest one and reports `depth_cut`, and a node tree deeper than the file limit of 32 is refused by the same checks as any write (`E_TOO_DEEP`). Attributes per element: 64, and text per text node: 64 KiB, counted as stored (a longer text is cut and reported); both are starting numbers set by slice 2 of the tree builder, unmeasured like the others. Rules: 5,000. The CSS reader (slice 3) adds starting guesses of its own (`css::Limits`, `css::selector`): 50,000 declarations in one read, 10,000 selectors in all (`a,a,a,...` makes a selector for each two bytes), 4,096 bytes of selector text in one rule, `@layer` blocks nested 16 deep, 16 compounds and 16 simple selectors in one selector, a budget of 2,000,000 steps for the cascade and the same for the style stage (`max_work`; the elements past it get no styles, or only inherit; a `var()` is charged for what it cost), and 64 MiB kept by the style stage (`max_style_bytes`); each cuts or refuses what is over it, and the report says so. A value or an attribute: 1,000 bytes, and 8 KiB for `class` and `style` (`max_class_bytes`: the Tailwind classes of a rich node of the export are about 1,000 bytes and a `style` is as long). Character-reference expansion is bounded, and its number is set by the first hostile tests. Writing: at most 100 Commands in the one call, the batch limit of the gate (`batchLimit` in `docs/mcp-tools.json`). Report: at most 200 entries and 32 KiB of entries, a message cut to 240 characters and a value to 80, control and bidi characters dropped from anything echoed, as `import_tokens` does (ADR-0020); a name is cut to 256 characters and a listed `src` to 200. The file limits (20,000 nodes, 20,000 characters of text, depth 32) stay the checks' own.
- **Crates and kinds** (kinds are those of `docs/architecture.md` section 3b and the matrix of `docs/standards/modular-thin-ui.md` L2; `cargo xtask deps-check` enforces them):
  - `meldframe-css` (kind `core`, in `crates/core/`, no dependency of its own, portable): the colour reader and the number and length reader, by a move out of `variables-import`. A feature may not import a feature of another group unless it is `composite` (L4), and a composite dependence would tie `html-import` to `variables-import` in every build, so the shared code goes to a core crate.
  - `html-import-tree` (kind `feature`, group `html-import`, in `crates/features/html-import/html-import-tree`, no dependency, portable): the tolerant tree builder, its limits and its report. It is the lowest of the importer's crates: the others read its `Tree`, `ElementId` and `Report`.
  - `html-import-css` (kind `feature`, group `html-import`, in `crates/features/html-import/html-import-css`, portable; lands with slice 3): the CSS reader, the selectors, the cascade and the Tailwind decoder. It depends on `html-import-tree`.
  - `html-import-style` (kind `feature`, group `html-import`, in `crates/features/html-import/html-import-style`, portable; slice 3): `var()` resolution, the shorthands, the browser's defaults, the value readers and the computed style of every element. It depends on `html-import-css`, `html-import-tree` and `meldframe-css`. It is a crate of its own because the CSS side passed the 4,000-line ceiling as one crate: the readers, the cascade and the Tailwind decoder are about 1,900 lines, the style stage about 1,550.
  - `html-import` (kind `feature`, group `html-import`, in `crates/features/html-import/html-import`, portable): the facade and, from slice 4, the mapping to Commands and a report, as a pure function from text to Commands. It re-exports the other two under the paths the callers use (`html_import::html`, `html_import::css`, `html_import::tw`). The importer's crates are of one group, so they may depend on each other (the xtask rule for a feature crate importing another of the same group, as `export-dialog` depends on `export`); none depends on a feature of another group. Beyond those, it depends on core crates only (`meldframe-protocol`, `meldframe-check`, `meldframe-layout`, `meldframe-module`, `meldframe-css`). The cargo feature of the same name in `apps/server` is on by default like `export`.
  - `meldframe-http-html-import` (kind `bin`, in `crates/integrations/`, as `meldframe-http-variables-import`): the tool `import_html` (Change tier, Policy Auto), its arguments, one atomic `Shared::submit_ops`, and the answer. axum and rmcp are not portable, which is why this is a `bin` and not part of the feature.
  - `meldframe-import-html-tests` and `meldframe-import-html-http-tests` (kind `tool`, no library code): the tests, the first run under WASM too.
- **Error codes.** `E_IMPORT_HTML_TOO_LARGE` (input over 256 KiB; `E_IMPORT_TOO_LARGE` is about the `css` of `import_tokens` and a code never changes meaning), `E_IMPORT_HTML_TOO_MANY` (more than 100 Commands; nothing is written), `E_IMPORT_HTML_TOO_MANY_ELEMENTS` (the tree builder's own bound: more than 5,000 elements by default; nothing is read further), `E_IMPORT_HTML_EMPTY` (no HTML element makes a node) and `E_IMPORT_HTML_UNSUPPORTED` (`strict` and at least one property refused). Their rows go into `docs/error-codes.md` in the slice that adds them. Malformed HTML is not an error: the builder recovers by its rules and the report says so.
- **One call, one Batch.** The Commands are `addNode`, parent before child, in DOM order; the op of Command `i` has the key `{idempotencyKey}:{digest}:{i}` (ADR-0020) and the ids are `imp-<hash of key and digest>-<i>`, so a retry writes nothing twice and importing one page twice is legal. There is no `ifSeq` (decision 41, answer 4).

## Considered options

- **A parser crate for HTML or CSS** (the family of `html5ever` and `lightningcss`): rejected, for the reasons of ADR-0020 that hold without a check: a large dependency tree that has to be audited against the allow list and built for wasm32 (L5), a parser that does far more than a subset needs, and work that is bounded by what we count and test, not by a crate's internals. The repository holds no HTML or CSS parser today, so any crate would be the first and the whole tree would be new. Not checked: whether any such crate builds for wasm32 or fits the allow list. The risk of our own parser is real and named: error recovery for real-world HTML is large, and the subset will mis-nest some malformed input; the report says when the builder had to recover.
- **A `composite` dependence of `html-import` on `variables-import`**: rejected. It ties two features together in every build and breaks the build of either alone (M3).
- **A second copy of the readers in `html-import`**: rejected. Two copies of the colour rules would drift, and the sRGB clamp of ADR-0020 would then differ between the two importers.
- **A headless browser to read a computed page**: rejected by decision 41 (answer 2): it is the approach (b) that `docs/fidelity-contract.md` section 9 rejects and it goes against the thin server of ADR-0002.
- **Writing a long import in parts**: not in v1 (decision 41, answer 3). A part is its own Batch, so a page in parts would be several Activity rows and a Revert of the first part would meet nodes that later parts added.

## Consequences

- **Slice 1 moves less than the note's wording.** `color.rs` of `variables-import` moves whole. Of `value.rs` only the number and length reading (`number`: `px` and `rem`) moves, and it returns a plain number and an optional unit kind (a `Rem` marker) instead of a `Val`. `Val`, `Conversion`, `classify`, `alias` and `has_fn` stay in `variables-import`: they are specific to variables, and of the three kinds of `Conversion` (`Colour`, `Clipped`, `Rem`) only `Rem` belongs with the length reader, so the enum is not moved. `variables-import` re-exports so that `variables_import::color` and `variables_import::value::Conversion` stay public paths (`values.rs` and `colors.rs` of `meldframe-variables-import-tests` import `variables_import::value::{Conversion, MAX_VALUE, Val, classify}`), and the existing tests of the variables import are the check that behaviour did not change. The moved size is below the 460 lines of the two files. The pull request of slice 1 confirms the exact cut, and this ADR is corrected there if the cut changes. Whether `hex_colour` of `export` follows is decided there too.
- **The size plan.** The tree builder, the CSS side, the style stage and the facade are crates of their own, each far under the 4,000 ceiling: `html-import-tree` 1,141 lines, `html-import-css` 1,934, `html-import-style` 1,555 and the facade 22, so the mapping of slices 4 and 5 has room in the facade (about 3,950) and the CSS crates keep about 2,050 and 2,400. Their tests are crates of their own too: 1,666 (tree), 3,201 (css, room for about 800), 1,245 (style) and 469 (round trip). A first plan of one crate of about 3,300 lines did not survive the CSS side: that stage alone came to about 3,500 lines, so the split came before the mapping, along the line the dependencies give (the tree builder lowest, because the CSS side reads its types, and the style stage above the CSS reader).
- **WASM test crate lists.** A new WASM test crate goes into the four places that list them: the `wasm-test` recipe of the `justfile`, both copies of `nightly.yml` (`.github` and `.gitea`) and the list in `AGENTS.md`.
- **Docs the slices touch when they build.** `docs/error-codes.md`, `docs/mcp-tools.json`, `skills/meldframe/SKILL.md` (checked by `meldframe-mcp-tests/tests/skill.rs`), `docs/architecture.md` (its crate list says what exists, so it changes when the crates do, not here), `AGENTS.md` and `docs/fidelity-contract.md` (slice 8).
- **What stays unmeasured.** The limits above, the visible error of each approximated row against a real web page, and the cost of the parse on hostile input are not measured. Slice 8 (the oracle extensions) is what measures the importer's reading of CSS against a browser's, and the hostile tests of slice 2 are what fix the numbers; until then they are starting numbers, not guarantees.
- **The tool text must say what the importer cannot do for the agent:** an import it wants to take back is a Revert by a person, not an undo it can do (a frame delete is Ask at the gate today, `docs/epics.md` E3.2), and an agent that has a browser should send inline computed styles.
