# HTML is imported by a bounded, tolerant parser of our own over a documented subset, with the colour and length readers shared through a core crate and the tool built as a feature crate and a bin crate

`docs/import-html.md` (the spike note for issue 256, merged as a proposal) maps HTML and CSS text to Nodes and proposes the tool `import_html`. The owner ordered the importer on 24 Nov 2026 and adopted the recommendations of section 7 of that note as the answers to its ten open decisions (decision 41), so this is accepted. This ADR records the choices that are hard to change once code and files depend on them: how the text is read, the limits, the crates and their kinds, and the error codes. The mapping tables of the note (section 3) and the tool's arguments and result (section 4) are not repeated here; the note stays the reference for them. Nothing is built yet. Claims about the repository were checked on `develop` at d6d8421: `Cargo.lock` holds no HTML or CSS parser crate, `deny.toml` allows MIT, Apache-2.0, Unicode-3.0, Zlib and BSD-3-Clause, and `rust-toolchain.toml` installs the `wasm32-unknown-unknown` target that `cargo xtask portable-check` builds against (L5). The limits below are the note's proposals taken as the starting numbers; no number was measured, and the first hostile-input tests and measurements may tune them, each change with its own note here or in the epic.

## Decision

- **A parser of our own, bounded by construction, no crate.** The feature crate reads HTML with a tolerant tree builder over a documented subset: void elements, the usual implied end tags (`p`, `li`, `td` and the like), character references and comments dropped. It is not the full HTML parsing algorithm. It reads CSS with a scanner of rules, simple selectors (type, `.class`, `#id`, `[attr]`, `[attr=value]`, `*`, compounds, descendant and child combinators, selector lists, and the export's `[data-node="id"]` with CSS escapes), the cascade (specificity, then source order, `!important` over normal), inheritance and a small fixed table of browser defaults, and it decodes the Tailwind forms that `crates/features/export/export/src/tw.rs` writes, back to declarations. It opens nothing and runs nothing: `<script>` is not read, and `<link>`, `@import`, `@font-face`, `url()` and `src` are never followed, only listed. The work is counted (as `TEXT_WORK` counts the scan of `variables-import`) so a test can assert that it is bounded.
- **The limits, as the starting numbers.** Input: 256 KiB for `html` and `css` together, in bytes, refused before anything is read (the size of `import_tokens` and of the export output; under the 1 MiB body limit of `meldframe-http`). Elements: 5,000. Nesting depth: 64 (the export's own `MAX_DEPTH`); a node tree deeper than the file limit of 32 is refused by the same checks as any write (`E_TOO_DEEP`). Rules: 5,000. A value or an attribute: 1,000 bytes. Character-reference expansion is bounded, and its number is set by the first hostile tests. Writing: at most 100 Commands in the one call, the batch limit of the gate (`batchLimit` in `docs/mcp-tools.json`). Report: at most 200 entries and 32 KiB of entries, a message cut to 240 characters and a value to 80, control and bidi characters dropped from anything echoed, as `import_tokens` does (ADR-0020); a name is cut to 256 characters and a listed `src` to 200. The file limits (20,000 nodes, 20,000 characters of text, depth 32) stay the checks' own.
- **Crates and kinds** (kinds are those of `docs/architecture.md` section 3b and the matrix of `docs/standards/modular-thin-ui.md` L2; `cargo xtask deps-check` enforces them):
  - `meldframe-css` (kind `core`, in `crates/core/`, no dependency of its own, portable): the colour reader and the number and length reader, by a move out of `variables-import`. A feature may not import a feature of another group unless it is `composite` (L4), and a composite dependence would tie `html-import` to `variables-import` in every build, so the shared code goes to a core crate.
  - `html-import` (kind `feature`, group `html-import`, in `crates/features/html-import/html-import`, portable): the tree builder, the CSS reader, the Tailwind decoder and the mapping to Commands and a report, as a pure function from text to Commands. It depends on core crates only (`meldframe-protocol`, `meldframe-check`, `meldframe-layout`, `meldframe-module`, `meldframe-css`) and on no other feature. It has the cargo feature of the same name in `apps/server`, on by default like `export`.
  - `meldframe-http-html-import` (kind `bin`, in `crates/integrations/`, as `meldframe-http-variables-import`): the tool `import_html` (Change tier, Policy Auto), its arguments, one atomic `Shared::submit_ops`, and the answer. axum and rmcp are not portable, which is why this is a `bin` and not part of the feature.
  - `meldframe-import-html-tests` and `meldframe-import-html-http-tests` (kind `tool`, no library code): the tests, the first run under WASM too.
- **Error codes.** `E_IMPORT_HTML_TOO_LARGE` (input over 256 KiB; `E_IMPORT_TOO_LARGE` is about the `css` of `import_tokens` and a code never changes meaning), `E_IMPORT_HTML_TOO_MANY` (more than 100 Commands; nothing is written), `E_IMPORT_HTML_EMPTY` (no HTML element makes a node) and `E_IMPORT_HTML_UNSUPPORTED` (`strict` and at least one property refused). Their rows go into `docs/error-codes.md` in the slice that adds them. Malformed HTML is not an error: the builder recovers by its rules and the report says so.
- **One call, one Batch.** The Commands are `addNode`, parent before child, in DOM order; the op of Command `i` has the key `{idempotencyKey}:{digest}:{i}` (ADR-0020) and the ids are `imp-<hash of key and digest>-<i>`, so a retry writes nothing twice and importing one page twice is legal. There is no `ifSeq` (decision 41, answer 4).

## Considered options

- **A parser crate for HTML or CSS** (the family of `html5ever` and `lightningcss`): rejected, for the reasons of ADR-0020 that hold without a check: a large dependency tree that has to be audited against the allow list and built for wasm32 (L5), a parser that does far more than a subset needs, and work that is bounded by what we count and test, not by a crate's internals. The repository holds no HTML or CSS parser today, so any crate would be the first and the whole tree would be new. Not checked: whether any such crate builds for wasm32 or fits the allow list. The risk of our own parser is real and named: error recovery for real-world HTML is large, and the subset will mis-nest some malformed input; the report says when the builder had to recover.
- **A `composite` dependence of `html-import` on `variables-import`**: rejected. It ties two features together in every build and breaks the build of either alone (M3).
- **A second copy of the readers in `html-import`**: rejected. Two copies of the colour rules would drift, and the sRGB clamp of ADR-0020 would then differ between the two importers.
- **A headless browser to read a computed page**: rejected by decision 41 (answer 2): it is the approach (b) that `docs/fidelity-contract.md` section 9 rejects and it goes against the thin server of ADR-0002.
- **Writing a long import in parts**: not in v1 (decision 41, answer 3). A part is its own Batch, so a page in parts would be several Activity rows and a Revert of the first part would meet nodes that later parts added.

## Consequences

- **Slice 1 is a move, not a rewrite, and it is a little smaller than the note's wording.** `color.rs` of `variables-import` moves whole. `value.rs` also holds what is specific to variables (`Val`, aliases, `classify`), so only its number and length reading (`px` and `rem` to a number, with the `Conversion` kinds) moves; the cut is made in that slice. `variables-import` keeps its public paths (`variables_import::value::{Conversion, MAX_VALUE, Val, classify}` is imported by `values.rs` and `colors.rs` of `meldframe-variables-import-tests`), and the existing tests of the variables import are the check that behaviour did not change. Whether `hex_colour` of `export` follows is decided there.
- **The size plan.** `html-import` is planned at about 3,300 lines in all, inside the 4,000 ceiling and above the 2,500 band where D1 calls a crate a candidate for a planned split. It is split into a tree builder and a mapper when the second passes 1,500 lines, as `meldframe-app-parts` and others were.
- **WASM test crate lists.** A new WASM test crate goes into the four places that list them: the `wasm-test` recipe of the `justfile`, both copies of `nightly.yml` (`.github` and `.gitea`) and the list in `AGENTS.md`.
- **Docs the slices touch when they build.** `docs/error-codes.md`, `docs/mcp-tools.json`, `skills/meldframe/SKILL.md` (checked by `meldframe-mcp-tests/tests/skill.rs`), `docs/architecture.md` (its crate list says what exists, so it changes when the crates do, not here), `AGENTS.md` and `docs/fidelity-contract.md` (slice 8).
- **What stays unmeasured.** The limits above, the visible error of each approximated row against a real web page, and the cost of the parse on hostile input are not measured. Slice 8 (the oracle extensions) is what measures the importer's reading of CSS against a browser's, and the hostile tests of slice 2 are what fix the numbers; until then they are starting numbers, not guarantees.
- **The tool text must say what the importer cannot do for the agent:** an import it wants to take back is a Revert by a person, not an undo it can do (a frame delete is Ask at the gate today, `docs/epics.md` E3.2), and an agent that has a browser should send inline computed styles.

## Plan

The slices are those of section 6 of `docs/import-html.md`, tracked in issue #272 and `docs/epics.md` (E4.4): 0 this record and the docs; 1 `meldframe-css`; 2 the tree builder with hostile tests; 3 the CSS reader and the Tailwind decoder; 4 the mapping of structure, layout, sizing and text; 5 the mapping of paint; 7 the tool; 8 the oracle extensions. Slice 6 of the note (the tests) is not a slice of its own: each slice lands with its tests, written first. Slice 9 (later decisions) is not scheduled. The order is the note's, and the work starts now, in parallel with other work (decision 41).
