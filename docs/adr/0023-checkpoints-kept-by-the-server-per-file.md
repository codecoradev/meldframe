# Checkpoints are rows kept by the server beside a file's log, taken at an agent's run start by the server itself, and restored by the person's app from the file as it was at the checkpoint

> Status note, 25 Nov 2026: the crate ceilings named below were written for the ceiling of the time. Since decision 42 (standard v1.3, ADR-0026) the hard ceiling of a crate is 50,000 lines; the ideal band of 1,500 to 2,500 lines and the file limit of 500 lines are unchanged. The decision below stands; a split it made stays, and a size figure is history.

E5.3 built checkpoints in the app layer of one page: `AppState.checkpoints` holds numbers in the log (`seq`), the app takes one when another actor's run starts, before a revert and before a restore, and `Action::RestoreCheckpoint` works out the commands with `meldframe-revert`. They are lost when the page goes, they exist only while an editor is open (an agent that works with no editor open leaves no checkpoint), another person's page does not see them, and the Activity tab has a list but no way to create one (`Action::CreateCheckpoint` has no button). The epic's open part asks for them to be kept per file by the server, a run start seen by the server, a Postgres adapter with a migration, and a web control. The owner ordered on 21 Nov 2026 that work goes on with the answers proposed here (decision 39), so this is accepted. It has been built as the Plan lays it out (slices 1 to 12), without a ticked box in the epic: the status note of E5.3 in `docs/epics.md` says what is built and what stays open. It follows ADR-0021 (a store beside the log, rules in a core crate, the app layer holding the state) and ADR-0016 (a checkpoint is a number in the log, a restore is new ops). Claims about code were checked against `develop` at e65a891; where a number is a proposal and not read from the code, it says so, and the Answers record what the owner's order fixed for each open question.

## Decision

- **What a checkpoint is.** A row `{n, seq, kind, label?, about?, by?, atMs}` of a file. `seq` is a number in the file's log: the file as the server had it after op `seq`, never a copy of it (ADR-0016 and the glossary, which keeps "snapshot" as an avoid-word). `kind` is `runStart`, `beforeRevert`, `beforeRestore` or `manual` (the app's `CheckpointKind` has `OtherActorRun` for the first; the name changes, see Consequences). `label` is the person's text, only on `manual`, at most 128 characters (the app's `MAX_LABEL`). `about` is the actor a checkpoint is about (the agent whose run starts, the actor of the batch being reverted); `by` is the actor that asked for it (the person, for `manual` and the two `before` kinds; none for a run start, which the server takes by its own rule). `atMs` is the server clock. `n` is per file, from 1, never reused, and orders the list; `seq` can be lower for a later `n` (a "before a revert" taken at what the person saw), so a row shows both. A checkpoint is not a Batch, is not undone or reverted with the design and is never part of the file.
- **Where it is stored: a table beside the log, per file, in the workspace of the file, as a store seam of its own.** `CheckpointStore` (feature crate `checkpoint-store`, group `activity`, with a memory adapter and a contract suite behind the cargo feature `contract`, as `activity-store`), and a Postgres adapter in `meldframe-store-pg` (`checkpoints.rs`). The numbers are taken under `pg_advisory_xact_lock` on the workspace's checkpoints with a key prefix of its own (`checkpoints:{len}:{workspace}`; ADR-0021 uses `batches:`, ADR-0018 `design_review:`) from a counter row per file. The tables cascade with the file (`files(id) on delete cascade`, the room key), so a recreated file name inherits nothing. `workspace_id` comes from the principal only (ADR-0006), never from a request. Nothing is written into `ops`, `Op`, `NewOp`, `Store` or `Command`: a marker on the largest table, a change of the seam both adapters and the contract suite share, and an op that is not part of the file's content (collab-ux A5) were all worse than a side table. Without `DATABASE_URL` the rows live in memory and go with the process, as batch headers do.
- **Bounds and retention (numbers marked "proposal" are accepted as proposed by decision 39 and the owner can still change them; only the first is read from the code).** The rule differs from ADR-0021, which refuses at its caps: a checkpoint the server takes on its own must never be refused, because the newest run start is the one a person needs, and one caller must not be able to push another's rows out. So each kind has its own share of the file, rows roll only within their own kind, and a `manual` row is never rolled out. Per file: 100 rows in all (the app's `MAX_CHECKPOINTS` today), made of at most 50 `manual` (a manual row over the share is refused with `checkpoint_full`), 25 `beforeRevert` and `beforeRestore` together and 25 `runStart` (at the share, the oldest row of that kind is deleted in the same transaction and under the same lock as the insert; proposal). The shares add up to the total, and each of the automatic ones rolls inside itself, so an automatic row is never refused and a flood of one kind cannot evict another kind. Per actor: at most 20 `manual` rows (refused over it) and at most 10 `runStart` rows per `about` actor (that actor's oldest rolls first; proposal), so one agent that starts runs all day can only replace its own. The numbers cost a per-workspace figure too (the sum of the counter rows of its files, as ADR-0021 does), which nothing in the code lets the design derive; it is question 3. Because the file total is the bound, the list needs no paging. A `manual` row lives as long as the file and there is no delete or edit route (questions 5 and 12 asked whether that is wanted; the Answers keep it so). Rows are not charged to the storage quota of ADR-0014, since the caps bound them and a row costs no op (question 12). The table follows the rule of `ops` (an update trigger that refuses every change, so a label never changes; no delete trigger, because `ops` has none and a file's rows must cascade); the roll is the adapter's own delete of automatic rows, and the contract suite proves it never touches a `manual` row or another kind. Removing a stored label is an operator task in SQL, as for a batch note.
- **Who may create, list and restore: every create is a person's call; listing is a Read.** Creating is `POST /v1/files/{file}/checkpoints`, registered as `checkpoint_create` (Change, not in the MCP catalogue, as `batch_review` is) so a deployment can deny it and the call log records the tier, the actor, the file and the outcome code and no label. Until ADR-0022 gives the principal a kind, a caller may create only when its actor is named in `MELDFRAME_REVIEWERS` (the one list ADR-0021 reads, same parser, exact match, deny by default; the route takes a `may(actor)` closure that `main` builds from it, so the new crate does not depend on `meldframe-http-activity`); after ADR-0022, when the principal's kind is `Person`. `just dev` already lists the editor's actor. So an agent cannot create a row of any kind, and a flood by agents cannot block or evict a person's rows (a test below). The body names only `manual`, `beforeRevert` or `beforeRestore`; `runStart` is the server's alone and a caller that sends it is refused `invalid`. What a caller chooses is checked: `seq` is at most the head of the file (the person may point at any earlier number on purpose); `about` is an actor string by the rules of an actor (at most 128 bytes, no control or hidden character) and only for `beforeRevert`, `label` only for `manual`, and `by` is never taken from the body but from the principal; the panel shows `by` beside `about`, so a named person's claim is never presented as the server's own. `canCreate` in the list answer is true when the caller may and the policy allows. Listing is `GET /v1/files/{file}/checkpoints`, any principal of the workspace, on the path of `GET /v1/files/{file}/batches` (per-address bucket, token, per-principal bucket, the call's slot and time limit, `valid_file`, the workspace of the principal); another workspace's file reads as empty, not `not_found`; like that list it has no registry entry. **Restore is not a server call.** It stays what ADR-0016 made it: the person's app works out commands from the file at the checkpoint and the file now, and sends them as the person's own ops, one history group. No restore route and no MCP tool exists, and this ADR adds none: a restore undoes the work of every actor since the checkpoint, so it is a person's confirmed act, and an agent that restored would have a Delete-tier effect that its own policy asks about (below).
- **How a restore meets the gate, risk tiers and approvals (ADR-0010, E2.4).** A restore appends ops, and its ops remove nodes: leaves first, so a removal is judged alone, and the removal of a frame is Delete tier even when empty. Every op of a restore is sent as the person's actor through the same gate as an edit, so nothing here decides or bypasses admission. Today Delete is Ask for every actor and the ops of the editor are sent one at a time, so a frame removal is answered `approval_required`, an approval is opened that nobody can answer yet (`Server::decide_approval` has no route), and the app drops the op: a restore across a frame an agent added leaves the frame empty and `OpRejected` names it (the E5.2 and E5.3 status notes, ADR-0016). Server-kept checkpoints do not change that. ADR-0022, when accepted, reads a person's Ask as Auto, so the person's restore removes frames and an agent's would be Ask; this ADR needs nothing from it and gains from it. Nothing creates an approval for the restore as a whole, and a checkpoint is never a way around the policy: creating one needs the Change tier and a person (above), and restoring needs what each op needs.
- **Transport: routes for the person, one ephemeral frame, no MCP tool.** The editor reads and writes through routes, as ADR-0021 chose for review states: the socket's messages from the front end are ops, and a new kind of message needs a version handshake that `ServerMsg` does not have. (1) `GET /v1/files/{file}/checkpoints` answers `{"checkpoints": [...], "canCreate": bool}`, newest `n` first. (2) `POST /v1/files/{file}/checkpoints` with `{"key", "kind", "seq"?, "label"?, "about"?}` answers the row; unknown fields are refused. (3) `GET /v1/files/{file}/checkpoints/{n}/state` answers the file at the checkpoint (below). (4) A new `ServerMsg::Checkpoint { room, n, seq, kind, about?, by?, label?, atMs }` is queued on the streams of the file after the call's op events, ephemeral by ADR-0009 (no sequence number, best effort, never replayed) and through `publish_with_headroom`, which ADR-0021 added so that a hint never takes the last slots of a queue. A row is immutable, so the frame needs no `rev`; the route is the truth and a lost frame is healed by three rules: a frame whose `n` is more than 1 above the highest the app holds makes it fetch the list; opening the Activity tab fetches it; and after a `Subscribed`, a `Resync` or a reconnect it fetches it. The roll is not announced: the app applies the same rule (one function, below) to the rows it holds. **No MCP tool in this ADR.** Labels do reach an agent anyway: the list route answers any principal of the workspace and the frame goes to every stream of the file, an agent's socket included (the same is true of batch notes through the list route and the `batch` frame). What is withheld is the tool that would put them in an agent's context on purpose, as ADR-0021 first withheld `get_batches`; it is the owner's call (question 4).
- **Untrusted text.** A label and an `about` actor are text shown to a person, so a bad one is refused and nothing is written, by the rule of notes (ADR-0021: refuse, never cut): `Label::parse` in the new rules crate trims, allows no line break and no control character, refuses `is_hidden_text` (the stricter set of `meldframe-activity`, not `is_invisible`), caps a run of combining marks at 4 and the length at 128 characters (counted as Unicode scalar values; the column checks `char_length`). An empty label is the same as none (as today). The app layer cleans again what it takes in from a route or a frame, because it trusts neither (`docs/architecture.md` section 9). The panel writes a label as text (no `{@html}`, no markdown, no link, `<bdi>`, clipped by CSS) and the label never drives a button or a status. Today the app's own check (`create_checkpoint` in `review.rs`) trims and counts to 128 and nothing more; the new rule is stricter and replaces it.
- **How the server sees a run start: the rule is `RunDetector`, run by the server from the one place every write passes.** `RunDetector::new(gap_ms)` already exists in `meldframe-revert` and takes the gap as an argument; the 5 minutes (300,000 ms) are written twice, as `RUN_GAP_MS` in the app's `review.rs` and as `pub const RUN_GAP_MS` in the reducer of `meldframe-activity` (whose comment says the detector uses the same number). One `pub const RUN_GAP_MS` moves next to `RunDetector` in `meldframe-revert`, and the app, the reducer and the server read it, so the lane's run and the checkpoint's run cannot drift (ADR-0008: rules live once). The server calls the rule from `Shared::submit_ops`, the handler REST, the live socket and MCP all end in (`apply_commands`, `make_variant` and `import_tokens` call it too, atomic calls included), through a new seam `RunSink` set once on `Shared` like `BatchSink`. The rule in `meldframe-checkpoints` (`RunWatch`): only an actor that is an agent starts a checkpointed run (PRD story 42 and the epic say "an agent run"; the app today also checkpoints another person's run, which narrows, question 2); the first written op of an agent after a gap of more than 5 minutes, or the first seen, takes a `runStart` row at `first_seq - 1`, the file as it was just before the call. Until ADR-0022 gives the principal a kind, "agent" is the `agent:` prefix of the actor string, as the lanes read it for display (`view.rs` of `meldframe-activity`); a wrong guess costs a missing or an extra automatic row and decides nothing about access (it is not the reviewer rule ADR-0021 refused to read from a prefix). **The common path costs a prefix test.** A call of a non-agent does nothing. For an agent the in-memory detector decides first; only a due run start runs a job, and it is its own `Shared::blocking` job under the caller's slot (as `mark` does for the batch sink in `mcp/tools.rs`), so a slow Postgres write never holds the call's own job, and its failure, a refused insert or its timeout is logged and counted and never changes the reply. **A call that fails after it wrote a prefix is covered.** A non-atomic call can write some ops and then fail (`Server::write` returns `Err` in its loop), and `submit_ops` has the accepted list only on the `Ok` arm. For an agent's call `submit_ops` keeps the keys of the call (at most the call's ops) and, on the `Err` arm, the sink finds the written ones by key through `Reader::written`, the unlogged read `BatchSink` already uses, and takes the lowest `seq`; with none written there is no run to start. **A detector race.** The detector is told in the order calls finish, not in `seq` order. Of calls of one agent in flight at a run's start (the per-principal slot limit, `max_per_principal`, is 4) the first to finish claims the start, so there is exactly one row per run and it may sit after the first calls' ops of that run; "Before X's run" then keeps their work on a restore. This is accepted and bounded by the slots; the exact place is the `ActivityLog` seam under the room lock (Considered options). **The map is bounded.** It holds an entry only for an agent seen within the gap (an older entry and none give the same answer), pruned by age on every call. The number of agents is bounded by what a workspace's credentials can be (grants are capped at 100 a workspace by ADR-0022, development tokens by the configuration), times the files they wrote in the last 5 minutes; a hard cap of entries is a number for slice 4 (proposal: 10,000; at the cap the oldest entry goes). It is in memory: after a restart the first write of an agent counts as a run start (question 7, answered: option (a)).
- **Idempotency and ordering.** `POST` takes a `key` (at most 100 characters, the op key limit; the column checks `octet_length` of the key and of `actor`, `about` and `by` as migration 0007 does for its actors) and is unique per `(file, by, key)`. A retry with the same key and the same kind, `seq`, `about` and `label` returns the row it made and writes nothing (the rule of op keys and batch headers). A retry with the same key and anything different is refused `key_reused` with the first row's `n` (as `StoreError::KeyReused` does for an op, and unlike ADR-0021's note, whose first value silently wins), so a different checkpoint is never swallowed. A retry after the first row has rolled out of the file finds no key and makes a second row: the key bounds a retry in time, not for ever. A `runStart` is unique per `(file, about, seq)`: a restart, a retry of the sink and a repeated call cannot make two. `seq` in a `POST` is optional and, when given, must be at most the head of the file (`Reader::head`, the read that is not a call of its own) and at least 0; a file with no ops has no row of `files` to point at (the table has a foreign key), so a checkpoint of an empty file is refused as `invalid` ("nothing to checkpoint yet"). The app sends the `seq` it holds (`replica.seq()`, the confirmed state the person sees), so a "before a revert" is the state that was on screen and does not depend on whether the request or the revert's first op arrives first. `n` is given under the lock in the order rows are written; the list is ordered by `n`; a header that could not be written never fails a call (as ADR-0021).
- **The file at a checkpoint, so that a restore still works after a reload.** The app's record (`ConfirmedLog`) starts where the page loaded the file and keeps 2,000 to 2,255 ops; a checkpoint older than its base is dropped by `prune_checkpoints` and cannot be restored. After a reload every checkpoint is older than the base, and a run start taken while no editor was open is older too, so a list that survives the reload but cannot restore would deliver the epic's first words and not its point. So the server answers the file as of a checkpoint: `GET .../checkpoints/{n}/state` returns `{seq, nodes}` (the shape of the snapshot route, nodes only like the app's record), worked out by `state_at` of `meldframe-revert` (pure, portable) over the file's ops read from the store a page at a time (`Store::ops_after`, as the live replay does). **Bounded, because an unbounded replay is a way to exhaust the server.** The `Store` seam has `latest_snapshot` only, not a snapshot at a number, so the replay starts at the latest snapshot when its `seq` is at most the checkpoint's, and at 0 otherwise. The snapshot route bounds its scan at `SCAN_WINDOW` (5,000 ops) and charges `SCAN_COST` (8 calls) after it has worked; this route does both before it reads: it refuses with `too_far` when the replay would read more than 5,000 ops (proposal, the same figure; question 6) and spends `SCAN_COST` of the principal's bucket before the replay, a cache hit costing one. `state_at` takes a whole slice, so streaming would need a new function; the bound makes that unnecessary (at most 5,000 ops in memory, each as large as the quota allows). The answer at a `(workspace, file, seq)` never changes, so it is cached with an entry bound (64 files, the snapshot route's `MAX_CACHED_FILES`) and a byte bound on the stored node text (16 MiB in all; proposal). The honest limit: a file whose log is longer than 5,000 ops past its latest snapshot refuses a checkpoint older than that window, until the store can give a snapshot at a number (a change of the `Store` seam both adapters and the contract suite share, not taken here) or the owner raises the figure. **Who may read it.** The state route is the whole past of a file, deleted content included, and today any agent token can already read the recent log (`get_tree` returns the last ops) but not all of it. So it takes the same gate as create (a person, interim by `MELDFRAME_REVIEWERS`, then by kind) and is registered as `checkpoint_state` (Read, not in the MCP catalogue) so a deployment can deny it and the call log records it; the list route stays open as above (question 4 asks whether an agent may read either). The restore then runs as today with that tree as the target: `Action::RestoreCheckpoint` emits an effect `FetchCheckpointState { n }`, the answer comes back as an action, and `restore_commands(target, replica.nodes())` runs in the app layer on the current replica, including the person's pending ops, as now. One path serves a checkpoint of this page and of an earlier one, so the app no longer calls `state_at`. This is also a prerequisite that ADR-0021's Consequences name for a later reopen-and-revert of batches ("checkpoints kept per file by the server"); the rest of that list stays out.
- **What the app layer keeps, and a revert or restore waits for its checkpoint.** `AppState.checkpoints` stays and becomes the list as the server last said it (at most the per-file total, newest `n` first; `id` is the text of `n`, stable across reloads and shared by every editor), plus `canCreate`. The app stops taking checkpoints itself: `RunDetector` use, `Review.runs`, the counter, `MAX_CHECKPOINTS` and `prune_checkpoints` leave `review.rs`. New actions: `CheckpointsLoaded`, `CheckpointPosted`, `Frame::Checkpoint`, `CheckpointStateLoaded`; effects `FetchCheckpoints`, `PostCheckpoint { key, kind, label?, about?, seq }` and `FetchCheckpointState { n }`. A checkpoint changes only when the server has said so, never optimistically. **Before a revert or a restore the app holds the commands until the server has the row.** `RevertBatch` emits `PostCheckpoint` (`beforeRevert`, the app's `seq`) and keeps the revert pending; `CheckpointPosted` applies it; a refusal, a failure or no answer within the server's call limit refuses the revert with `checkpoint_failed` and sends nothing, and the person may try again (the key makes the retry safe). A restore fetches the state first, works out the commands (an empty list is `nothing_to_restore` and takes no row), posts `beforeRestore`, and applies on `CheckpointPosted`. Blocking is the recommendation because `docs/collab-ux.md` 5.5 promises a checkpoint first and a revert that went ahead without one would break it silently; where the server keeps no checkpoints (the list answered 404, so `canCreate` is false because the module is not built) or the caller may not create one, the revert proceeds as it does where no checkpoints exist; the alternative (proceed with a warning when the post fails) is question 8. A refusal is an `Event::Refused { code }` that the panel words (`checkpoint_full`, `invalid`, `forbidden`, `key_reused`, `checkpoint_failed`). The rules that are pure (the label, the roll, the run rule, the bounds) are functions of `meldframe-checkpoints`; the app calls them and the Svelte panel only draws state. Without the server module there is no local path, so a rule is not kept twice.
- **The web control.** In `packages/web-activity`'s checkpoint section: a text field (at most 128 characters, a visible label, not placeholder-only) and a button "Create checkpoint" (the glossary lists "save" as an avoid-word for Checkpoint; `docs/collab-ux.md` 5.5 says "Save checkpoint" and is corrected in the docs slice), shown disabled when `canCreate` is false, with the refusal worded in the panel's live region. Rows keep the words of `checkpointWords` in `view.ts`: "Before {name}'s run", where the name is the actor as `actorLabel` shows it (today "Before claude's run" for `agent:claude`), "Before reverting {name}'s batch", "Before a restore", or the label; a manual row also names `by`. Restore stays behind its confirmation. A keyboard shortcut is a question.
- **Crates, layers and where the wiring goes** (`docs/architecture.md` section 3b matrix: a `core` crate depends on core only; `feature` on core, engine, integration, os, feature of its group; `bin` on everything). `meldframe-checkpoints` (kind `core`, portable): row types, `Kind`, `Label::parse`, the bounds, `roll`, `RunWatch`, the `RunSink` trait; it depends on `meldframe-revert` and `meldframe-activity` (for `is_hidden_text`) only. `checkpoint-store` (kind `feature`, group `activity`): the seam, `MemoryCheckpoints`, the contract suite. `meldframe-http-checkpoints` (kind `bin`): the sink, the detector map, the routes, the module that registers `checkpoint_create` and `checkpoint_state`, the publish of the frame, all behind one `install(...)` so `main.rs` stays small, as `meldframe-http-activity`. `meldframe-checkpoint-tests` and `meldframe-checkpoint-pg-tests` (kind `tool`): every new test, so no crate carries its own over its ceiling. Postgres: `meldframe-store-pg/src/checkpoints.rs` and `Backing::checkpoints()`. The cargo feature `checkpoints` of `apps/server` (default on, question 11) turns the module on; off, the routes, the sink and the registry entries are gone and `cargo xtask build-matrix` proves it. **Ceilings, from `wc` of each crate now (rs, ts, tsx, js, mjs, css, scss, svelte, html; `size-check` may count a few lines differently):** `apps/server` was 1,979 (room 21) when this was written and is 2,013 on `develop` at the time of the answers (see Answers, Crate ceilings). ADR-0022's joint budget table is stale: it says 1,913 with room 87, and the 45 and 19 lines it plans for the two stacks (64) do not fit in 21 either, and it leaves `lib.rs` (484 now) at exactly 500. So this ADR changes nothing in `lib.rs`, takes at most 12 lines in `main.rs` (the `install` call and the closure) and 2 in `modules.rs`, and slice 0 served both stacks (superseded: decision 35 lifted the ceiling and slice 0 is not needed, see Answers): it moves files out of `apps/server` (ADR-0022 names `limits.rs`, 81 lines, and `modules.rs`, 27, as the first candidates), enough for both sums, and the two lines of `modules.rs` then land in the moved file. Others: `meldframe-http` 1,877 (room 123): the `RunSink` field and its call, at most 40 lines; `meldframe-protocol` 1,728 (room 272): the frame, about 40; `meldframe-app` 1,780 (room 220): the checkpoint code leaves `review.rs` (225) and a module of at most 120 lines arrives, net zero or negative, one-line arms only in `app.rs`; `meldframe-app-model` 1,634; `meldframe-store-pg` 1,388 (about 300 for the adapter); `packages/web-link` 1,966 (room 34): the fetch and post code goes in a new package beside it, and `shell.ts` takes only the dispatch of the three new effects and the frame, at most 30 lines; `packages/web-activity` 1,226; `meldframe-revert` 1,573 with its tests (the constant moves in, 3 lines); `meldframe-rooms` 1,993 is not touched. Every slice that adds a crate edits the line of `docs/architecture.md` for it.
- **Migration numbering and compatibility.** `migrations/` holds `0001` to `0007` on `develop`. ADR-0022 plans `0008` (identity, grants, audit) and `0009` (`calls.grant_id`) and says the numbers are taken from the next free one when each slice lands; this ADR does the same: the file is `NNNN_checkpoints.sql`, the number is the next free at merge, the second of two proposals that name the same number renumbers, and the two share no table beyond `files`. The sqlx migrator applies files by number, so a database that has one stack's number applied and not the other's is a development database to recreate (the repository has no release tag; whether a deployed database exists beyond what `just dev` creates is not something the repository shows). **The schema depended on questions 1, 2 and 9, now answered** (the set of `kind` values, whether `by` and `about` are columns, and the two unique indexes follow from what runs start a checkpoint and what the kinds are called) and on question 3 (the shares), so the migration is written from the answers below. Its shape: `check` constraints that repeat the bounds of a row (kind in its set, `char_length(label) <= 128`, `seq >= 0`, label only on `manual`), `octet_length` checks on `actor`, `about`, `by` and `key`, the two unique indexes (`(file_id, by, key)` where a key is given; `(file_id, about, seq)` where the kind is `runStart`), and a counter table per file (`next_n` and a count per kind) updated under the lock. Nothing existing changes shape: `ServerMsg::Checkpoint` is a new variant (`ServerMsg` is declared with `deny_unknown_fields` in `wire.rs`, so a strict older front end would fail on it; `web-link` drops a type it does not know, and the first-party front end and server ship together, as for `touch` and `batch`); the app-held checkpoints were never stored, so nothing is migrated.

## Considered options

- **Keep checkpoints in the app and persist them from the page** (status quo plus a write to the server): rejected; a run start with no editor open is never seen, two editors disagree, and the rule would live in the front end's process.
- **Derive run starts on read from the log and the time of each op** (no stored automatic rows): rejected. `ops.created_at` is a column of the Postgres table since `0001_init.sql` (migration 0004 only indexes `(file_id, created_at)`), but `StoredOp` and the in-memory store carry no time, so the two adapters would differ, the `Store` seam would change to expose it, a list would scan the log, and the `before` kinds and manual ones need rows anyway. Option (b) of question 7 would use the Postgres time, narrowly, for the restart case; the answer takes option (a) and leaves (b) for later.
- **A marker op or a `Command` in the log**: rejected; see above. A checkpoint is not part of the file's content.
- **A copy of the file at each checkpoint**: rejected (ADR-0016, glossary): a second state to keep right, and the log is the truth. The cost is the replay of the state route, bounded and cached.
- **See the run start inside the room, under the lock, through the `ActivityLog` seam of `meldframe-rooms`** (called for every written op in `seq` order, with the clock): the exact place, since the race above cannot happen, and a failed prefix write is seen too. Rejected for now: `Rooms` owns a concrete `MemoryActivityLog` (the `Rooms` alias and `Server::assemble_in` in `apps/server/src/lib.rs`), `lib.rs` is at 484 of 500 and ADR-0022's plan takes the rest, and `meldframe-rooms` is at 1,993. It would also tie a database write to the server lock unless it only queued. Revisit when `lib.rs` has room.
- **The app layer posts the run start when it sees one**: rejected for the same reason as the status quo.
- **A server-side restore** (a route that returns the commands, or that applies them): rejected here. The person's pending ops are part of "current", so the app works the commands out on its own replica; the atomic send of a restore is E5.2's open question; and a route that applies would be a Delete-tier effect of one caller on every actor's work. A later change can add a plan route over the same pure functions.
- **An MCP tool for agents to list or create checkpoints**: not taken; see Transport and question 4.
- **Refuse at the cap, as ADR-0021 does for headers**: rejected for automatic rows (the newest would be lost); kept for manual rows.
- **Run start for every actor, as the app does today**: not the default, see question 2; the server does not know which actor is "me", so every person's own run would take a row, and in the development setup the editor's token has an `agent:` actor.

## Consequences

- **Delivered, and what it adds to E5.3.** Checkpoints survive a reload and a server restart (on Postgres), every editor of the file sees the same list, a run start is taken with no editor open, and a person can create one with a label. A restore of a checkpoint from before the page loaded works through the state route (if question 1 keeps it). It does not change what a restore can remove: the frame removal limit above stays until E2.4's approval path or ADR-0022.
- **Restore covers nodes only.** `ConfirmedLog` holds `Vec<Node>` and `state_at` replays on `Doc::of_nodes`, so the variables of a file (ADR-0017, a second table, carried by the snapshot route) are not part of a restore; whether a log that holds variable commands replays through `state_at` was not run and is not claimed. This ADR keeps the scope and the docs slice says so; including variables is a separate decision (question 10).
- **The detector is in memory, and a row can be late.** After a restart the first write of an agent counts as a run start as question 7's answer (a) accepts, so there is one extra automatic row per active agent and file, which the roll keeps bounded; and in a race the one row of a run may sit after the first calls' ops. In the development setup the editor's own token has an `agent:` actor (`just web` opens the editor as `agent:dev`), so its runs also take rows until the principal has a kind (ADR-0022); a developer sees noise, never missing safety.
- **A label is text that other people read.** The risks left are a misleading or rude label (bounded by 128 characters, shown attributed, never styled) and an agent that reads one through the list route or the frame (question 4). A test sends a label with a hidden character and one that looks like an instruction and checks that the first is refused and the second comes back only as text with its author. Another test, with a second agent actor and a flood of run starts and of refused creates, checks that no person's row is evicted and the person's own `manual` create still works.
- **The call log** records `checkpoint_create` (actor, tool, file, tier, decision, outcome code) and no label, like every call; the automatic rows are not calls and have `about` and no `by`.
- **Tests that must change.** The checkpoint tests of `meldframe-app-review-tests` (`review.rs`, `review_refused.rs`) and `packages/web-activity` (`panel.test.ts`, `view.test.ts`, `controller.test.ts`) build local checkpoints and `otherActorRun`; they move to the new actions and kind. The generated TypeScript (`tools/check-protocol.sh`) changes (`id`, `kind`, `canCreate`), and so does `tools/wasm-smoke.mjs` if it names a checkpoint.
- **Docs this ADR makes stale, edited in the docs slice:** the glossary (**Checkpoint** says "a named point"; add the server-kept row and that an agent's run starts it; **Run** says "another actor's run"), `docs/collab-ux.md` 5.5 and Q12, the E5.3 status note in `docs/epics.md`, `docs/error-codes.md` (`checkpoint_full`, the app's `not_in_log` goes), `AGENTS.md` (the module, the cargo feature, retention, the SQL step to remove a label), and `docs/architecture.md` (the crates and the frame). The skill (`skills/meldframe/SKILL.md`) is not touched, because no MCP tool or tool text changes.

## Answers

Accepted on 21 Nov 2026 by the owner's order to go on with the answers this ADR proposed (decision 39). Where a question had no proposal, the more conservative, reversible option is taken and says so. The numbers are those of the questions as first asked, so a reference to "question 7" in the sections above resolves to the answer below. Every answer can be changed later by the owner.

1. **Restore after a reload.** The state route stays as the Decision describes it, with the bounded replay, and slice 6 stays in the Plan where it is. It can be dropped later; if it is, the alternative this question named applies: list and create, with restore only for a checkpoint the page saw arrive live, and every older one listed as "older than this page".
2. **Which run starts take a checkpoint.** Proposed, accepted: an agent's only, as PRD story 42 and the epic say. "Agent" is the `agent:` prefix of the actor string until ADR-0022 gives the principal a kind, so an agent whose actor lacks the prefix gets no automatic row, and the editor's own `agent:dev` token takes rows in development.
3. **The numbers.** Accepted as proposed: 100 rows a file (from the code), 128 characters (from the code), 5 minutes (from the code); 50 `manual`, 25 for the two `before` kinds and 25 `runStart` per file; 20 `manual` rows and 10 `runStart` rows per actor; 5,000 ops of replay; 64 cached files and 16 MiB; 10,000 detector entries. The workspace figure had no proposal and cannot be derived from the code. Taken: no workspace figure now. A workspace is bounded by the rows of each of its files, and the counter row per file lets a sum be added later without changing the schema. The migration can now be written.
4. **Agents and checkpoints over MCP.** Proposed, accepted: no tool; creating a checkpoint and reading the state of a file at one are a person's. Listing stays open to any principal of the workspace, as the Decision says, so labels reach an agent the way batch notes do; only the tool is withheld.
5. **Delete and edit.** Proposed, accepted: neither. A label is removed by an operator in SQL.
6. **The bound of the state route.** Accepted as proposed: 5,000 ops of replay, the snapshot route's window, and `too_far` beyond it, with no change to the `Store` seam. A refusal for a long file's old checkpoint is acceptable until the store can give a snapshot at a number.
7. **Run start after a restart.** No proposal; the question leans to option (b) ("likely the better default") and calls (a) the simplest. This answer departs from that lean: taken, option (a), one extra row per active agent and file after a restart, bounded by the roll. It adds no method to `CheckpointStore` and no scan of `ops`. Option (b) can be added later without a schema change.
8. **Revert and restore wait for the checkpoint.** Proposed, accepted: they do, and a failed post refuses the revert with `checkpoint_failed`. Restore stays the person's and is worked out in the app; no server route returns the plan, and the atomic send stays open in E5.2.
9. **Words and shortcut.** Accepted: the button reads "Create checkpoint" and the kind `otherActorRun` is renamed `runStart`. The shortcut had no proposal. Taken: none, because Cmd or Ctrl and Shift and S is also a browser key; it can be added later.
10. **Variables in a restore.** No proposal. Taken: nodes only, as today (see Consequences); including the variables table is a separate decision.
11. **Default on.** Accepted: `checkpoints` joins the default features of `apps/server`, as `activity` did.
12. **Retention, quota and the roll.** Accepted as the Decision writes it: rows live as long as the file, are not charged to the storage quota of ADR-0014, automatic rows roll inside their kind, and a `manual` row is refused at its share (`checkpoint_full`) and never rolled.

**Crate ceilings.** Decision 35 (20 Nov 2026) replaced the flat 2,000-line ceiling with an ideal band of 1,500 to 2,500 lines and a hard ceiling of 4,000. The ceilings paragraph of the Decision and slice 0 were written against 2,000. On `develop` today `apps/server` is 2,013 lines and every other crate this ADR touches is under 2,000, and with the additions the ADR plans each stays under 2,500, so slice 0 (the move out of `apps/server`) is not needed for the size limit. The file limit of 500 lines is unchanged, and `lib.rs` is not changed by this ADR.
