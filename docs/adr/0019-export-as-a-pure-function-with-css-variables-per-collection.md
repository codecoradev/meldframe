# Export is a pure function of the render model, and variables become CSS custom properties named by collection and name

ADR-0003 makes the layout core the source of truth and the export a translation. This records the shape of that translation (E4.1), where the choices are hard to undo once exported pages exist.

## Decision

- **`export_frame(nodes, vars, frame, options) -> Export { html, css, report }` is pure** (feature crate `export`, kind feature, portable). It reads the render step (`resolve_with`) for everything the canvas paints, the node for the fields that layout reads, and the layout core for the size of text and of a fill that its siblings squeeze (rules G1, G2 and G4 of the contract). It does no I/O and reads no clock; the same file gives the same bytes. The text measurer is a parameter (`TextMeasurer`): the server has only the stub, so a text box from the tool is as exact as the stub; E4.2 passes the recorded table of the real text engine.
- **The output is a whole HTML document** with `data-node="<id>"` on every element (the hook the oracle reads) and `data-name` for the layer name. In `css` form every rule selects `[data-node="<id>"]` and sits in an inline `<style>`. In `tailwind` form the elements carry Tailwind v4 utilities (the contract's where it names one, an arbitrary property `[prop:value]` otherwise) and the document links `meldframe.css`; `Export.css` is then the **input** of the Tailwind compiler (`@layer theme, base, utilities`, the two partial imports without preflight, the font, the reset in the `base` layer so that a utility on a paragraph still wins, and the variables). The utilities themselves come from the classes of the HTML. Tailwind 4.3.5 compiled every class of a rich fixture when this was written (by hand, not in CI). No `@theme` and no idiomatic classes: the contract's open question 9 stays open.
- **A variable the frame uses, and every variable its aliases reach, is `--<collection>-<name>`**: both lowercase, every run of other characters one hyphen (`appearance` and `color/brand-500` give `--appearance-color-brand-500`). A collision gets `-2`, `-3` in file order. The name follows the name of the variable, not its id, so a rename changes the exported name; an id would not be readable by the developer who receives the file.
- **Modes.** The default mode of every collection is one `:root{...}` rule; every other mode is `:root[data-mode-<collection>="<mode>"]{...}`, with the mode name made a slug as above. The mode picked in the options is the attribute on `<html>`, so one document holds every mode and a page switches by setting the attribute. All variables sit on the one element, so an alias (`var(--other)`) follows the mode picked for the collection it points at, as `meldframe_variables::resolve` does; a rule on a child element would not.
- **Values.** A colour is written as the render model paints it (`#rrggbb`, alpha dropped, because the canvas drops it: one model, not two). A number is unitless. A bound `fill` is `var(--x)`; a bound `radius` is `calc(var(--x) * 1px)` and a bound `opacity` is `var(--x)`, so one number variable can feed either field. A binding that does not resolve is the default of its field, with a `unresolved_binding` warning, as the canvas paints it.
- **The border is `::after`, never a CSS border**, so it takes no room (contract, open question 6 answered as verified there). It is positioned over the children, and `overflow:hidden` on a clipping frame clips a border drawn outside or on the edge; the report says `border_clipped`.
- **The report** has `unsupported` (what was dropped or approximated: `shader_approximated`, `on_text`, `border_clipped`), `warnings` (the layout findings of rules G1 to G3 with their own codes, `unresolved_binding`, `unresolved_alias`, `invalid_colour`, `text_outside_contract`) and `assets` (the ids of the images the HTML refers to, as `url(assets/<id>)`; the files are not part of the export, contract open question 7 is answered by "relative files next to the document" for now).
- **A frame is exported; a top-level frame sits at its own x and y, a frame inside another at the origin.** Output is limited to 256 KiB of HTML and stylesheet together; more is `E_EXPORT_TOO_LARGE`. The limit bounds the answer: in the plain CSS form the stylesheet is in the document and again in `css`, both come back, so it counts twice. Not found and not a frame reuse `E_NODE_NOT_FOUND` and `E_NOT_A_FRAME`.
- **Bounded work.** The export reads the frame and what is inside it, not the file: it takes the subtree first (iteratively, down to 64 levels; deeper is cut with a `too_deep` warning, the writes of the server stop at 32), and lays out, paints and checks only that. The frame is then a root, which is how its own size is read; the result is the same as for the frame alone, except for the layout finding of a frame that is a fill in a hug parent, which is about a parent that is not exported. Before anything is cloned the subtree is counted for the least bytes it must produce (text, names, a floor per element); over the limit is refused there. The walk checks the running size at every element. The share of a fill with unequal padding is worked out once per parent.
- **Strings.** A user string lands in one of four places and is escaped for it: HTML text and attribute values (`&`, `<`, `>`, `"`), the selector `[data-node="..."]` (every character but letters, digits, `-` and `_` as a hex escape, so no `<`, quote, brace or newline survives), identifiers (collections, variables and modes are slugs of lowercase ASCII letters, digits and hyphens; a name with no such character is `x`; a name in another script becomes `x` or loses its letters, a documented limit that the `-2` suffix keeps unique), and values (a colour is copied only as hex, an image only as 64 hex digits, otherwise `transparent` or no image and an `invalid_colour` or `invalid_asset` finding in `unsupported`; the font and asset prefixes of the options are hex-escaped). The `<style>` body has no `<`.
- **Modes and values.** A mode or collection of the options that is not in the file is a `unknown_mode` warning; a variable with no value in a mode and none in the default is a `missing_value` warning.
- **Coverage.** The export column of the coverage table of `meldframe-render` says which node fields the export renders (all but the shader preset). It cannot be proven in that crate (a core crate cannot depend on a feature crate), so the tests of the `export` crate prove it: every field marked rendered changes the output when it changes, and one marked unsupported does not.

## Considered options

- Export as a second walk over the nodes that paints its own values: rejected, it is the drift the coverage table exists to prevent (risk R1).
- Variable names from ids (`--v_9f3a`): rejected, unreadable in the developer's file; names are unique per collection only, which the collection prefix and the suffix on collision cover.
- Mode rules on a class or on the frame: rejected, an alias would then resolve at the wrong element.
- `@theme` with `bg-brand-500`-style classes: deferred with the idiomatic Tailwind question.

## Consequences

- A rename of a collection, a variable or a mode changes the names in the next export; nothing stores an exported name.
- The oracle (E4.2) feeds `html` and `css` as they are, with a measurer built from the recorded table, and reads `[data-node]` boxes; the Tailwind variant is compiled from the classes of the HTML plus `Export.css`.
- Open: the shader preset has no CSS form; the Tailwind form of a border pseudo-element and of the image utilities is compiled by hand but not yet gated by the oracle; per-corner radius, rotation and the other "unsupported until proposed" rows of the contract are not in the model.
