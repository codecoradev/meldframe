# AGENTS.md: meldframe

Design canvas for humans and AI agents. Pre-alpha; docs first, no product code yet.

## Where to look

- Product context, before any design or copy work: `PRODUCT.md`.
- Terms, before naming anything or writing docs: `GLOSSARY.md`. Use its words; the `_Avoid_` words stay out of code, docs and tool text.
- Requirements, before scoping a change: `docs/prd.md`.
- Structure and seams, before adding a module or changing an interface: `docs/architecture.md`.
- Why a hard-to-reverse choice was made, before reopening it: `docs/adr/`.
- Open decisions and order of work: `docs/roadmap.md`. Milestones, epics, acceptance and exit criteria, before starting any work item: `docs/epics.md`. Owner decisions: `docs/decisions.md`.
- Layering, detachable modules, the app layer, the gate and live events, before adding a crate, module or transport: `docs/standards/modular-thin-ui.md` and ADR-0007 to ADR-0010.

## Workflow

Full contributor rules: `CONTRIBUTING.md`.

- Branch from `develop` with a prefix (`feat/`, `fix/`, `docs/`, `chore/`); rebase onto `develop`; one logical change per pull request; squash merge with a clean message.
- Sign off commits (`git commit -s`). Write repository artifacts in English.
- Test first for behaviour changes: a failing test at the agreed seam, then the minimal change.
- Put no AI attribution in commits, pull requests, docs or comments.
- Before opening a pull request, run Cora as an agent reviewer on the full diff and put the verdict in the description (`CONTRIBUTING.md`). The CI Cora review also runs on every pull request, but the local agent review stays required. Do not edit a description after opening: it restarts CI.
- Merge only after the owner approves.

## Layers

Every crate declares its kind (core, engine, integration, os, feature, app, ffi, ui, feature-ui, bin, tool); the checker (`cargo xtask deps-check`, from E0) enforces the matrix in `docs/architecture.md` section 3b. Feature modules never import each other except composite crates; UI crates hold no business state and use tokens only; every change passes the admission gate. A file stays under 500 lines and a crate under 2,000; ceilings only go down.

## Commands

- `cargo xtask deps-check`: reads `cargo metadata` and enforces crate kinds and the dependency matrix (`docs/standards/modular-thin-ui.md` L1 to L4). Each crate declares `[package.metadata.meldframe] kind = "..."` (feature crates also `group`, and `composite = ["group"]` to import another group). Prints every violation and exits non-zero on any.
- `cargo xtask build-matrix`: builds the workspace with default features off, then each declared feature of each crate alone (M3), then runs the tests of each crate with default features off (so `apps/server` proves that a feature left out removes its tools: `cargo test -p meldframe-server --no-default-features`). Fails if any step fails.
- `cargo xtask portable-check`: builds every portable-kind crate (core, engine, integration, os, feature, app, ffi) for `wasm32-unknown-unknown` (L5). `rust-toolchain.toml` installs the target; otherwise run `rustup target add wasm32-unknown-unknown`.
- `just wasm-test`: runs the unit and integration tests of the order, check, core, layout, render, history, revert and sync crates, and the property tests of history and sync (`meldframe-history-props`, `meldframe-sync-props`), the scenario tests of sync (`meldframe-sync-scenarios`) the variable tests (`meldframe-variables-tests`, `meldframe-variables-limits-tests`) the export tests (`meldframe-export-tests`) and the variables import tests (`meldframe-variables-import-tests`), under WASM on Node, from the same test sources as the native run (E1.1). `.cargo/config.toml` sets `wasm-bindgen-test-runner` as the runner of the `wasm32-unknown-unknown` target, so the recipe is `cargo test --target wasm32-unknown-unknown --tests -p ...`. Needs Node and the runner, whose version must equal the `wasm-bindgen` crate in `Cargo.lock`: `cargo install wasm-bindgen-cli --version <that version> --locked`. A test file imports `wasm_bindgen_test::wasm_bindgen_test as test` on `wasm32` only, so a new test file in these crates needs the same two lines. Property tests default to 20 seeds under WASM (the environment does not reach a WASM test); the 600-seed runs stay native.
- `cargo build -p meldframe-oracle-runner` then, in `tools/fidelity-oracle`, `npm ci`, `npx playwright install chromium` and `node oracle.mjs --seeds 50` (`--seeds 500` is the nightly): the fidelity oracle (E4.2, `docs/fidelity-contract.md` section 7). The runner (`crates/core/meldframe-oracle-runner`, kind tool) lays fixture files out with the layout core and exports each frame with the `export` crate in both forms; the harness loads both in Chromium and exits 1 when a box is more than 0.05 px from the core's rect, Tailwind differs from CSS, a paint probe fails, an ink edge is more than 1 px away, or a known gap in `known-gaps.mjs` starts to pass. A failing fuzz seed prints its file: add it to `fixtures.mjs`. `npm test` there checks the gate on made-up results and `npm run sensitivity` that a deliberately wrong export (geometry and paint) fails it. The `oracle` job of pull request CI (not a required check yet) and `fidelity-oracle` in the nightly run it; run it by hand before a change to `export`, `meldframe-layout` or the fidelity contract. Playwright, Pixi, Tailwind and Inter are exact in the lockfile: a browser upgrade is its own change.
- `tools/check-protocol.sh`: regenerates the TypeScript types in `packages/protocol/src/generated` from `meldframe-protocol` and the app layer (`meldframe-app`: Action, Effect, Event, AppState), compiles a sample consumer with `tsc` and fails if the generated files differ from the committed ones. Run it and commit the result after any change to the protocol types.
- `tools/build-wasm.sh [out-dir]` (`just wasm-build`): builds `meldframe-wasm` for `wasm32-unknown-unknown` and runs the `wasm-bindgen` CLI (the version of the `wasm-bindgen` crate in `Cargo.lock`; the script says how to install it) into `apps/web/.wasm` (git-ignored). `tools/check-wasm.sh` (`just wasm-smoke`) builds the Node glue into a temporary directory and runs `tools/wasm-smoke.mjs` on it: the JSON boundary (Action in, Effects out, state, nodes, the scene and events as JSON) through the real wasm. The browser gets the same six calls as `Bridge` in `crates/app/meldframe-wasm`.
- `tools/mutation-check-sync.sh [name...]`: the E1.1 mutation check. Switches one replica or history rule off at a time (dependency rule on the client and on the test server, per-actor undo, put-back of a refused undo, and more), runs the history, sync and property tests, and fails if a mutant survives. Each mutant gets a quick pass first (stops at the first failing test binary, `MELDFRAME_MUTATION_SEEDS` property seeds, 100 by default) and the full pass only when it survives that; `--list` prints the names. `MELDFRAME_SEEDS=n` sets the seeds of the full pass (600 by default; `MELDFRAME_SEED=n` replays one).
- `tools/check-migrations.sh`: creates a scratch database on the Postgres at `ADMIN_DATABASE_URL` (default `postgres://postgres@127.0.0.1:5433/postgres`), applies `migrations/*.sql` to it from empty, asserts the schema version and append-only rules, then drops it.
- `cargo xtask size-check [--base <git-ref>]`: 500 lines per file and 2,000 per crate (D1), counting rs, ts, tsx, js, mjs, css, scss, svelte and html files. `xtask/size-allow.toml` lists what is over; an entry must equal the current size, so entries only go down. With `--base` (`--base <ref>` or `--base=<ref>`; the ref must resolve, otherwise the check errors; use `origin/develop` in CI) an entry that is new or higher than on the base fails.
- `cargo xtask ui-literals`: rejects colour, font-size and duration literals in `ui` and `feature-ui` crates and in `apps/web` styles and Svelte files (U4; the fast baseline for the web client: `npm run ui-literals` in `apps/web` is the strict, authoritative check there, covering TypeScript, named colours, Tailwind arbitrary values and more, and CI runs both). Read values from the tokens module (`crates/ui/meldframe-ui/src/tokens.rs`, `packages/web-tokens/src/tokens.ts`); only those three files, `crates/ui/meldframe-ui/src/tokens.rs`, `packages/web-tokens/src/tokens.ts` and `packages/web-tokens/src/tokens.css`, are exempt.
- `cargo xtask licences --check`: every third-party crate's licence expression must be allowed by `[licenses] allow` in `deny.toml` (D2). The same list drives `cargo deny check` (install with `cargo install cargo-deny --locked`). Model weights have no check yet (no models are shipped).
- Compile-fail tests (`crates/core/meldframe-rooms/tests/ui`, `trybuild`) compare the exact compiler output: after a toolchain bump, or a change to the signature of `Permit::new` or `Room::accept` (the output quotes them), regenerate the `.stderr` files with `TRYBUILD=overwrite cargo test -p meldframe-rooms --test compile_fail` and review the diff.
- Before a pull request: `cargo fmt --all --check`, `cargo clippy --workspace --all-targets -- -D warnings`, `cargo test --workspace`, `cargo xtask deps-check`.

## Parallel worktrees

When several worktrees build at once, give each its own target directory outside the worktree (`export CARGO_TARGET_DIR=<path>`), delete it when the worktree is removed, and watch the free disk space (a target directory is several GB). A shared target directory lets worktrees overwrite each other's `meldframe-*` artifacts: false "cannot find" errors (an `xtask` binary built for another worktree was a case of this, fixed in #101 for the Cargo workspace root, but the overwrite itself remains). The `just` recipes and `cargo xtask` honour the variable through cargo; unset, the target stays in the worktree.

## CI

GitHub Actions in `.github/workflows/` (the repository is hosted on GitHub; `develop` is protected and the required checks are `checks`, `migrations` and `pr checks`): `ci.yml` (the fast set in two jobs, `checks` and `migrations`: scripts self-test, format, lint with warnings as errors, tests, `deps-check`, the protocol drift check, and the migrations check; every pull request must pass it), `nightly.yml` (the heavier gates `build-matrix`, `portable-check`, `size-check`, `ui-literals`, `licences`, `wasm-test`, `property-tests`, `mutation-check`, nightly on `develop` and on demand: `gh workflow run nightly.yml --ref develop`; run them yourself before a pull request), `pr-checks.yml` (one job: branch prefix, Message Standard, description sections What, Why, Changes, Testing) and `cora-review.yml` (the Cora review of each pull request, run from the base branch so a pull request cannot change its own review; config in `.cora.yaml`; the local Cora agent review stays required). A gate whose command does not exist yet is listed in `.gitea/ci-pending.txt` and passes without running; remove its line in the pull request that adds the command. Check scripts live in `scripts/ci/` (`sh scripts/ci/selftest.sh`). `.gitea/workflows/` keeps equivalent workflows for a Gitea runner, unused while the repository is hosted on GitHub; keep them in step when a workflow changes. The shared check scripts still read `.gitea/ci-pending.txt`.

## Release (develop to main)

A pull request from `develop` to `main` is a release. Pull request CI is the fast set, so before a release is merged run the heavy gates it skips and write the result in `Testing`: `just check` (all of it), `just wasm-test` and `just wasm-smoke`, `tools/mutation-check-sync.sh`, the property tests with more seeds (`MELDFRAME_SEEDS=6000 cargo test --release -p meldframe-history -p meldframe-history-props -p meldframe-sync-props`), and the browser checks against the development server: `packages/web-e2e/scripts/editor-e2e.mjs` (with a second token for the checks of another actor) and, when the MCP surface or the capture changed, `packages/web-e2e/scripts/m1-claude-demo.mjs`. The last nightly run on `develop` must be green. A release that skips one of these says which and why. Nothing here runs in pull request CI: a heavy check is run on purpose, at a release, and by hand before a change that touches what it covers.

## Rules that are easy to break

- Keep pull requests small: 15 files or fewer (ceiling 20) and under 1,000 changed lines (ceiling 1,500; 600 to 1,000 is normal for a feature slice), one kind of content. Lockfiles, generated files, pure moves, snapshots and large fixtures do not count; tests do. A large or mixed pull request is slow to review and hard to review well; split it by layer, crate or feature slice (a short stack is fine) and plan the boundaries before parallel work. Going over a ceiling needs a written reason under `## Why`.
- Nothing public is created (accounts, domains, packages, registries) without an owner order.
- Do not carry PPTX, Flutter or Dart.
- Do not start new spikes; build the first vertical slice in this repository with exit criteria written first.
- Never invent users, metrics, testimonials or prices.

## Development

Needs `just`, `psql` and either Docker or local Postgres 16 binaries. Copy `.env.example` to `.env` (development values only).

- `just dev-db`: start Postgres on `127.0.0.1:5433` (databases `meldframe_dev`, `meldframe_test`) and load the development seed. Uses `docker compose` when a Docker daemon is reachable, otherwise `scripts/pg-start.sh` starts a local cluster without Docker (idempotent; run it again after a sandbox or machine restart).
- `just dev`: the one command for development (`scripts/dev.sh`): starts Postgres (as `just dev-db`), applies the seed, generates a development token on first run (saved in the git-ignored `.dev-token`, printed once, handed to the server through `MELDFRAME_DEV_TOKENS` in the environment, never argv) and runs the server on `http://127.0.0.1:8080` (override with `MELDFRAME_LISTEN`) on `DATABASE_URL`. The server applies the migrations itself when it connects (the sqlx migrator owns the schema of `public`; the seed lives in the separate `dev_seed` schema, so the two never clash; never load `migrations/*.sql` into the dev database with `psql -f`, `PgStore` refuses it). Without `DATABASE_URL` the binary keeps files in memory. Endpoints: `GET /v1/health`, `POST /v1/files/{file}/tools/{tool}` (Bearer token; `example_edit` is the Change-tier placeholder tool), `GET /v1/ws`. `just dev-server` runs the server alone against a database that is already up; it needs `MELDFRAME_DEV_TOKENS` (`token:workspace:actor`, token of 16 bytes or more; `just dev` builds it from `.dev-token`) in `.env` or the environment. `MELDFRAME_REVIEWERS` (actors, comma separated, exact match of the whole actor string, trimmed, empty entries ignored; more than 32 entries or an entry that is not an actor stops the server at start) names who may accept or flag a batch through `PUT /v1/files/{file}/batches/{n}/review` (ADR-0021): unset means nobody, and the route answers `forbidden` to every caller. `just dev` adds the dev actor `agent:dev` (the actor of the dev token, which `just web` opens the editor as) to it; `just dev-server` and a binary started by hand set it themselves. An agent that shares the editor's token shares its actor and so may review: give an agent a token of its own with an actor that is not listed. The server connects, and so migrates the database, only when `MELDFRAME_LISTEN` is set and `DATABASE_URL` is set; without `MELDFRAME_LISTEN` it prints the registry and exits without touching Postgres. `example_edit` is a placeholder Change-tier write tool compiled in by the default `example` feature: drop it from release builds (build without that feature) before real authentication ships.
- `just web`: the web client (`apps/web`, Svelte 5 + Vite + TypeScript + Tailwind CSS v4 + Bits UI) on Vite's dev server, with `/v1` (REST and the live socket) proxied to the server of `just dev` through the guarded proxy (`packages/web-tools/src/proxy-guard.ts`): the token is read from `.dev-token` into `MELDFRAME_WEB_TOKEN` for the proxy and never reaches the browser; `MELDFRAME_SERVER` overrides the target (loopback only unless `MELDFRAME_WEB_ALLOW_REMOTE=1`). Builds the WASM bridge first when `apps/web/.wasm` is missing (needs `wasm-bindgen-cli`, see `tools/build-wasm.sh`), and runs `npm ci` when `node_modules` is missing or older than `package-lock.json`. The page opens the editor on the file `MELDFRAME_WEB_FILE` (default `file_dev`) as the actor `MELDFRAME_WEB_ACTOR` (default `agent:dev`, the dev token's actor; sign-in replaces both in M2): the document over the live socket, the connection state, selection, and editing with the pointer and the keyboard (drag to move, handles to resize, V F R T for the tools and a drag to draw, Delete, Ctrl or Cmd Z and Shift Z or Y; the pure part is `packages/web-document`). A delete of a frame or of a large subtree, sent alone, is answered `approval_required` (E2.4): the owner's answer is `Server::decide_approval`, which no route offers yet, so it stays refused until sign-in and the owner screen exist. A file the server does not know yet opens empty and comes to exist with its first op. The design pages are at `/?tokens` (the tokens), `/?states` (every chrome control in both themes with its six states) and `/?layout` (the editor layout with made-up content; no server needed); the last two load on demand. The layout answers `Option+1` (layers panel), `Option+2` (right panel) and `?` (the shortcut hint); the tool keys are V F R T. `packages/web-chrome/scripts/states-e2e.mjs` and `packages/web-chrome/scripts/layout-e2e.mjs` check those two pages in a real browser (focus ring, hit areas of 24 px or more, names, computed boxes at 1440x900 and 1280x800, no overlap, the keys; run by hand with the Vite dev server up, `node packages/web-chrome/scripts/states-e2e.mjs [web-url]`). `packages/web-e2e/scripts/editor-e2e.mjs` checks the editor in a real browser against the development server (`node packages/web-e2e/scripts/editor-e2e.mjs`; it restarts the server for the reconnect check; run by hand, with Playwright from the global module path). `packages/web-panels/scripts/variables-e2e.mjs` checks the Variables panel and the mode switch the same way (it adds a collection and a frame to the file; the Variables section of the right card opens the panel). In `apps/web`: `npm run typecheck` (svelte-check), `npm run lint`, `npm test` (vitest, also `just test`), `npm run build` (to `dist/`), `npm run ui-literals` (colours, font families and sizes, durations and pixel sizes only in `packages/web-tokens/src/tokens.ts` and `tokens.css`), `npm run licences` (npm licences against the allowed set; the dev-only MPL-2.0 `lightningcss` of Tailwind is the one exception), and `npm run check` for all of them.
- `just dev-smoke` (`tools/dev-smoke.sh`): starts the server binary on a random port with a throwaway token and a scratch database, submits an op over REST, restarts the server and checks the file is restored from Postgres. Skips without `DATABASE_URL` (fails with `MELDFRAME_REQUIRE_PG`); the migrations CI job runs it.
- Postgres tests: `crates/core/meldframe-server-tests/tests/pg_*.rs` (the shared store contract, the restart test and the schema checks for `PgStore`) skip with a printed `SKIPPED` unless `DATABASE_URL` is set (`MELDFRAME_REQUIRE_PG=1`, set in CI, makes that a failure); `PgStore` applies `migrations/` with the sqlx migrator and refuses a database loaded by `psql -f` (the dev seed lives in its own `dev_seed` schema, so `meldframe_dev` is fine); `DATABASE_URL=postgres://postgres:postgres@127.0.0.1:5433/meldframe_test cargo test -p meldframe-server-tests --test pg_contract --test pg_restore --test pg_isolation` runs them (each test uses a schema of its own).
- `just test`: run the test suite. `just check`: everything to run before opening a pull request (pull request CI runs only the fast part; the rest runs on push to `develop` and nightly).
- `DATABASE_URL=postgres://postgres:postgres@127.0.0.1:5433/meldframe_dev` and `TEST_DATABASE_URL=...meldframe_test`; override the port with `MELDFRAME_PG_PORT`.
- Development seed (`scripts/dev-seed.sh`): workspace `ws_dev`, file `file_dev` and a random per-install token (printed once, saved to the git-ignored `.dev-token`, only its hash is stored). It is idempotent, only runs against `meldframe_dev` or `meldframe_test` on this machine (`scripts/dev-seed-test.sh` checks the guards), and refuses to run when `MELDFRAME_ENV` is `release`, `production` or `prod`, `MELDFRAME_RELEASE` is `1`, or `PROFILE` is `release`. The server must never load it in a release build.
