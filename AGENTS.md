# AGENTS.md: meldframe

Design canvas for humans and AI agents. Pre-alpha; docs first, no product code yet.

## Where to look

- Product context, before any design or copy work: `PRODUCT.md`.
- Terms, before naming anything or writing docs: `GLOSSARY.md`. Use its words; the `_Avoid_` words stay out of code, docs and tool text.
- Requirements, before scoping a change: `docs/prd.md`.
- Structure and seams, before adding a module or changing an interface: `docs/architecture.md`.
- Why a hard-to-reverse choice was made, before reopening it: `docs/adr/`.
- Open decisions and order of work: `docs/roadmap.md`. Milestones, epics, acceptance and exit criteria, before starting any work item: `docs/epics.md`. Owner decisions: `docs/decisions.md`.
- Layering, detachable modules, the app layer, the gate and live events, before adding a crate, module or transport: `docs/standards/modular-thin-ui.md` and ADR-0007 to ADR-0010. The front end stack and the order of work (a thin UI audit, then React for the web, then a GPUIX + React desktop spike): ADR-0026 and E7 in `docs/epics.md`.

## Workflow

Full contributor rules: `CONTRIBUTING.md`.

- Branch from `develop` with a prefix (`feat/`, `fix/`, `docs/`, `chore/`); rebase onto `develop`; one logical change per pull request; squash merge with a clean message.
- Sign off commits (`git commit -s`). Write repository artifacts in English.
- Test first for behaviour changes: a failing test at the agreed seam, then the minimal change.
- Put no AI attribution in commits, pull requests, docs or comments.
- Before opening a pull request, run Cora as an agent reviewer on the full diff and put the verdict in the description (`CONTRIBUTING.md`). The CI Cora review also runs on every pull request, but the local agent review stays required. Do not edit a description after opening: it restarts CI.
- Merge only after the owner approves.

## Layers

Every crate declares its kind (core, engine, integration, os, feature, app, ffi, ui, feature-ui, bin, tool); the checker (`cargo xtask deps-check`, from E0) enforces the matrix in `docs/architecture.md` section 3b. Feature modules never import each other except composite crates; UI crates hold no business state and use tokens only; every change passes the admission gate. The product is a modular monolith (standard v1.4, `docs/standards/modular-thin-ui.md` D1): one small module per page or capability, shared pieces in reusable modules of their own and never copied, a new page is a new module with its own tests. A file stays under 500 lines; a crate with a single seam aims for 1,500 to 2,500 lines and never passes 50,000 (above 2,500 it is a candidate for a planned split); ceilings only go down. Text from a model, a server or a file is made safe to display, and capped, once where it enters the app layer (U9). A toolkit or a target is swapped by replacing `ui`, `feature-ui` and `bin` crates only, front ends that share a language share one set of view crates, and the host decides which kinds of client it accepts (U10 to U12). What a person types into a property field, the manage view of the Variables, the tab of the right card and the question of the Activity panel, whether a dialog or one of the two overlays (the shortcut sheet and the command palette) is open (menus, tooltips and popovers stay with the component library), and the raw answers of the server (`Action::Wire`: the shell hands over the status and the text and parses nothing) are the app layer's (`docs/architecture.md` section 3d): a front end sends the text or the click and draws the state, and a new rule of that kind is written in Rust first, with its test at the app seam.

## Commands

- `cargo xtask deps-check`: reads `cargo metadata` and enforces crate kinds and the dependency matrix (`docs/standards/modular-thin-ui.md` L1 to L4). Each crate declares `[package.metadata.meldframe] kind = "..."` (feature crates also `group`, and `composite = ["group"]` to import another group; a `group` on a crate that is not feature or feature-ui fails, and so does a `composite` that names a group no feature crate declares). Prints every violation and exits non-zero on any.
- `cargo xtask build-matrix`: builds the workspace with default features off, then each declared feature of each crate alone (M3), then runs the tests of each crate with default features off (so `apps/server` proves that a feature left out removes its tools: `cargo test -p meldframe-server --no-default-features`). Fails if any step fails.
- `cargo xtask portable-check`: builds every portable-kind crate (core, engine, integration, os, feature, app, ffi) for `wasm32-unknown-unknown` (L5). `rust-toolchain.toml` installs the target; otherwise run `rustup target add wasm32-unknown-unknown`.
- `just wasm-test`: runs the unit and integration tests of `meldframe-order`, `meldframe-check`, `meldframe-css`, `meldframe-text`, `meldframe-core`, `meldframe-layout`, `meldframe-render`, `meldframe-export-tests`, `meldframe-history`, `meldframe-revert`, `meldframe-sync`, `meldframe-sync-props`, `meldframe-variables-tests`, `meldframe-variables-limits-tests`, `meldframe-variables-rename-tests`, `meldframe-variables-panel-tests`, `variables-import`, `meldframe-activity-tests`, `meldframe-app-unit-tests`, `meldframe-app-layout-tests`, `meldframe-app-export-tests`, `meldframe-variables-manage-tests`, `meldframe-variables-props`, `meldframe-checkpoint-tests`, `meldframe-app-review-tests` and `html-import` under WASM on Node, from the same test sources as the native run (E1.1). `.cargo/config.toml` sets `wasm-bindgen-test-runner` as the runner of the `wasm32-unknown-unknown` target, so the recipe is `cargo test --target wasm32-unknown-unknown --tests -p ...`. Needs Node and the runner, whose version must equal the `wasm-bindgen` crate in `Cargo.lock`: `cargo install wasm-bindgen-cli --version <that version> --locked`. A test file imports `wasm_bindgen_test::wasm_bindgen_test as test` on `wasm32` only, so a new test file in these crates needs the same two lines (a file without them builds, runs as `no tests to run!` and passes without running a test). The list of crates is the same in three places, the `justfile` recipe and the `wasm-test` job of `.github/workflows/nightly.yml` and `.gitea/workflows/nightly.yml`: change all of them together. Property tests default to 20 seeds under WASM (the environment does not reach a WASM test); the 600-seed runs stay native.
- `cargo build -p meldframe-oracle-runner` then, in `tools/fidelity-oracle`, `npm ci`, `npx playwright install chromium` and `node oracle.mjs --seeds 50` (`--seeds 500` is the nightly): the fidelity oracle (E4.2, `docs/fidelity-contract.md` section 7). The runner (`crates/core/meldframe-oracle-runner`, kind tool) lays fixture files out with the layout core and exports each frame with the `export` crate in both forms; the harness loads both in Chromium and exits 1 when a box is more than 0.05 px from the core's rect, Tailwind differs from CSS, a paint probe fails, an ink edge is more than 1 px away, or a known gap in `known-gaps.mjs` starts to pass. A failing fuzz seed prints its file: add it to `fixtures.mjs`. `npm test` there checks the gate on made-up results and `npm run sensitivity` that a deliberately wrong export (geometry and paint) fails it. The `oracle` job of pull request CI (not a required check yet) and `fidelity-oracle` in the nightly run it; run it by hand before a change to `export`, `meldframe-layout` or the fidelity contract. The gate is verified on Linux only: on macOS the text boxes come out whole pixels off the core with no change to the code (issue 231), so `oracle.mjs` and `sensitivity.mjs` stop there with a note and exit code 2 unless `MELDFRAME_ORACLE_ANY_PLATFORM=1` (a text failure on a Mac cannot be told from that issue), and the `oracle` job of the pull request is the check for a contributor on a Mac. Playwright, Pixi, Tailwind and Inter are exact in the lockfile: a browser upgrade is its own change.
- `tools/check-protocol.sh`: regenerates the TypeScript types in `packages/protocol/src/generated` from `meldframe-protocol` and the app layer (`meldframe-app`: Action, Effect, Event, AppState), compiles a sample consumer with `tsc` and fails if the generated files differ from the committed ones. Run it and commit the result after any change to the protocol types.
- `tools/build-wasm.sh [out-dir]` (`just wasm-build`): builds `meldframe-wasm` for `wasm32-unknown-unknown` and runs the `wasm-bindgen` CLI (the version of the `wasm-bindgen` crate in `Cargo.lock`; the script says how to install it) into `apps/web/.wasm` (git-ignored). `tools/check-wasm.sh` (`just wasm-smoke`) builds the Node glue into a temporary directory and runs `tools/wasm-smoke.mjs` on it: the JSON boundary (Action in, Effects out, state, nodes, the scene and events as JSON, the Activity panel's and the checkpoints' actions, frames, effects and state among them) through the real wasm. The browser gets the same nine calls as `Bridge` in `crates/app/meldframe-wasm` (the ninth is `hit(x, y)`: the id of the front-most node under a world point, or `undefined`, from the one rule of `meldframe_render::HitIndex`; T9), and `displayText(raw, maxChars)` (`meldframe_text::label`: the one text helper of rule U9 for a screen that has no app state, the error page). The host configuration is checked there too: `setLayoutOnCanvas`, and `setMeasurer` (a JavaScript function sizes a hug text; a function that throws, or answers NaN, a negative, an absurd size or something that is not a pair of numbers, gets the stub's size).
- `PROFILE=release WASM_TARGET=nodejs bash tools/build-wasm.sh <dir>` then `node tools/hit-perf.mjs <dir> [node counts...]` (T9, decision 43, question 4): the milliseconds of one `hit(x, y)` call through the real wasm glue under Node, for 1,000, 5,000 and 19,999 nodes by default, with the layout on the canvas on and off: a call over a box, a call over nothing (the scan reads every box), and the first call after an edit, which builds the scene and the index again. Exits 1 when a call is over a quarter of a frame at 60 Hz (p99); the first call after an edit is printed and not judged. The numbers it gave when it was written are in `docs/front-end-rules-decisions.md` (T9).
- `tools/mutation-check-sync.sh [name...]`: the E1.1 mutation check. Switches one replica or history rule off at a time (dependency rule on the client and on the test server, per-actor undo, put-back of a refused undo, and more), runs the history, sync and property tests, and fails if a mutant survives. Each mutant gets a quick pass first (stops at the first failing test binary, `MELDFRAME_MUTATION_SEEDS` property seeds, 100 by default) and the full pass only when it survives that; `--list` prints the names. `MELDFRAME_SEEDS=n` sets the seeds of the full pass (600 by default; `MELDFRAME_SEED=n` replays one). It edits source files in the working tree, one mutant at a time: run it in a throwaway worktree (`git worktree add --detach ../mutation-check`, with its own `CARGO_TARGET_DIR` as in "Parallel worktrees": its first run builds from scratch), never in a checkout with uncommitted work. It refuses to start a mutant on a file that has local changes and restores the file with a trap on exit, but a run killed with SIGKILL, or a power cut, can leave a mutated file behind: `git checkout -- <file>` fixes it. The full list is long (`--list | wc -l` counts it: 71 when this was written), each mutant rebuilds and tests the sync and history crates: the reporter of issue 235 saw about 10 mutants in 15 minutes (one run, so one to two hours of full CPU is their figure, not a measured bound). Do not run the full list on a developer machine; give it a few names (`tools/mutation-check-sync.sh <name>...`) when you work on the replica and history rules. The whole list runs on Linux in the `mutation-check` job of `nightly.yml`. It avoids the constructs that broke it under the bash 3.2 and the BSD `sed` of a stock Mac (the table is read with `read -d ''`, and the substitution does not use `sed -i`); `scripts/mutation-check-portable-test.sh` (run by `just check`) searches for them and runs a copy against a `sed` shim that models only the `-i` difference and a fake `cargo`; it has not been run on a Mac.
- `tools/connect-claude.sh [--port N | --listen HOST:PORT] [--token TOKEN] [--name NAME]`: prints the `claude mcp add` line for the MCP endpoint of a development server (`docs/quickstart-agent.md`). The address comes from the arguments, then `MELDFRAME_LISTEN`, then `127.0.0.1:8080`; the token from `--token`, then `MELDFRAME_AGENT_TOKEN`, then `.dev-token`, and a token under 16 bytes is refused. It starts nothing, calls no server and writes no file.
- The `import_html` MCP tool (E4.4, `docs/import-html.md`, ADR-0024): HTML and CSS text that an agent has read, as nodes, one atomic batch of at most 100 commands, Change tier, Policy Auto, its own cargo feature `html-import` of `apps/server` (default on; `cargo test -p meldframe-server --no-default-features` and `cargo xtask build-matrix` show that a build without it has no tool). The importer is `html_import::map::import` (a pure function of the text, portable; tests in `crates/features/html-import/html-import/tests` (`map_*.rs`, `import.rs` and `roundtrip.rs` among them), all under WASM), the adapter is `meldframe-http-html-import` and its tests, a real MCP client against the real server, are `meldframe-mcp-tests` (`tests/import_html*.rs`) (native only). No URL is fetched, no `<link>`, `@import`, `url()` or `src` is followed and nothing runs. After a change to the tool text or schema, `cargo test -p meldframe-review-tests --test regenerate -- --ignored regenerate` rewrites `docs/mcp-tools.json`, and `skills/meldframe/SKILL.md` follows the text.
- `tools/check-migrations.sh`: creates a scratch database on the Postgres at `ADMIN_DATABASE_URL` (default `postgres://postgres@127.0.0.1:5433/postgres`), applies `migrations/*.sql` to it from empty, asserts the schema version and append-only rules, then drops it.
- `cargo xtask size-check [--base <git-ref>]`: 500 lines per file and a hard ceiling of 50,000 per crate (D1; the ideal band of a crate with a single seam is 1,500 to 2,500), counting rs, ts, tsx, js, mjs, css, scss, svelte and html files, in every crate and also in the source that no Cargo package owns (each directory of `tools/`, such as `tools/fidelity-oracle`, each `packages/*` directory without a manifest, such as `packages/protocol`, and the files directly in `tools/` as the unit `tools`). After its result line it prints a note naming each crate above 2,500 as a candidate for a planned split (never a failure; nothing is printed when there is none). `xtask/size-allow.toml` lists what is over a ceiling; an entry must equal the current size, so entries only go down, and an entry for something within its ceiling fails as not needed. With `--base` (`--base <ref>` or `--base=<ref>`; the ref must resolve, otherwise the check errors; use `origin/develop` in CI) an entry that is new or higher than on the base fails.
- `cargo xtask mm-check [--base <git-ref>] [--list]`: the modular monolith rule of D1 as a check (`xtask/src/monolith.rs` has the rules and their limits, `xtask/monolith.toml` the limits and the allow-lists; text only, a few seconds; issue 314). MM1: in a crate above the threshold (4,000 lines, tests included) with a `src/lib.rs`, the root holds only docs, `use`, `mod`, `pub use` and attributes, at most 150 lines. MM2: such a crate has at most 40 top-level modules, each a file of at most 500 lines or a directory of at least 2 files whose root obeys MM1, starting with a one-sentence `//!` doc naming the capability (`--list` prints them). MM3: two files with a function of the same body (25 tokens or more, tests left out) fail, in any crate; `[[allow_copy]]` lists today's groups. MM4: a pattern of `[shared.<name>]` (the hidden-character sets, hex colour, asset id, CSS number reader) written outside its home fails with "use <home>"; `[allow_shared.<name>]` lists today's files. MM5: top-level modules of a monolith that use each other in a cycle fail. MM6: a crate named `*-tests`, `*-props` or `*-scenarios` with no source of its own fails; `[allow_test_crate]` lists the ones that remain (issue 316 moves them, `docs/test-crates-plan.md` says which and why). Every allow-list entry has a reason and only goes down: one that no longer matches fails as not needed, and with `--base <ref>` (use `origin/develop` in CI) an entry that is not on the base fails (an entry may shrink, so deleting one copy of three is progress, and may follow a moved file: a copy group matches the base by function name, a file of `[allow_shared]` by file name; a group that gains a member fails; a configuration that is not on the base yet is being introduced, and passes with a note). Limits: MM3 finds exact copies only (the same rule with another variable name, error type or loop is not found); MM4 is as good as the pattern list somebody keeps up to date; MM5 sees `crate::<module>` paths, not a re-export under another name; none of it checks that a shared helper is a good one, only that there is one. Pull request CI runs it with `--base`, the nightly runs it, and `just check` runs it.
- `cargo xtask ui-literals`: rejects colour, font-size and duration literals in `ui` and `feature-ui` crates (Rust, CSS and the React `.tsx` files of the web packages) and in `apps/web` styles, Svelte and `.tsx` files (U4; the fast baseline for the web client: `npm run ui-literals` in `apps/web` is the strict, authoritative check there, covering TypeScript, named colours, Tailwind arbitrary values and more, and CI runs both). For `.tsx` both read JSX style objects (`fontSize: 13`, `transitionDuration: 200`; the strict script also a bare number as a length), `text-[13px]`-style class strings and JSX comments (`{/* */}`, trailing `//`). Read values from the tokens module (`crates/ui/meldframe-ui/src/tokens.rs`, `packages/web-tokens/src/tokens.ts`); only those three files, `crates/ui/meldframe-ui/src/tokens.rs`, `packages/web-tokens/src/tokens.ts` and `packages/web-tokens/src/tokens.css`, are exempt.
- `npm run boundaries` (in `apps/web`; `packages/web-tools/scripts/boundaries.mjs`): the TypeScript counterpart of `cargo xtask deps-check` (E7.2, audit finding T18). Every package under `packages/` and `apps/web` declares `"meldframe": { "kind": ..., "group": ..., "composite": [...] }` in its `package.json`; the kinds are proto, model, host, kit, view, render, bin and tool, and a view also names its group. It prints each violation as `path:line: [rule] message` and exits non-zero on a missing or unknown kind, an import the matrix of kinds does not allow, a view that imports a view of another group its `composite` does not name, a framework outside its kinds (the `FRAMEWORKS` table in `boundaries-lib.mjs`: svelte and bits-ui in kit, view and bin, pixi.js in render and bin, and in a kit or a view only a `.svelte` file may import them), a `.svelte` file in a package of a kind that has none, and a cycle between packages. Test files and scripts follow the matrix but may import frameworks and test tooling. `packages/web-tools/boundaries-allow.json` lists what breaks a rule today, each with a reason: an entry must equal its number of imports, so entries only go down, and one that is no longer needed fails (`--base <ref>` also rejects an entry that is new or higher than on that ref). It runs in `npm run check` and in the `checks (web)` job of `ci.yml`, in about a fifth of a second. Not covered yet: DOM globals in model packages and union types copied from `protocol` (audit section 5, rules 5 and 8). `npm run lint` lints every `packages/web-*` directory by itself, so a new package needs no entry there.
- `cargo xtask licences --check`: every third-party crate's licence expression must be allowed by `[licenses] allow` in `deny.toml` (D2). The same list drives `cargo deny check` (install with `cargo install cargo-deny --locked`). Model weights have no check yet (no models are shipped).
- Compile-fail tests (`crates/core/meldframe-rooms/tests/ui`, `trybuild`) compare the exact compiler output: after a toolchain bump, or a change to the signature of `Permit::new` or `Room::accept` (the output quotes them), regenerate the `.stderr` files with `TRYBUILD=overwrite cargo test -p meldframe-rooms --test compile_fail` and review the diff.
- Before a pull request: `cargo fmt --all --check`, `cargo clippy --workspace --all-targets -- -D warnings`, `cargo test --workspace`, `cargo xtask deps-check`, `cargo xtask mm-check`.

## Parallel worktrees

When several worktrees build at once, give each its own target directory outside the worktree (`export CARGO_TARGET_DIR=<path>`), delete it when the worktree is removed, and watch the free disk space (a target directory is several GB). A shared target directory lets worktrees overwrite each other's `meldframe-*` artifacts: false "cannot find" errors (an `xtask` binary built for another worktree was a case of this, fixed in #101 for the Cargo workspace root, but the overwrite itself remains). The `just` recipes and `cargo xtask` honour the variable through cargo; unset, the target stays in the worktree.

## CI

GitHub Actions in `.github/workflows/` (the repository is hosted on GitHub; `develop` is protected and the required checks are `checks`, `migrations` and `pr checks`): `ci.yml` (the fast set in two jobs, `checks` and `migrations`: scripts self-test, format, lint with warnings as errors, tests, `deps-check`, `mm-check`, the protocol drift check, and the migrations check; every pull request must pass it; it only reads the compile caches), `ci-cache.yml` (on every push to `develop` it builds what `ci.yml` builds, the lint and the test binaries of the workspace, the Postgres tests and the oracle runner, and saves the caches under the keys `ci.yml` reads: a cache saved by a pull request run is visible to that pull request alone, so without this every pull request compiled about 300 crates from nothing and `checks` took about 14 minutes; not a required check), `nightly.yml` (the heavier gates `build-matrix`, `portable-check`, `size-check`, `mm-check`, `ui-literals`, `licences`, `wasm-test`, `property-tests`, `mutation-check`, nightly on `develop` and on demand: `gh workflow run nightly.yml --ref develop`; run them yourself before a pull request, except `mutation-check`, which runs on Linux and is read from the nightly (see the entry of `tools/mutation-check-sync.sh`)), `pr-checks.yml` (one job: branch prefix, Message Standard, description sections What, Why, Changes, Testing) and `cora-review.yml` (the Cora review of each pull request, run from the base branch so a pull request cannot change its own review; config in `.cora.yaml`; the local Cora agent review stays required). A gate whose command does not exist yet is listed in `.gitea/ci-pending.txt` and passes without running; remove its line in the pull request that adds the command. Check scripts live in `scripts/ci/` (`sh scripts/ci/selftest.sh`). `.gitea/workflows/` keeps equivalent workflows for a Gitea runner, unused while the repository is hosted on GitHub; keep them in step when a workflow changes. The shared check scripts still read `.gitea/ci-pending.txt`.

## Release (develop to main)

A pull request from `develop` to `main` is a release. Pull request CI is the fast set, so before a release is merged run the heavy gates it skips and write the result in `Testing`: `just check` (all of it), `just wasm-test` and `just wasm-smoke`, the property tests with more seeds (`MELDFRAME_SEEDS=6000 cargo test --release -p meldframe-history -p meldframe-sync-props -p meldframe-variables-props`), and the browser checks against the development server: `packages/web-e2e/scripts/editor-e2e.mjs` (with a second token for the checks of another actor), `packages/web-panels/scripts/activity-e2e.mjs` (with a second token for an agent and `MELDFRAME_REVIEWERS` naming the person only, on a file with no batches yet), `packages/web-panels/scripts/checkpoints-e2e.mjs` (the same two tokens, on a file with no ops yet) and, when the MCP surface or the capture changed, `packages/web-e2e/scripts/m1-claude-demo.mjs`. The last nightly run on `develop` must be green, and its `mutation-check` job is the mutation check of the release: read it there (`gh run list --workflow nightly.yml --branch develop` lists the runs; open one to read the `mutation-check` job, because a run is red when any nightly job failed, and take a run on the commit you release) and do not run `tools/mutation-check-sync.sh` in full on a developer machine. When the release needs a fresh result (the replica or history rules changed since the last run), start one on demand with `gh workflow run nightly.yml --ref develop` (`nightly.yml` has `workflow_dispatch`; it runs every nightly job, not only that one) and wait for it (it queues behind a nightly that is running, a later run queued behind the same one replaces it, so check that the run you read is on the commit you release and was not cancelled; the `mutation-check` job may take up to 150 minutes). `Testing` names the nightly run (its link or id and its commit) that the mutation check was read from. A release that skips one of these says which and why. Nothing here runs in pull request CI: a heavy check is run on purpose, at a release, and by hand before a change that touches what it covers, except the full mutation check, which stays in the nightly (before a change to the replica or history rules, run `tools/mutation-check-sync.sh` with a few mutant names).

## Rules that are easy to break

- Keep pull requests small: 15 files or fewer (ceiling 20) and under 1,000 changed lines (ceiling 1,500; 600 to 1,000 is normal for a feature slice), one kind of content. Lockfiles, generated files, pure moves, snapshots and large fixtures do not count; tests do. A large or mixed pull request is slow to review and hard to review well; split it by layer, crate or feature slice (a short stack is fine) and plan the boundaries before parallel work. Going over a ceiling needs a written reason under `## Why`.
- Nothing public is created (accounts, domains, packages, registries) without an owner order.
- Do not carry PPTX, Flutter or Dart.
- Do not start new spikes; build the first vertical slice in this repository with exit criteria written first.
- Never invent users, metrics, testimonials or prices.

## Development

Needs `just`, `psql` and either Docker or local Postgres 16 binaries. Copy `.env.example` to `.env` (development values only).

- `just dev-db`: start Postgres on `127.0.0.1:5433` (databases `meldframe_dev`, `meldframe_test`) and load the development seed. Uses `docker compose` when a Docker daemon is reachable, otherwise `scripts/pg-start.sh` starts a local cluster without Docker (idempotent; run it again after a sandbox or machine restart; it finds the binaries in `/usr/lib/postgresql/*/bin` or Homebrew's `postgresql@16`, and `MELDFRAME_PG_BIN` names the directory of `pg_ctl` for any other place; with Docker reachable it needs none).
- `just dev`: the one command for development (`scripts/dev.sh`): starts Postgres (as `just dev-db`), applies the seed, generates a development token on first run (saved in the git-ignored `.dev-token`, printed once, handed to the server through `MELDFRAME_DEV_TOKENS` in the environment, never argv) and runs the server on `http://127.0.0.1:8080` (override with `MELDFRAME_LISTEN`) on `DATABASE_URL`. The server applies the migrations itself when it connects (the sqlx migrator owns the schema of `public`; the seed lives in the separate `dev_seed` schema, so the two never clash; never load `migrations/*.sql` into the dev database with `psql -f`, `PgStore` refuses it). Without `DATABASE_URL` the binary keeps files in memory. Retention: a batch header and its note live as long as the file (they are removed with the file's row; no route or tool deletes a header or changes a note, and the first note a batch gets stays), are not charged to the workspace's storage quota, and are capped at 2,000 headers for one actor in a file, 20,000 in a file and 200,000 in a workspace (past a cap the call still writes, and the batch has no number, note or review); without `DATABASE_URL` they live in memory and go when the server stops. There is no moderation action; removing a stored note is a risky operator task done by hand in the database, and the steps are these. In one transaction in a maintenance window: take the lock the store takes (`pg_advisory_xact_lock` on the workspace's batches, `lock` in `crates/integrations/meldframe-store-pg/src/batches.rs`); disable the trigger `batches_guard` on `batches`, which holds for the whole table until it is enabled again; set `note` to null on the row (`file_id` is the file's room key, with `n`) and its `rev` to the `next_rev` of that file's row in `batch_files`, then raise `batch_files.next_rev` by one (the store takes a `rev` the same way, and the app layer keeps the highest `rev` of each batch, so a note removed without a new `rev` stays on screen in open editors); enable the trigger again before the transaction ends. No frame is sent, so an open editor drops the note only when it next reads the list (a reload, or opening the Activity tab). A retry of the same key with a note can set the note again, because the first note a batch gets wins and the batch has none now. Try the steps on `meldframe_dev` first. Limits: a note is at most 500 characters and 3 line breaks with no hidden characters (a bad note refuses the whole call); the list route returns 100 batches a page at most (50 by default), `get_batches` 50 (20 by default), and the panel holds the newest 500 batches and 32 lanes. What the person sees, in the Activity tab of the right card: a lane for each actor (Agent or Person, and Working, Quiet or Idle), its batches newest first, each with its number, time, how far it got, review state and who last changed it, a summary of what it changed, the note as "Agent note from <actor>" in quotation marks, Show, and Revert behind a confirmation (a batch from before the page loaded says it cannot be reverted from the page); Accept, Needs review and Clear only to a listed reviewer; "N batches to review" on the tab and above the lanes (or "Unknown" while the server's count is not known: no batch frame or page of the list has said it yet, or the first list failed to load); and the checkpoints with Restore. With `MELDFRAME_REVIEWERS` unset the review buttons never show and the route answers `forbidden`. The browser check is `packages/web-panels/scripts/activity-e2e.mjs`.
- Checkpoints, operator notes (E5.3, ADR-0023). A checkpoint is a row beside a file's log (`meldframe-http-checkpoints`, `checkpoint-store`, `meldframe-store-pg` with migration 0008; the rules are `meldframe-checkpoints`): the file as the server had it after change `seq`, never a copy and never an op. The module is the cargo feature `checkpoints` of `apps/server` (default on; it needs `mcp` and `activity`): left out, there is no run sink, no route and no registry entry for `checkpoint_create` (a Change) and `checkpoint_state` (a Read), neither of which is an MCP tool, so a deployment can deny them. The server takes a `runStart` row itself when an actor whose name starts with `agent:` writes after 5 minutes without a write of its own (the prefix test stands until ADR-0022 gives a principal a kind; the detector is in memory, so the first write after a restart takes one extra row; `just dev` runs the editor as `agent:dev`, so its writes take rows too). A person makes the others: only the actors of `MELDFRAME_REVIEWERS` (the list of the Activity notes above) may create a checkpoint or read a file at one, and the list route is open to the workspace, so a name reaches an agent that lists. Retention: a file keeps 100 rows, 50 `manual`, 25 `beforeRevert` and `beforeRestore` together and 25 `runStart`; an actor has at most 20 `manual` and 10 `runStart` rows in a file; an automatic row past its share rolls the oldest of its own kind (never another kind, never a `manual` row), a `manual` row past its share is refused as `checkpoint_full`; rows are not charged to the storage quota, go with the file (cascade) and are never deleted or edited by a route. Without `DATABASE_URL` they live in memory. `GET .../{n}/state` replays at most 5,000 ops from the latest snapshot (`too_far` beyond), costs 8 calls of the caller's bucket on a miss and is cached (64 answers, 16 MiB). Removing a stored name is a risky operator task done by hand, as for a batch note: in one transaction in a maintenance window, take the lock the store takes (`select pg_advisory_xact_lock(hashtextextended('checkpoints:' || octet_length(ws) || ':' || ws, 0))` with `ws` the workspace id; `lock` in `crates/integrations/meldframe-store-pg/src/checkpoints.rs`); disable the trigger `checkpoints_immutable` on `checkpoints`, which holds for the whole table until it is enabled again; set `label` to null on the row (`file_id` is the file's room key and `n` its number; the table allows a `manual` row with no label and the counts do not change); enable the trigger again before the transaction ends. No frame is sent, so an open editor drops the name when it next reads the list (a reload, or opening the Activity tab). Try the steps on `meldframe_dev` first. The browser check is `packages/web-panels/scripts/checkpoints-e2e.mjs` (the header says how to start the server on Postgres and the page; it refuses a file that has ops).
