# Contributing to Meldframe

Meldframe is a closed-source design canvas for people and AI agents. The repository is private; changes come from the owner's team and the agents it works with. This page is the short version of how a change gets in. [AGENTS.md](AGENTS.md) is the same rules written for coding agents, and it wins if the two ever differ.

## Before you start

- Read the requirement and the epic you are working on: `docs/prd.md`, `docs/epics.md` (milestones, acceptance criteria, definition of done).
- Use the words in [GLOSSARY.md](GLOSSARY.md). Words marked _Avoid_ stay out of code, docs and tool text.
- For a new crate, module or transport, read `docs/architecture.md` and `docs/standards/modular-thin-ui.md` first. Decisions that were hard to reverse are in `docs/adr/`; do not reopen one without a new ADR.
- Nothing public (accounts, domains, packages, registries) is created without an owner order.

## Workflow

1. Branch from `develop`. The branch name starts with `feat/`, `fix/`, `docs/`, `chore/`, `refactor/`, `perf/`, `test/`, `ci/`, `build/` or `release/`, then a lowercase slug (`feat/room-snapshots`). CI rejects other names. `main` receives releases only: a pull request from `develop` after the heavy gates of "Release" in `AGENTS.md` have run.
2. Write the failing test first for any behaviour change, at the agreed seam, then the minimal change.
3. Commit with [Conventional Commits](https://www.conventionalcommits.org/) (`feat(core): ...`) and sign off every commit: `git commit -s`.
4. Rebase onto `develop` (no merge commits) and push with `--force-with-lease`.
5. Open a pull request into `develop` with the template. It needs four sections, each with text: **What**, **Why**, **Changes**, **Testing**. Link the issue (`Refs #n`).
6. Keep a pull request small: one logical change, one kind of content (workflow, shell scripts, Rust code, documentation), about 400 changed lines and 10 files at most. Split anything larger. Small pull requests are quick to review; large mixed ones are slow to review and can exhaust the CI Cora time budget.
7. A pull request is squash-merged with a clean message, and only after the owner approves.

## Message Standard

Commit messages, pull request titles and pull request descriptions carry no AI attribution. CI rejects a `Co-Authored-By` trailer, a `Claude-Session` trailer, a `claude.ai` or `claude.com` link, and a "Generated with" or "Generated by" footer, in every commit of the branch and in the pull request title and description. CI cannot see the final squash message, so whoever merges checks it. The same rule applies to code, comments and docs.

To check a branch before you push (this prints nothing when it is clean):

```sh
git log origin/develop..HEAD --format=%B | sh scripts/ci/message-patterns.sh
```

## Checks

Run all of these yourself before you open a pull request. Pull request CI runs only the fast set (format, lint, tests, `deps-check`, the protocol and migrations checks, and the pull request checks); the heavier ones (`build-matrix`, `portable-check`, `size-check`, `ui-literals`, `licences`) run nightly, so a gap in local checking is caught within a day:

```sh
cargo fmt --all --check
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace
cargo xtask deps-check        # kind and group rules, UI toolkit usage
cargo xtask build-matrix      # the product builds with no features and with each feature alone, and tests run with defaults off
cargo xtask portable-check    # portable kinds compile for each planned target
cargo xtask size-check        # 500 lines per file, 2,000 per crate; the allow-list only shrinks
cargo xtask ui-literals       # no colour, font, size or duration literals in UI crates
cargo xtask licences --check  # dependency and model licences
```

These commands arrive with the workspace and the `xtask` crate (T0.1 to T0.3). Until then the matching CI jobs are listed in `.gitea/ci-pending.txt`: they report success without running, and the pull request that adds a command removes its line so the job starts to count. The CI check scripts live in `scripts/ci/`; `sh scripts/ci/selftest.sh` runs their good and bad examples.

Before you open a pull request, run Cora as an agent reviewer on the whole diff (`git diff origin/develop...HEAD`): `cora mcp` gives `cora.review_prepare`, an independent reviewer judges the prepared prompt and opens the real files, then `cora.review_finalize` with `min_severity=major` gives the verdict. Fix every major or critical finding and review again. Write the verdict in the Testing section when you open the pull request: editing the description afterwards cancels and restarts the CI runs.

The CI Cora review is disabled (`.gitea/workflows/cora-review.yml`, config in `.cora.yaml`) because it exceeded its time budget on the shared runner and delayed the other checks. The local agent review above is required for every pull request. A pull request merges with the fast CI checks green, the local agent review clean and no major or critical finding left.

## Several worktrees at once

When more than one git worktree builds at the same time (parallel agents, or a branch checked out beside `develop`), give each worktree its own target directory, outside the worktree:

```sh
export CARGO_TARGET_DIR=$HOME/cargo-targets/<worktree-name>
```

Worktrees that share one target directory overwrite each other's `meldframe-*` build artifacts. The symptoms look like code bugs: false "cannot find ..." errors; a stale `xtask` binary that checked another worktree's files was one case (issue #99, fixed in #101 for the Cargo workspace root, but the overwrite itself remains). Delete the directory when you remove the worktree, and watch the free disk space: one target directory is several GB. The `just` recipes and `cargo xtask` need no change; cargo reads `CARGO_TARGET_DIR` itself, and without it the target stays in `target/` of the worktree.

## Reporting problems

Open an issue in this repository with the bug, task or epic template. Do not put secrets, tokens or customer data in an issue or a pull request. Conduct questions go to the owner; see [CODE_OF_CONDUCT.md](CODE_OF_CONDUCT.md).
